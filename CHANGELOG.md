# Changelog

All notable changes to Construct are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Began the full-project best-practice audit remediation program (`tests/audit/REMEDIATION-PLAN.md`, tracker epic `construct-bcbo`). Fourteen finding families (F01–F08 P0 trust boundaries, F09–F14 P1 hardening) were each verified against live code by a parallel investigation agent, producing 50 failing red fixtures under `tests/audit/` (104 tests, 97 failing) that pin each defect — model-callable destructive/shell/path tools (F01), live secrets in generated config (F02), unshipped `schemas/`+`registry/` breaking consumer installs (F03), JSONC-silent host config (F04), port-only process kills (F05), a Dockerfile entrypoint deleted by ADR-0039 (F06), unpinned CI actions + unredacted Terraform plan secrets (F07), and absent untrusted-content labeling (F08), plus six P1 hardening families. Fixtures are named `*.red.mjs` (excluded from the auto-discovered suite) and promote to `*.test.mjs` as each fix lands.

### Fixed

- Made `construct-mcp` start by default in VS Code / GitHub Copilot so the orchestrator is usable on open instead of asking the user to "enable the MCP server." VS Code does not auto-start `.vscode/mcp.json` servers unless `chat.mcp.autostart` is set, and the orchestrator's first action is an MCP call (`orchestration_policy`), so a dormant server made it refuse or stall until manually started. `syncCopilot`/`syncVSCode` (`scripts/sync-specialists.mjs`) now write `"chat.mcp.autostart": "always"` (VS Code ≥1.105, string enum) into the generated `.vscode/settings.json` alongside the existing agent-scan pin, via the renamed `pinVscodeChatSettings` helper that applies each managed key only when unset and never clobbers a non-strict-JSON (commented) settings file. This is Copilot-specific — Claude Code, OpenCode, and Codex already auto-start their declared MCP servers (verified). Note: VS Code still requires a one-time per-developer MCP *trust* grant on first launch, which it stores locally and cannot be pre-granted from committed config — `autostart` removes the recurring per-session Start click, not that first trust. Covered by `tests/vscode-mcp-toolkit-path.test.mjs`.

### Security

- Closed a shell-injection vector in the `summarize_diff` MCP tool (F01 / CX-AUDIT-MCP-SAFETY-002). A model-supplied `base_ref` was interpolated into `git diff --stat ${baseRef}` and run through `execSync` with a shell (`lib/mcp/tools/project.mjs`), so a value like `HEAD$(touch …)` executed arbitrary commands on the host — reachable by any prompt-injection that reaches the tool's arguments. The git calls now run via `execFile` with an allowlisted argv (`runGit`), passing the ref as one literal argument the shell never evaluates; refs that start with `-` (git option injection) or carry control characters are rejected. The static `git log`/`git status` calls in `project_context` moved to the same shell-free path. Proven by `tests/audit/f01-mcp-safety/malicious-ref.test.mjs` (a command-substitution payload writes no sentinel after the fix).
- Added root containment for model-supplied file paths in MCP file tools (F01 / CX-AUDIT-MCP-SAFETY-003). `scan_file` resolved `file_path` with no root enforcement and `delete_ingested_artifacts` joined model-supplied `files[]` onto the ingested dir with no check, so a `../` chain, an absolute path, or a symlink could read any file via `scan_file` or **delete** any file outside `.cx/knowledge/internal` via `delete_ingested_artifacts` (a destructive traversal not in the original audit evidence). A new `lib/path-policy.mjs` `resolveWithinRoot` pins each path to a declared root — rejecting `../` escapes, out-of-root absolutes, backslash/UNC separators, and symlinks whose realpath escapes (checked on the longest existing ancestor) — and is wired into both tools; the delete validates the whole batch before removing anything. Proven by `tests/audit/f01-mcp-safety/scanfile-containment.test.mjs` and `delete-traversal.test.mjs`.
- Required a one-time out-of-band approval token for the destructive MCP tools `storage_reset` and `delete_ingested_artifacts` (F01 / CX-AUDIT-MCP-SAFETY-004). These tools are reachable only through the model's argument channel yet authorized destruction on a model-supplied `confirm: true` alone, so a model error, prompt injection, or replayed argument blob could self-authorize irreversible deletion. Destruction now also requires an `approval_token` verified server-side (`lib/mcp/destructive-approval.mjs`): a random token issued out-of-band, persisted 0600 under the user state dir — outside any project root, so the now root-contained `scan_file` cannot read it — scoped per tool, single-use, and expiring after 5 minutes. A bare `confirm: true` is rejected. Proven by `tests/audit/f01-mcp-safety/destructive-confirm.test.mjs`; `tests/mcp-server.test.mjs` updated to the new contract.
- Added a declared output schema and safety classification to every MCP tool (F01 / CX-AUDIT-MCP-SAFETY-001). The catalog's 75 tool defs (plus the `call` gateway) carried an `inputSchema` and description but no `outputSchema` and no read/write/destructive class or filesystem/network/process scope, so a host could not validate tool output or reason about a tool's blast radius. New `lib/mcp/tool-safety.mjs` is a single classification table — derived from each tool's own documented behavior (several are self-declared: `storage_reset`/`scope_archive` as destructive, `model_resolve`/`triage_recommend`/`capability_describe` as read-only) — applied via a `withSafetyEnvelope` decorator that throws if a tool ships unclassified. Declaring `outputSchema` activates MCP SDK client-side validation requiring the response to carry matching `structuredContent`; the `CallTool` handler now returns `structuredContent: toolResult` alongside the existing text content (every dispatch branch already returns a JSON object, so this satisfies every tool's schema). Proven by `tests/audit/f01-mcp-safety/safety-envelope.test.mjs` plus the existing `host-mcp-emulation.functional.test.mjs`, which caught the missing `structuredContent` as a real client-side protocol error before this fix.
- Added a per-tool call-rate budget and a durable audit record to every MCP tool call (F01 / CX-AUDIT-MCP-SAFETY-005, closing the family). `lib/mcp/broker.mjs`'s `Broker` already had rate-limiting and audit-trail machinery, but it is role/policy-based and only instantiated in team/enterprise mode — `Broker.invoke` was never actually called from the live `CallTool` dispatch path in any deployment mode, so solo mode (the default) had no bound on how often a tool could be called and no audit trail for tool calls at all. New `lib/mcp/tool-rate-limit.mjs` (`ToolRateLimiter`) applies a sliding-window budget tiered by safety class (destructive: 5/60s, write: 60/60s, read: 300/60s — `CONSTRUCT_MCP_TOOL_RATE_WINDOW_MS=0` disables, mirroring the existing timeout-override convention), keyed on the real underlying tool even when called through the `call` gateway so one long-tail tool's budget can't conflate with another's. Every call now also lands a value-free record (tool name, safety class, ok, duration — never arguments or result content) in the existing tamper-evident `lib/audit-trail.mjs`, queryable via `construct audit trail --tool=<name>`. This completes F01: every MCP tool now carries the full envelope the audit asked for — input/output schema, safety class, root containment, an out-of-band confirmation model, a timeout, a rate budget, and an audit log. Proven by `tests/functional/mcp-tool-rate-audit.functional.test.mjs`, which drives the real server as a subprocess and confirms both the audit record and the rate-limit rejection through the actual protocol path.
- Enforced 0600 on `config.env` at its single write path (F02 / CX-AUDIT-SECRETS-003). `writeEnvValues` (`lib/env-config.mjs`) wrote the credential-bearing `config.env` with no mode, so it landed at the umask default (0644 — group/world readable) whenever a caller skipped its own post-write chmod (several do: `setup.mjs`, `service-manager.mjs`, `legacy-config-migration.mjs`, `roles/preference.mjs`). The write now sets mode 0600 and re-applies 0600 on every rewrite (`fs.writeFileSync` keeps an existing inode's mode, so the mode option alone cannot tighten a file an earlier write left loose), POSIX-guarded. Proven by `tests/audit/f02-secrets/config-env-mode.test.mjs`. The remainder of F02 is owned by the in-flight `construct-trxz` secrets epic and cross-linked rather than duplicated: the stdio MCP env value→reference flip (`construct-trxz.12`) stays deferred because it needs validation against real installed hosts (whether Claude/VS Code/OpenCode expand a `${VAR}` reference inside a stdio `env` block, and Codex has no interpolation at all), and the resolver precedence alignment plus worker/daemon audit-trail wiring (`construct-trxz.13`) sit on `construct-trxz`'s resolver redesign.
- Shipped the repo-root data directories the runtime loads in the published package (F03 / CX-AUDIT-PACKAGE-002). `package.json` `files` omitted `registry/` and `schemas/`, yet the runtime reads `registry/capabilities.json` (`lib/registry/validate.mjs`), `registry/agent-manifest.json` (`lib/registry/agent-manifest.mjs`), and `schemas/*.json` (`lib/embedded-contract/capability.mjs`) from the package root — so a consumer `npm install` got a package whose registry/schema validation and capability inventory were broken on first run (`loadAgentManifest` threw ENOENT; 17 of 21 schemas were silently dropped). Two further repo-root dirs the runtime reads were also unshipped and are now included: `config/tag-vocabulary.json` (`lib/tags/vocabulary.mjs`, which hard-throws on a missing vocabulary) and `vendor/pandoc-ext/diagram.lua` (the `publish`/figures path). `files` now lists `schemas/**`, `registry/**`, `config/**`, `vendor/**`. Proven by `tests/audit/f03-package/packed-asset-parity.test.mjs`, which runs a real `npm pack`, extracts the tarball, and asserts every runtime-loaded repo-root directory is present.
- Made a half-staged project detectable and repairable (F03 / CX-AUDIT-PACKAGE-005). `stageProjectAdapters` (`lib/install/stage-project.mjs`) could return `{ staged:true, synced:false }` — the `.construct/` launcher staged but `.claude/` adapters never synced (the bundled sync script missing, or `sync-specialists.mjs --project` exiting non-zero) — and both callers (`bin/construct-postinstall.mjs`, `construct init`) discarded the result, so a project left half-built was invisible with no repair path. Staging now records every outcome in a durable `.construct/stage-state.json` marker (best-effort: a marker-write failure never turns a successful stage into a reported failure) and exports `readStageState` plus `repairStagedProject`, which re-drives a half-staged project to a synced state idempotently and no-ops when already synced. Proven by `tests/audit/f03-package/half-stage-recovery.test.mjs`.
- Added an itemized mutation manifest to the postinstall hook (F03 / CX-AUDIT-PACKAGE-004). `bin/construct-postinstall.mjs` staged `.construct/` launchers and appended Construct ignore patterns to `.gitignore` with no record of what it touched and no recovery command — npm has no uninstall lifecycle hook to reverse these mutations, so a stale or removed Construct dependency left the consumer project permanently mutated with no path to undo. The hook now writes `.construct/install-manifest.json` after the mutation phase: an itemized list of every path it created or appended plus the recovery command (`npx construct init --repair`), best-effort so a manifest-write failure never propagates to fail the consumer's `npm install`. Proven by `tests/audit/f03-package/postinstall-mutation-manifest.test.mjs`, which runs the real hook against an isolated tmpdir consumer and asserts both the receipt existence and its `.gitignore` entry. This completes F03.
- Degated the Docker/container surface per ADR-0039 (F06 / CX-AUDIT-DOCKER-001 through -004). ADR-0039 (2026-06-25) deleted `lib/server/` — the HTTP dashboard daemon — and its ECS/ALB deploy surface, but the `Dockerfile`, the docker job in `release.yml`, and phantom references in ECS Terraform, the ALB health check, deploy docs, and the PRD were left in place. The Dockerfile's `CMD ["node", "lib/server/index.mjs"]` referenced a non-existent file (image builds and immediately exits), and the `HEALTHCHECK curl /api/auth/status` targeted an unimplemented route (no server registered it — the path existed only in deploy config). The docker job in `release.yml` also pushed mutable `:latest`/channel tags BEFORE the Trivy CVE scan step (lines 190/202 vs line 209), so a failing scan could not un-publish a vulnerable image. Remediation: deleted `Dockerfile`, removed the docker job from `release.yml` (replaced its `needs: [build-binary, docker]` with `needs: [build-binary]` in the publish job). Three fixtures in `tests/audit/f06-docker/` now encode the degated contract: each passes when no Dockerfile exists / no docker push step is present, and enforces correctness only if the surface is re-introduced. Updated `tests/release-workflow.test.mjs` (previously asserted docker job behavior). F06 complete (ADR-aligned degate).
- Added ownership-gated stop to the runtime service manager (F05 / CX-AUDIT-RUNTIME-001/-003/-004). `killPortOwners` (`lib/service-manager.mjs`) blindly signalled whatever PID `lsof` found owning a configured port — no verification that the PID was launched by Construct — so a stale or mistyped `MEMORY_PORT`/`BRIDGE_PORT` entry terminated an unrelated developer process that happened to be listening. The fix adds a per-port ownership record: `startServices` now writes `.construct/runtime/port-N.json` when it spawns each service (PID, command, cwd, `marker: 'construct'`, `constructManaged: true`, timestamp). `killPortOwners` reads that record before sending `SIGTERM`; if no record exists or the PID doesn't match or the record lacks Construct markers, the process is not signalled and the result status stays `not-running`. A new `isConstructOwnedPort(processRecord, { port })` export exposes the ownership predicate so the caller can separately reason about ownership without coupling to the kill path. Proven by three fixtures in `tests/audit/f05-runtime-ownership/` (owned-stop: predicate correctness; non-owner-refusal: stop does not kill a foreign PID; stale-port: stop does not kill a real foreign process owning a stale configured port). F05 complete.
- Fixed four VS Code / Copilot host-readiness defects (F04 / CX-AUDIT-HOST-001 through -005, completing the family). (1) **HOST-001**: The MCP eager-start setting was written as `chat.mcp.autostart` (all-lowercase) — VS Code setting ids are case-sensitive; the unrecognized id was silently ignored, so the server was never auto-started. Corrected to `chat.mcp.autoStart` (camelCase, matching the VS Code docs primary source). (2) **HOST-002**: `pinVscodeChatSettings` read existing settings with `JSON.parse` inside a `try { } catch { return }`, so any user with a JSONC settings.json (line comments, trailing commas — the common case for hand-edited VS Code config) silently received no managed keys. The catch now uses a JSONC-safe strip (`parseJsoncContent`) that removes full-line `//` comments and trailing commas before parsing, then writes the result as JSON with the managed keys merged in. (3) **HOST-004**: `mcpEntryPointsOutsideToolkit` detected stale toolkit paths with a POSIX-slash regex and a POSIX-prefix check, missing Windows backslash / drive-letter paths — a stale Windows entry was never refreshed and VS Code silently launched a non-existent construct-mcp. Now normalizes backslashes to forward slashes before comparison. (4) **HOST-005**: The generated Copilot/VS Code custom-agent frontmatter granted `construct-mcp/*` (a wildcard over the entire 75-tool surface) plus `edit/editFiles` and `web/fetch` — not least-privilege for a routing front door. `COPILOT_AGENT_TOOLS` now lists the explicit orchestration tools (`construct-mcp/orchestration_policy`, `orchestration_run`, `orchestration_readiness`) plus read-only context tools; write and outbound access removed. (5) **HOST-003**: Added `lib/host/readiness.mjs` — a discrete host-config readiness classifier (`classifyHostReadiness`) with a typed `HOST_READINESS_REASONS` enum (missing_config / stale_path / jsonc_unpatched / wrong_key / untrusted / disabled / server_start_failure / missing_tool / sandbox_disabled / healthy) that distinguishes actual failure modes rather than collapsing to a file-presence binary; the `construct doctor` lane wire-up is a follow-up bead. Proven by five fixtures in `tests/audit/f04-host-readiness/`. Updated `tests/vscode-mcp-toolkit-path.test.mjs` (previously green-locked the JSONC-skip and lowercase key) and `tests/functional/host-config-parity.functional.test.mjs` (previously asserted the wildcard grant) to reflect the corrected contracts.
- Extended the secret audit trail to non-op (plaintext) resolutions (F02 / CX-AUDIT-SECRETS-005). `enableSecretAuditTrail` (`lib/providers/secret-audit-wiring.mjs`) only wired up `secret.op_read` events — the 1Password CLI path — leaving every plaintext-tier resolution (project .env, config.env, home .env, shell-rc, alt-store) unrecorded, so the common credential path produced no durable audit trail. The wiring now also handles `secret.resolve` events for non-op resolutions, writing a value-free record carrying the source tier and outcome (`project-env`, `config-env`, etc.) but never the materialized credential value; op-ref resolve events are deliberately skipped (they are already covered by the existing `op_read` record). Proven by `tests/audit/f02-secrets/audit-source-tier.test.mjs`. The two remaining F02 beads stay owned by `construct-trxz`: the stdio MCP env value→reference flip (needs real-host validation across Claude/VS Code/Codex) and the resolver precedence alignment (process.env-vs-file tier, live-path risk).
- Hardened CI/CD pipelines against supply-chain attacks and secret leaks (F07 / CX-AUDIT-CI-001 through -004). (1) **Action SHA pins**: all 48 `uses:` references across 10 workflow files were pointing at mutable version tags (`@v6`, `@v4`, etc.) — a compromised action repo could repoint a tag at malicious code that then runs with the pipeline's secrets. Every action is now pinned to a 40-hex commit SHA with the tag retained as a comment: first-party (`actions/*`) and all third-party (`dorny/paths-filter`, `gitleaks/gitleaks-action`, `aws-actions/*`, `hashicorp/setup-terraform`). (2) **Least-privilege `permissions:`**: six workflows had no top-level `permissions:` block, inheriting the repo default (potentially read/write on every resource); one workflow granted `contents: write` workflow-wide. All workflows now declare an explicit top-level `permissions:` (deny-all `{}` where all jobs have their own, `contents: read` where checkout is the only need); `promote-staging-to-main.yml` moved its broad grant to per-job scope. (3) **Policy gate blocking**: the `template policy` step in `ci.yml` carried `continue-on-error: true`, making a policy violation produce a passing job. The flag is removed — policy gates must fail the build. (4) **Release tooling from lockfile**: `release.yml` installed esbuild via `npm install -g` (unpinned global fetch) and invoked `npx postject` (on-demand package resolution) — both inject un-checksummed code into the binary build job. The workflow now runs `npm ci` (with devDeps), adds `node_modules/.bin` to `GITHUB_PATH`, and calls `esbuild`/`postject` from the locked dependency graph; `postject@1.0.0-alpha.6` added to `devDependencies`. (5) **Terraform plan redaction**: the `Post plan to PR` step in `deploy.yml` posted `plan.txt` verbatim into the PR comment — a secret in a planned ECS `environment` attribute (e.g. `TF_VAR_dashboard_token`) was readable by anyone with repo read access and permanently in the PR timeline. The step now applies a redaction pass (`const redacted = truncated.replace(/(,\s*value\s*=\s*)"[^"]*"/g, '$1"***"')`) before posting. Proven by five fixtures in `tests/audit/f07-cicd/`. F07 complete.

## [1.4.1] - 2026-06-30

### Fixed

- Stopped the nightly `hook performance budgets` workflow (`.github/workflows/hook-budgets.yml`, cron `17 7 * * *`) from failing every night. The `guard-bash` PreToolUse hook declared `@p95ms 5`, a target set before it grew the role-fence path (`doctorRoot` lookup, last-agent file reads, lazy `manifest`/`fence`/`approval` imports); the variance-heavy CI bench measured ~17-19ms marginal, so the gate failed persistently from 2026-06-29. The hook and the gate are both load-bearing (it blocks `rm -rf /`, force-push-to-main, fork bombs, destructive DDL, and enforces role fences) and the budget lane is deliberately nightly-only (ADR-0029), so neither was removed — instead the budget is re-baselined to `@p95ms 15` to reflect the hook's real fence-enforcement cost, with the gate's ×2 tolerance still catching a true regression. Per the no-skip-vars rule, the declared budget is raised rather than a skip variable added.

- Enforced research recency in the web-search execution layer so newer evidence is no longer buried under older authority. Recency was thoroughly *specified* (cx-researcher prompt, `rules/common/research.md` §1, `research-execution-policy.recencyRule`, brief templates all mandate most-recent-first and a 12-month staleness threshold) but never *enforced*: `lib/mcp/tools/web-search.mjs` dropped any date from provider results and returned them in provider/relevance order, so a high-Admiralty older source outranked a newer one and the model — handed date-blind, authority-ranked results — surfaced stale information. The tool now normalizes a `date` from whatever field the provider supplies, flags `stale` against the documented 12-month window, and reorders results most-recent-first (fresh → undated → stale, newest first within a tier). Admiralty-derived `confidence` is left intact per ADR-0017 — recency rides alongside as separate `date`/`stale` signals rather than being folded into the grade. Covered by `tests/functional/web-search.functional.test.mjs` (date normalization, staleness flag, most-recent-first ordering over an older A1). Note: the internal RAG/knowledge ranking (BM25/cosine/RRF/MMR) remains relevance-only with no recency decay — a separate follow-up, scoped narrowly to avoid degrading timeless-query relevance.

### Added

- Ship `construct` as a real GitHub Copilot / VS Code custom agent. VS Code reads custom agents from `.github/agents/*.agent.md` and grants tools by its own namespaced ids (`<server>/*`, `web/fetch`, `search/codebase`, …); the Claude-format tool names in `.claude/agents/construct.md` (`Read,Grep,…,orchestration_policy`) are not recognized there, so selecting construct in VS Code surfaced an agent with no usable tools — it would refuse internet/orchestration requests because none of its tools were actually granted. `syncCopilot` (`scripts/sync-specialists.mjs`) now emits `.github/agents/construct.agent.md` with VS-Code-namespaced grants (`construct-mcp/*`, `web/fetch`, `web/githubRepo`, `search/*`, `read/problems`, `edit/editFiles`) and the orchestration prompt as its body, so the picker entry actually scopes in the construct-mcp orchestration tools and live web access. Verified by `tests/functional/host-config-parity.functional.test.mjs`. To stop VS Code listing the orchestrator twice (it also scans `.claude/agents`), sync now writes a `chat.agentFilesLocations` pin into `.vscode/settings.json` (`{".github/agents": true, ".claude/agents": false}`) via a safe merge that never clobbers a JSONC/user settings file and respects an existing choice (`pinVscodeAgentLocations`, covered in `tests/vscode-mcp-toolkit-path.test.mjs`). Per VS Code docs the `.claude/agents` compatibility scan may not be fully suppressible by that setting in every version, so the guaranteed fallback for a residual duplicate is the one-time eye-icon hide in the agents dropdown. MCP servers defined in `.vscode/mcp.json` must also be started in the session — both remain VS Code runtime behaviors to confirm in-editor.

### Fixed

- Corrected the generated GitHub Copilot front-door framing. `.github/copilot-instructions.md` described `construct.prompt.md` as a "reusable role profile for single-pass work" and pointed "real" multi-specialist runs at a separately-invoked `orchestration_run` MCP tool — framing `construct` as a single-pass profile *beside* the orchestrator when selecting the `construct` mode is meant to *be* the orchestrator. The block now states that selecting `construct` from the chat-mode dropdown enters the orchestrator, which classifies the request and dispatches specialists through the `construct-mcp` tools (`orchestration_policy` then `orchestration_run`), names the `.vscode/mcp.json` server dependency, and notes it routes rather than guesses when those tools are unavailable. Emitted from `syncCopilot` in `scripts/sync-specialists.mjs`.

- Healed stale construct MCP server paths in generated `.vscode/mcp.json` so VS Code / GitHub Copilot can actually start `construct-mcp`. The merge in `syncVSCode` (`scripts/sync-specialists.mjs`) preserves existing server entries so user customizations survive a re-sync, but it also preserved a construct-owned server path left behind by a moved or deleted toolkit checkout (a fully-resolved, non-placeholder path) — so VS Code kept launching `node <old-checkout>/lib/mcp/server.mjs`, the server never started, and the Copilot orchestrator had zero construct tools and refused every request. `mcpEntryPointsOutsideToolkit` now flags a construct `lib/mcp/*.mjs` path outside the current toolkit root as stale so the next sync refreshes it to the live path, while genuine user-owned servers (no toolkit path) are still preserved. Covered by `tests/vscode-mcp-toolkit-path.test.mjs`.

- Taught the orchestration policy to route live web/network requests to `cx-researcher` instead of refusing them. Driving the runtime revealed the dispatch-wiring fix (below) was necessary but not sufficient: a bare "connect to the internet" or "fetch example.com" classified as the `immediate` track with no specialist, so the read-only orchestrator (which holds no network tools) still deflected. `requiresLiveWebAccess` (`lib/orchestration-policy.mjs`) now detects explicit web access — a literal URL, an online/internet/connectivity phrase, a `fetch`/`download`/`scrape`/`curl` verb paired with a web object or domain, an "is … online/reachable" probe — and feeds both `requiresExternalResearch` (reason `web-access`, which injects `cx-researcher`) and `determineExecutionTrack` (promotes off `immediate` to `focused` so it actually dispatches). A precision floor keeps local work local: "fetch the user record from the database", "open the config file", "explain how the retrieval path works" do not trigger. The shared orchestration micro-prompt also gained a fallback directive: when a request needs a capability the orchestrator lacks, route it via `orchestration_run` or ask one clarifying question rather than telling the user to run it themselves. Covered by `tests/research-gate.test.mjs`.

- Restored the orchestrator's cross-host dispatch capability. The `construct` persona is a read-only router whose contract is classify-then-dispatch (`orchestration_policy` → `orchestration_run`), but on the Claude Code host it could do neither: two layers were broken. First, `orchestration_run` was never in `CORE_TOOL_NAMES` (`lib/mcp/server.mjs`), so the MCP server advertised it on no host — it was reachable only through the `call` gateway, yet the orchestrator prompt names it directly (invalid on Claude, OpenCode, and Codex alike). Second, Claude Code treats an agent's `tools:` frontmatter as a hard allowlist, and the generated list omitted both dispatch tools, so even the already-flat `orchestration_policy` was blocked. The visible symptom: asked to "connect to the internet," the orchestrator refused and told the user to run `curl` themselves instead of dispatching `cx-researcher` (which holds `WebSearch`/`WebFetch`). The fix promotes `orchestration_run` into the flat core (it is the indivisible second half of an already-core tool — the ADR-0048 "high-frequency action tool stays flat where evidence justifies it" carve-out) and adds a single `ORCHESTRATOR_DISPATCH_TOOLS` source in `scripts/sync-specialists.mjs` that grants both tools to the orchestrator on every host (named into Claude's allowlist; allow-by-default already holds on OpenCode; no per-agent gate on Codex). A new functional test (`tests/functional/orchestrator-dispatch-grant.functional.test.mjs`) asserts the parity across all three hosts plus the MCP surface, so the grant can't silently drift.

## [1.4.0] - 2026-06-30

### Added

- Real-process secret-resolution test coverage (`construct-trxz.9`). A functional test exercises the resolver against a real `op` subprocess (a fake binary on PATH) rather than an injected stub: it proves a repeated `op://` reference spawns `op` exactly once within a process (the in-process cache holds) and that a fresh process re-resolves from a cold cache — pinning the cross-process re-prompt behavior as observed reality. This complements the real-boundary tests added per epic (setup-credentials single-link, credential diagnostics no-leak, service op-run wiring, MCP add no-plaintext, cache-first poll). ## [1.3.0] - 2026-06-29

This release makes OpenCode the primary conversation surface, retires the web/dashboard tier in favor of a terminal-first architecture, and consolidates the legacy registries into a single unified registry (RFC-0004). It contains two breaking changes — see **Removed**.

### Added

- Agent-reachable MCP tool surface: `find_tool` intent-driven tool discovery (ADR-0048), an artifact loop, and OpenCode auth hardening.
- Intent-driven, team-aware orchestration: requests route to teams with blocked-decision handling; typed team integration sources drive scoped `provider_fetch` reads.
- Oracle governance: swarm dispatch, a `cross-team-handoff-blocked` synthesized signal, and team governance oversight.
- Demo plug-in layer: `demo init --from-project`, an expanded canonical catalog of 6 terminal scenarios, and a self-demo guided tour via bare `construct`.
- `construct` CLI primitives: a `display-width` primitive and a shared presentation core with clickable links and chat ticker/wrap fixes.
- `registry:validate --unified` gates the unified registry (RFC-0004 Phase 1.4).

### Changed

- OpenCode is now the first-class conversation surface. `construct sync` installs the front-door agent, MCP wiring, and runtime plugin; the `construct` CLI remains setup/admin/headless infrastructure.
- The previous local conversation-loop capability has been replaced by `surfaces.opencode-primary` in the capability registry.
- All registry consumers (MCP `list_teams`/`get_team`, policy-inventory, staleness graph, doctor watchers) now read the unified registry instead of the legacy `contracts.json`/`teams.json` files.
- Demo execution is recording/tour oriented: VHS and Playwright surfaces are supported, with printed script steps as fallback.
- Research-shaped host conversations now classify through `orchestration_policy` and execute through `orchestration_run`; the OpenCode front-door prompt no longer implies that `workflow_invoke` itself performed evidence gathering.
- OpenCode now emits its host-facing MCP tool ids in the front-door prompt (`construct-mcp_orchestration_policy` / `construct-mcp_orchestration_run`) so research routing can execute instead of failing host-side tool validation.
- PDF artifact generation now preserves ordered-list numbering, loosens body and heading spacing, and widens page margins so published PRDs, decisions, research briefs, and generic PDFs read like release-grade documents instead of cramped exports.
- Bare `construct` launches chat; `construct chat` is deprecated.
- CI gates run through thin `npm run` wrappers over `bin/construct`; the workflows no longer re-spell the underlying commands.

### Removed

- **Breaking:** the `chat --web` browser launcher has been removed. Construct chat is terminal-only; there is no web/browser surface to launch.
- **Breaking:** the legacy `contracts.json` contract files have been deleted. Readers now resolve contracts from the unified registry; any consumer reading `specialists/contracts.json` directly must migrate to the unified-registry shape.
- Retired the dashboard web app and HTTP server, the native desktop chat window, and the dead Ink TUI — Construct is terminal-first (ADR-0039/0041 amended).
- Removed Construct's local conversation UI implementation, related package surface, docs page, and surface-specific tests.
