# ADR-0082: Write control-plane provider IDs canonicalize to the manifest namespace

- **Date**: 2026-07-16
- **Status**: accepted
- **Deciders**: Gerald Dagher
- **Supersedes**: none
- **Resolves**: `construct-4uxq0.4.5` (ADR-E, provider-ID namespace canonicalization) from the continuous-work audit's ADR-beads table in `docs/notes/research/2026-07-continuous-work-audit/target-architecture.md`

## Problem

Construct has two independent provider-identifier namespaces that were never reconciled. The embed capability-proposal layer — capability presets (`lib/embed/presets/tpm.mjs`, `ops-triage.mjs`, `pm-repos.mjs`), the core pack's per-specialist write-proposal grants (`lib/packs/core-pack.mjs`'s `DEFAULT_EMBED_BINDINGS`), and the extension-manifest registry itself (`lib/extensions/manifests/atlassian-jira.manifest.json`, `atlassian-confluence.manifest.json`) — all identify Jira and Confluence by their manifest IDs, `atlassian-jira` and `atlassian-confluence`. The write control-plane's governed-provider allowlist, `KNOWN_PROVIDERS` in `lib/writes/write-intent.mjs:15`, is `Object.freeze(['jira', 'github', 'confluence'])` — short IDs that predate the manifest namespace. `docs/notes/research/2026-07-continuous-work-audit/truth-matrix.md` row 27 grades this `partial`: "Two-stack design is consistent internally but creates a provider-ID namespace mismatch: embed proposals use `atlassian-jira`/`slack`, write control-plane `KNOWN_PROVIDERS=['jira','github','confluence']`."

The mismatch is not hypothetical. A capability preset drafts a Jira ticket proposal with `providerId: JIRA_PROVIDER` where `JIRA_PROVIDER = 'atlassian-jira'` (`lib/embed/presets/tpm.mjs:30,123`), and `lib/embed/capability-jobs.mjs:300-301` enqueues it into the approval queue as tool `atlassian-jira.createIssue` — this enqueue path does not call `write-intent.mjs`'s validator, so the malformed-looking ID is accepted at proposal time. The break surfaces later, at execution time, in two different and differently-dangerous ways I verified directly:
1. `lib/writes/control-plane.mjs:50-54`'s `DEFAULT_ADAPTER_FACTORIES` is keyed by the short IDs (`jira`, `confluence`, `github`). `executeApprovedWriteIntent` (`control-plane.mjs:82-85`) parses the approved record's tool name, looks up `factories['atlassian-jira']`, finds nothing, and throws `no governed adapter registered for provider "atlassian-jira"` — a loud failure, but only reachable when something calls `executeApprovedWriteIntent`/`drainApprovedWriteIntents` directly (truth-matrix row 21 notes the drain is currently dead code, called by nothing outside its own tests).
2. `lib/cli/approvals.mjs:88-97`, the one path that *is* reachable today (`construct approvals approve <id>`), is worse: it guards execution with `if (parsed && KNOWN_PROVIDERS.includes(parsed.providerId))`. For `atlassian-jira`, that condition is false, so the `if` body — the only code that calls `executeApprovedWriteIntent` — never runs, and the CLI falls through to `println('Approved: ...')` with no error and no indication the write never executed. This is a silent no-op dressed as success, the same false-success failure class the rest of the truth-matrix audit repeatedly flags (rows 5, 6, 8).

## Context

The provider boundary itself — read-oriented data-source manifests vs. governed-write adapters as two separate stacks — is sound and not in question here; `target-architecture.md`'s "Provider boundary" section says so explicitly: "the fix needed is the namespace canonicalization (ADR-E), not a redesign." The same document's entity-mapping table assigns this fix to the Action Intent entity: "`lib/writes/write-intent.mjs` — real, typed, `KNOWN_PROVIDERS` needs the namespace fix (row 27)." This ADR is on the critical path for `construct-4uxq0.9.4` ("408a: governed adapters + provider-ID namespace fix"), which lands PR #408's Slack governed-write adapter and depends explicitly on this ADR for "namespace direction" before it can wire the new adapter into the same `KNOWN_PROVIDERS`/`DEFAULT_ADAPTER_FACTORIES` machinery.

I checked whether `lib/config/source-target-registry.mjs` already solves this — it does not; it is a different, narrower, and already-intentional mapping for a different subsystem. Its header comment states the descriptor key "is distinct from the manifest `id` for providers whose manifest id differs from their config-facing provider name (the Jira manifest id is `atlassian-jira`; its `sourceTarget.provider` is `jira`)." That mapping serves `construct.config.json`'s `sources.targets[].provider` field and `lib/embed/demand-fetch.mjs` — the **read-side** source-target config surface — and is populated from each manifest's own `sourceTarget.provider` block, not from `write-intent.mjs`'s `KNOWN_PROVIDERS`. It is a legitimate, documented alias for config ergonomics on one subsystem; it has no relationship to, and does not resolve, the write control-plane's separate `KNOWN_PROVIDERS` allowlist or `control-plane.mjs`'s `DEFAULT_ADAPTER_FACTORIES` keys. The two mappings happening to agree on the direction of the Jira alias (`atlassian-jira` → `jira`) is coincidental, not shared machinery — canonicalizing the write plane does not touch this file, and this file's existence should not be read as prior art that already covers the write-plane gap.

## Decision

The write control-plane adopts the manifest-ID namespace. Concretely:

1. `lib/writes/write-intent.mjs:15`'s `KNOWN_PROVIDERS` becomes `Object.freeze(['atlassian-jira', 'github', 'atlassian-confluence'])` (github's manifest ID is already `github` — `lib/extensions/manifests/github.manifest.json` — so it is unaffected).
2. `lib/writes/control-plane.mjs:50-54`'s `DEFAULT_ADAPTER_FACTORIES` keys change from `jira`/`confluence` to `atlassian-jira`/`atlassian-confluence` (`github` unchanged) so the map key matches the `providerId` parsed from an approved intent's tool name.
3. `lib/mcp/tools/provider-write.mjs:110`'s documented `args.provider` contract (`'jira' | 'confluence' | 'github'`) and its adapter-resolution path move to the same manifest IDs, so a direct MCP `provider_write` call and an embed-capability-proposal-derived write agree on one spelling.
4. The presets, `core-pack.mjs`'s `DEFAULT_EMBED_BINDINGS`, and the manifests themselves are already correct under this decision and require no change — they are the authoritative source this decision converges toward, not the side being fixed.

This is a decision of direction only; no code in this change lands the rename. `construct-4uxq0.9.4` is the bead that performs the rename, wires the new Slack adapter into the corrected namespace, and closes out the mismatch end-to-end.

## Rationale

I mapped the actual call sites (`grep -rn "KNOWN_PROVIDERS\|atlassian-jira" lib/ --include="*.mjs" | grep -v test`) rather than assuming the bead's stated preference was self-evidently right. The manifest-ID side is both larger and further downstream: extension manifests (`atlassian-jira.manifest.json`, `atlassian-confluence.manifest.json`), the read-side contract registry (`lib/providers/contract.mjs:64-65,124,126`, keyed `atlassian-jira`/`atlassian-confluence`), all three capability presets, and `core-pack.mjs`'s embed bindings already speak the manifest namespace — none of that would need to change under this decision. The short-ID side that does need to change is exactly two files for the core fix (`write-intent.mjs`'s `KNOWN_PROVIDERS` array, `control-plane.mjs`'s `DEFAULT_ADAPTER_FACTORIES` object), plus `provider-write.mjs`'s direct-call contract for full consistency — a small, load-bearing set, not a system-wide rename. `lib/cli/approvals.mjs` needs zero changes: it already imports `KNOWN_PROVIDERS` as a constant rather than hardcoding provider strings, so it self-corrects once the constant changes. Adopting the short-ID side instead (rejected alternative 2, below) would require editing every manifest, every preset, `core-pack.mjs`, and `lib/providers/contract.mjs` — a larger, higher-risk surface for the same outcome, for no offsetting benefit: the manifest ID is also the one exposed in `construct.config.json`-adjacent surfaces and CLI-facing embed-binding config, so it is the more user-visible spelling worth keeping stable.

## Rejected alternatives

- **Add a permanent alias/mapping layer translating `atlassian-jira` ↔ `jira` at the write control-plane boundary.** Rejected. This repo has a standing precedent against permanent back-compat shims for internal renames: ADR-0066 calls its config-layer clean break a decision made "per the refit's no-backwards-compat mandate," explicitly rejecting "a dual-read migration path... instead of a clean break" because "a dual-read path is exactly the kind of permanent complexity that mandate exists to prevent." ADR-0073 follows the same precedent for RichDocument adoption ("no back-compat shim... no dual-path fallback kept indefinitely"), and ADR-0045 makes the same call for intake zones ("no back-compat, no deprecation reads"). A permanent alias here would be the same category of complexity this codebase has repeatedly chosen not to carry, for a rename with a small, enumerated call-site count (see Rationale) that does not need a transition window.
- **Write control-plane keeps short IDs; manifests/presets/core-pack adopt them instead.** Rejected on blast radius: this direction touches every extension manifest, all three capability presets, `core-pack.mjs`'s embed bindings, and the read-side `lib/providers/contract.mjs` registry — strictly more files than the chosen direction — to arrive at the same unified namespace, with no compensating benefit.
- **Do nothing; leave both namespaces standing.** Rejected: the mismatch is already live and produces a false-success failure mode today (`lib/cli/approvals.mjs`'s silent `KNOWN_PROVIDERS.includes()` guard swallows a Jira-proposal approval with no error), and it blocks `construct-4uxq0.9.4`'s Slack-adapter integration from having a stable namespace to wire into.

## Consequences

- Positive: one provider-ID spelling across manifests, capability proposals, and the write control-plane; the silent-approval-with-no-execution failure in `lib/cli/approvals.mjs` becomes structurally impossible for Jira/Confluence once `KNOWN_PROVIDERS` matches the IDs those proposals already carry; `construct-4uxq0.9.4` has a settled namespace to add the Slack adapter into instead of choosing one under implementation pressure.
- Negative / cost: `lib/providers/contract/adapters/jira/*` and `.../confluence/*` directory and export names (`createGovernedJiraProvider`, etc.) keep their short names under this decision — only the `DEFAULT_ADAPTER_FACTORIES` map *key* changes, not the adapter module paths — which leaves a residual short/long inconsistency between directory naming and provider-ID naming that this decision does not resolve and that a future pass could clean up separately.
- Follow-up: this ADR performs no implementation. `construct-4uxq0.9.4` ("408a: governed adapters + provider-ID namespace fix") is the bead that renames `KNOWN_PROVIDERS`, `DEFAULT_ADAPTER_FACTORIES`'s keys, and `provider-write.mjs`'s provider contract, and lands the Slack governed-write adapter into the corrected namespace. That bead also lists this ADR as a direct dependency, along with the already-closed `construct-4uxq0.9.1`/`.9.2`/`.9.7` atomic-persistence and policy-exception fixes it shares a persistence layer with.
- Test files referencing `KNOWN_PROVIDERS` (at least one confirmed under `tests/`) will need their expected-provider-ID literals updated in the same change; this ADR does not enumerate them exhaustively — that is implementation-time work for `construct-4uxq0.9.4`.

## Reversibility

Medium: reverting means changing two-to-three files' string literals back (`write-intent.mjs`, `control-plane.mjs`, `provider-write.mjs`) plus any tests updated alongside them — no data migration, since `KNOWN_PROVIDERS` and `DEFAULT_ADAPTER_FACTORIES` are in-memory constants with no persisted representation of the old values. The one durable-state consideration is any already-enqueued approval-queue record whose `toolCall.tool` was stamped under the old namespace before this change lands (e.g. an `atlassian-jira.createIssue` tool name recorded pre-fix) — those records already carry the manifest-namespace spelling this decision moves *to*, per the Problem section's evidence, so no back-fill of existing queue records is required either direction.
