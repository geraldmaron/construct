# ADR-0085: Standing Assignment is the canonical continuous-work concept; embed capabilities, PR #408 directives, and PR #410 watch triggers converge into it

- **Date**: 2026-07-16
- **Status**: proposed
- **Deciders**: Gerald Dagher
- **Supersedes**: none
- **Resolves**: `construct-4uxq0.4.1` (ADR-A) — the continuous-work audit's naming/architecture gate. Directly unblocks `construct-4uxq0.10.2` (directive due-stamp-before-execution fix, P0-4), `construct-4uxq0.10.3`, the CLI/product-facing naming work the audit flags as ADR-A-gated, and PR #408c's re-authoring (`docs/notes/research/2026-07-continuous-work-audit/pr-reconciliation.md` §3). Does not resolve ADR-B (whether "embed" survives as a product-facing name) or ADR-D (delivery-semantics/lease ratification) — those remain open, separate gates.

## Problem

Construct has three unmerged or half-wired mechanisms that all claim the same job — "durable, recurring or triggered work an agent system executes and tracks to completion" — and none of them is canonical:

1. **Embed capability reasoning** (`lib/embed/capability-jobs.mjs`), live on `main`, registered by the daemon per enabled capability.
2. **PR #408's `directives[]`** (`lib/directives/directive-config.mjs`, `lib/directives/due-tracker.mjs`), unmerged on `origin/fix/ws-b-followups` (head `95dbe6875a4c4b8a96cc9d0a9212329ee62fb3ed`).
3. **PR #410's `sources.targets[].watch`** trigger block, staged on `origin/feat/cross-source-watch` (head `1c99ae38`) but not on the current branch's merged config surface.

The audit that produced this ADR was explicitly instructed not to let a fourth, parallel concept emerge alongside these three (`docs/notes/research/2026-07-continuous-work-audit/target-architecture.md`, "Framing" section) — a constraint this ADR treats as binding. Left undecided, `construct-4uxq0.10.2`/`.10.3`, the CLI naming work, and PR #408c's re-authoring all stay blocked, and PR #408 cannot be split into independently-gated slices per the reconciliation plan.

## Context

Independent verification of each mechanism, beyond what the audit reports, confirms the audit's characterization and shows the three are not just overlapping in *purpose* but incompatible in *lifecycle correctness*:

**Embed capability reasoning** (truth-matrix row 2, `opt-in-unproven`) — `lib/embed/capability-jobs.mjs:196 runCapabilityTick` is honest about its own limits: absent a `reasoningExecutor` injection it records `skipped-with-reason(reasoning-executor-not-available)` (line 215, constant `SKIP_REASON_NO_EXECUTOR` at line 53) rather than fabricating completion. Off by default, gated behind `CONSTRUCT_EMBED_REASONING_EXECUTOR=1` plus config, per the module's own header comment. This is a real, honestly-degrading mechanism — but it has never run its full reasoning path in production, and its scope is narrower than "any triggered unit of work" (it is specifically specialist-capability-shaped: bound provider slice → workflow plan → contract-checked output → write-intent enqueue).

**PR #408 `directives[]`** (truth-matrix rows 7–9, `scaffold`/`contradicted`) — `lib/directives/directive-config.mjs` defines a directive as a standing instruction (`provider`, `specialist`, `instruction`, `trigger`, `action`, `output`, `autoRun`) with an explicit module-header admission that it is "never executed by this module" and that even the daemon's consumer "only ever records that a directive is due... rather than running anything unattended." Independent verification of `lib/embed/daemon.mjs`'s directive-runner job on `origin/fix/ws-b-followups` confirms the audit's P0-4 finding exactly: at line 1150, `if (!isDirectiveDue(directive, state)) continue;` gates on due-ness, and at line 1152 — before any execution, before any specialist is invoked — `writeDirectiveState(this.#rootDir, directive.id, { lastRunAt: new Date().toISOString() })` stamps the directive as having run. The rest of the block (lines 1153–1169) only writes an observation and a stderr hint to run `construct directives run <id>`, a CLI subcommand that is not registered (only `list`/`status` are, per truth-matrix row 7). The due-tracker's own `isDirectiveDue` (`lib/directives/due-tracker.mjs`) then reads that same stamped state on the next tick and correctly concludes the directive is *not* due — because, as far as the state file is concerned, it just ran. A directive can therefore report "due," stamp itself "ran," and never actually execute, and no later tick will ever re-surface it. This is not a missing feature; it is a lifecycle model that manufactures false completion by construction, and it is the mechanism `lib/oracle/execute.mjs`'s directive-execution branch was found to silently depend on as its only real executor (truth-matrix row 8). Two additional confirmed defects compound this: the `writes`/`directives` config surface has a duplicated `"writes"` schema key (`schemas/project-config.schema.json` lines 146 and 157) and is absent from `FIELD_RULES` (`lib/config/schema.mjs`), so strict-mode config validation refuses the PR's own new surface (truth-matrix row 9, P0-5).

**PR #410 `watch`** (truth-matrix rows 10–11, `dead`/`contradicted`) — independently verified: `lib/config/source-targets.mjs:224-248`'s `normalizeConfigTarget` builds its output object from exactly `{ id, provider, selector, provenance }` — a `watch` key on the raw config target is never read or copied. A repo-wide check confirms no consumer anywhere reads `target.watch`. The schema accepts the field; the runtime silently discards it. Separately, the currently-merged `lib/sources/watch.mjs:156 refreshWatch` implements a *different*, real, already-shipped cadence concept (`git ls-remote` / directory-hash polling with `lastSeenHead`/`lastSeenHash` persisted via `resolveStatePath`) that has nothing to do with the `watch` config block PR #410 also stages — the same word denotes two unrelated things in the same PR. `refreshWatch` (lines 156–182) has its own confirmed defect independent of naming: it advances `lastSeenHead`/`lastSeenHash` at detection time (unconditionally, on every call) rather than after downstream processing completes, conflating "seen" with "processed" (truth-matrix row 13) — a defect a canonical Evidence Cursor contract needs to close regardless of which trigger concept wins this ADR.

**The three do not reconcile with each other.** `directives[].trigger.intervalMinutes` and `sources.targets[].watch.intervalMinutes` are two independent cadence models with no arbitration if both land (truth-matrix row 11); embed capability cadence (`embed.cadence.every`, ISO-8601 duration via `parseCadenceMs`) is a third. `docs/notes/research/2026-07-continuous-work-audit/pr-reconciliation.md`'s synthetic-merge check states plainly that merging all three as-is "would not be coherent."

### External prior art

External research was performed live via `WebSearch` (not solely reasoned from training-data knowledge); results below are cited with the pages actually returned.

Every comparable production system that offers durable, recurring/triggered work converges on the same three-part shape target-architecture.md independently proposes (Trigger Policy / Run / Outcome):

- **Temporal** — a **Schedule** ("contains instructions for starting a Workflow Execution at specific times") is explicitly distinct from a **Workflow** (the definition) and a **Workflow Execution** (the run/record). Temporal's own docs frame Schedules as the modern replacement for Temporal Cron Jobs specifically because they add "durability, observability, and lifecycle controls that traditional schedulers lack" — the same justification this ADR's Standing Assignment gives for superseding three ad hoc cadence mechanisms. ([Schedule | Temporal Platform Documentation](https://docs.temporal.io/schedule), [Temporal Schedules: More Reliable & Scalable than Cron Jobs](https://temporal.io/blog/temporal-schedules-reliable-scalable-and-more-flexible-than-cron-jobs))
- **Dagster** — **Schedules** and **Sensors** are both "instigators" (Dagster's own term) that trigger a **Job**'s **Run**; an **Asset**'s materialization is the outcome record. Trigger-policy and execution-record are cleanly separated concepts here too. ([schedules and sensors | Dagster Docs](https://docs.dagster.io/api/dagster/schedules-sensors))
- **Airflow** — a **DAG** carries a `schedule_interval`; each firing produces a **DAG Run**, "an object representing an instantiation of the DAG in time." Definition, trigger, and execution-instance are three distinct nouns.
- **GitHub Actions** — a **Workflow** declares `on:` triggers (push, schedule, `workflow_dispatch`); each firing produces a **Run** with its own status/conclusion.
- **AWS EventBridge Scheduler** — a **Schedule** (cron or rate-based) invokes a target with "at-least-once event delivery," configurable retries, and a dead-letter queue for undeliverable outcomes — trigger, delivery attempt, and terminal outcome are separately modeled exactly as Action Attempt/Outcome are in target-architecture.md.
- **Zapier** — a **Zap** (definition) fires on a **Trigger**; each firing is a **Run**, and each completed action within a run is counted as a **Task** — again trigger/run/outcome, under different names.

None of these systems name the *durable trigger+definition* entity "Assignment," and a direct search for "standing assignment" as software-architecture terminology returned no established usage — it is confirmed **not** prior art, it is a coinage for this codebase specifically ([search results](https://www.isaqb.org/wp-content/uploads/2020/10/iSAQB_Glossary_of_Software_Architecture_EN.pdf) among others returned no match). The closest real-world term is **"standing order"** (banking: "an automated instruction... to transfer a fixed amount at regular intervals... without requiring manual initiation each time" — [Standing order (banking) - Wikipedia](https://en.wikipedia.org/wiki/Standing_order_(banking))), which is semantically almost exact but was not selected as the name here (see Rejected alternatives) because it carries a specific financial-transaction connotation that risks misreading in a codebase that also does governed financial-adjacent writes (Jira, Slack, git). A codebase-wide grep for `Assignment` found only `model-router.mjs`'s unrelated `normalizeEnvAssignments`/`resolveTierAssignments` (env-var → model-tier mapping) — a real but low-risk term collision, distinguishable by context and not touching the same subsystem.

The three-part shape (trigger policy, run, outcome) recurring across every system surveyed validates target-architecture.md's Trigger Policy / Run / Outcome split independent of what the fourth, unifying entity is called. That entity's name is this ADR's actual decision.

## Decision

1. **Standing Assignment is adopted as the single canonical concept** for "a durable, recurring or triggered unit of scheduled work that Construct executes and tracks to completion," **superseding**:
   - Embed capability reasoning (`lib/embed/capability-jobs.mjs`) as a user/product-facing concept — its deterministic snapshot/plan/contract-check/enqueue machinery is retained and reused as the Standing Assignment execution path for specialist-bound work, per target-architecture.md's "formalize, don't rebuild" framing.
   - PR #408's `directives[]` (`lib/directives/`) — retired outright as a concept. `lib/directives/directive-config.mjs`'s shape (provider/specialist/instruction/trigger/action/output) is a reasonable *field* inventory to carry forward into the Standing Assignment schema, but the due-tracker's due-stamp-before-execution lifecycle (confirmed at `lib/embed/daemon.mjs:1150-1152` on `origin/fix/ws-b-followups`) is not carried forward under any name — this is disqualifying, not a naming preference (see Rationale).
   - PR #410's `sources.targets[].watch` trigger block (the *dead*, schema-only field verified absent from `normalizeConfigTarget`) — retired as staged. The already-shipped, unrelated `lib/sources/watch.mjs` polling mechanism is **not** retired by this decision; it becomes one of the Trigger Policy implementations a Standing Assignment can select (source-change trigger), once its detection-vs-processing cursor defect (truth-matrix row 13) is fixed under the Evidence Cursor contract (ADR-C's atomicity standard, not this ADR).
2. **The daemon's `setInterval` cadences remain internal scheduler mechanics**, not a competing concept — per target-architecture.md, the embed daemon is demoted to an internal scheduler host that ticks Standing Assignments due for evaluation; it does not retire.
3. **This is a naming/architecture ratification, not an implementation order.** It authorizes the Standing Assignment schema and lifecycle contract (Trigger Policy → Evidence Cursor → Run → Action Intent → Approval Decision → Action Attempt → Outcome → Assurance Finding, per target-architecture.md's control-flow section) as the target shape that `construct-4uxq0.10.2`, `.10.3`, and PR #408c's re-authoring build toward. It does not itself land code, migrate config, or rename CLI surfaces — those are separate, tracked beads gated on this decision plus, where applicable, ADR-B (embed naming) and ADR-D (lease/delivery semantics).

## Rationale

Three converging lines of evidence — not just deference to the audit's recommendation — support consolidation into one new concept rather than either alternative:

- **The three mechanisms are not merely redundant; one of them is actively unsafe as a foundation.** Directives' due-stamp-before-execution defect (`lib/embed/daemon.mjs:1152`) is a false-success bug in the exact dimension this whole audit was commissioned to find: a directive can be marked "ran" having never run, permanently starving the one real executor (`lib/oracle/execute.mjs`) of work it thinks is already done. Building the canonical model *on* directives (rejected option 3, "directives-only wins") would mean adopting that lifecycle defect as the standard rather than fixing it once. Building the canonical model as a genuinely new schema, informed by but not identical to directives' field shape, lets the fix be structural — Run creation and Outcome recording become separate, independently-persisted events (per the flow-engine checkpoint pattern in `lib/flows/checkpoint.mjs`, the one subsystem in the codebase target-architecture.md and truth-matrix row 31 independently confirm is genuinely atomic) rather than one field (`lastRunAt`) serving as both "I noticed this is due" and "I finished this."
- **Every external system surveyed treats the trigger-defining entity and its cadence as a first-class, singular concept — never three parallel ones.** Temporal Schedules, Dagster Schedules/Sensors, Airflow's DAG `schedule_interval`, GitHub Actions' `on:` triggers, and EventBridge Scheduler's Schedule all reify "what should run and when" once per system, with the trigger/run/outcome split happening *within* that one concept, not *across* competing concepts for the same job. Construct currently has three parallel answers to "what should run and when" (`directives[].trigger`, `sources.targets[].watch`, embed's `cadence.every`/daemon `setInterval`) with, per truth-matrix row 11, "no arbitration" between them if more than one lands. That is the anti-pattern every surveyed system avoids by construction, and it is also the audit's own explicit constraint (target-architecture.md's "Framing" section: converge, don't add a parallel concept).
- **Nine of the model's ten entities already exist and work; only the unifying trigger/scheduling concept is missing.** Source Target, Run, Evidence Cursor, Action Intent, Approval Decision, Action Attempt, Outcome, and Assurance Finding all map onto real, independently-audited Construct subsystems (target-architecture.md's mapping table). Adopting Standing Assignment is formalization plus one new concept, not a rewrite — consistent with the "don't build a second workflow engine" constraint and with reusing `lib/flows/engine.mjs`'s `createRun`/`advanceRun` rather than inventing new execution machinery.

On the name itself: "Standing Assignment" is not established prior art (confirmed by live search — no software-architecture glossary or comparable system uses it), but it is not a poor coinage either. It reads correctly to an engineer: "standing" signals durability/recurrence (echoing "standing order," a real and closely-related banking term for an automated recurring instruction, without inheriting that term's narrower financial-transaction connotation), and "assignment" signals a bounded unit of delegated, trackable work — appropriate for a system whose whole framing is specialists being assigned responsibility for sources. No collision was found against Temporal/Dagster/Airflow/GitHub Actions/Zapier/EventBridge terminology, and the one in-codebase near-collision (`model-router.mjs`'s tier "assignments") is a different subsystem, unlikely to cause confusion in practice. This ADR endorses the name as proposed rather than proposing a refinement — see Rejected alternatives for the "standing order" alternative that was seriously considered and set aside.

## Rejected alternatives

- **Option 2 — keep all three as distinct concepts (embed capabilities, directives, watch triggers).** Rejected. This is the status quo plus PR #408/#410 as staged, and it is the exact anti-pattern the audit was scoped to prevent (target-architecture.md's binding "Framing" constraint) and that external prior art (every system surveyed) avoids. Truth-matrix row 11 confirms the concrete failure mode: two independent cadence models (`directives[].trigger.intervalMinutes`, `watch.intervalMinutes`) with no arbitration if both ship, and row 17 shows the same pattern already exists today between `construct monitor` and doctor's source-watch — "two fully independent, uncoordinated mechanisms keyed off the same `sources.targets[]`," which the audit separately grades `contradicted`. Keeping three concepts formalizes and multiplies an already-confirmed defect class rather than closing it.
- **Option 3 — directives-only wins; capabilities and watch retire.** Rejected. Directives is the *worst* of the three foundations on the evidence, not a neutral pick among equals: it has a confirmed, disqualifying lifecycle defect (due-stamp before execution, `lib/embed/daemon.mjs:1150-1152`), a duplicate schema key that breaks its own strict-mode validation (`schemas/project-config.schema.json:146,157`), and it currently only executes via an accidental dependency on Oracle (truth-matrix row 8) — a coupling target-architecture.md explicitly says must not exist ("a Standing Assignment's action plane must run independent of whether Oracle happens to observe it"). Directives' *field shape* (provider/specialist/instruction/trigger/action/output) is genuinely reusable and is carried into the Standing Assignment schema per the Decision section, but the concept and its execution model are not.
- **"Standing order" instead of "Standing Assignment."** Seriously considered given it is real, established terminology with almost exactly the right meaning ("an automated instruction... at regular intervals... without requiring manual initiation each time"). Set aside, not because it is wrong, but because Construct's action plane performs literal financial/business-system writes (Jira issues, Slack posts, git operations) where "standing order" risks being misread as itself a financial-transaction primitive rather than the generic scheduling concept it would need to be. This is a judgment call, not a hard defect in the term — flagged here explicitly so a human reviewer can override it if they weigh the tradeoff differently.
- **Waiting for ADR-B (embed naming) to resolve first, then picking the unifying term.** Rejected as sequencing, not substance: ADR-B decides whether *"embed"* survives as the product-facing name for the daemon/scheduler-host layer, a different question from what the *assignment unit itself* is called. Per target-architecture.md's recommended target shape, "embed" surviving as the internal daemon name and "Standing Assignment" being the product-facing unit name are not in tension — they can be decided independently, and blocking this ADR on that one would stall `construct-4uxq0.10.2`/`.10.3` for no evidentiary reason.

## Consequences

**Positive:**
- Unblocks `construct-4uxq0.10.2` (fix the directive due-stamp-before-execution defect) and `construct-4uxq0.10.3` — both can now target the Standing Assignment lifecycle contract directly instead of patching a concept slated for retirement.
- Unblocks CLI/product-facing naming work: `construct directives ...`, `construct embed capabilities ...`, and any future `construct watch ...` surface converge toward a single `construct assignments ...` (or equivalent) surface once ADR-B additionally resolves the "embed" question.
- Unblocks PR #408c's re-authoring (per `pr-reconciliation.md` §3): the directives slice is re-built against the Standing Assignment model rather than patched in place, avoiding shipping the due-stamp defect under a new name.
- Gives `construct-4uxq0.10.1` (duplicate `"writes"` schema key) and the `FIELD_RULES` gap a single target schema to land against instead of a schema surface slated for replacement.
- Removes the "two parallel polling models" defect (truth-matrix row 11) by construction — a Standing Assignment has exactly one Trigger Policy field, not three competing cadence mechanisms.

**Negative / cost:**
- This is explicitly a naming and boundary decision, not a working implementation — `construct-4uxq0.10.2`/`.10.3`, the CLI rename, and 408c's re-authoring are real, currently-unscoped follow-up work this ADR creates a dependency on, not work it completes.
- Every existing reference to "embed capability" and "directive" as user-facing concepts (docs, CLI help text, config field names) needs an eventual rewrite pass once the Standing Assignment schema is implemented — deferred, not free.
- `lib/embed/capability-jobs.mjs`'s reasoning-executor gate, contract validation, and authority-guard check are reused, not replaced, so this decision does not by itself resolve embed capability reasoning's `opt-in-unproven` status (truth-matrix row 2) — that remains a separate proof-in-production question, orthogonal to naming.
- The `sources.targets[].watch` schema block from PR #410 stays deferred (per `pr-reconciliation.md` §2) rather than landing now — it returns as part of the unified Trigger Policy schema once Standing Assignment's shape is implemented, not before.
- Downstream ADRs this gates (per target-architecture.md's critical path) — ADR-C/D remain audit-decidable and unblocked already, but ADR-A landing is a prerequisite specifically for the 408-split's final slice (408c) and for any CLI/doc surface work that names the unified concept.

## Reversibility

**Medium-low, and status is "proposed" specifically because of that.** No code changes accompany this ADR — it is a naming and target-architecture ratification only, so today it costs nothing to reverse. But everything it is designed to unblock (`construct-4uxq0.10.2`/`.10.3`, CLI naming, PR #408c's re-authoring, eventual doc rewrites) is real implementation and documentation work that will accrue on top of the "Standing Assignment" name once those beads land. Reversing the name *after* that work ships means a second rename pass across schema, CLI surface, and docs — materially more expensive than reversing it now. This is exactly why this decision requires explicit human ratification before any of that downstream work begins, rather than proceeding on an audit recommendation alone: the audit can gather and weigh the evidence, but committing the org to CLI/doc rewrites and a directive-migration path is a product decision, not an engineering fact (target-architecture.md's own ADR ownership table marks ADR-A "User (audit drafts)" for exactly this reason).
