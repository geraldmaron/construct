# ADR-0087: AWS deployment topology for Standing Assignment execution — EventBridge Scheduler + SQS + Fargate workers (Option A), recommended pending user ratification

- **Date**: 2026-07-16
- **Status**: proposed
- **Deciders**: Gerald Dagher
- **Supersedes**: none
- **Resolves**: the AWS topology question `construct-4uxq0.4.12` (ADR-L) raised — which of three shapes executes recurring, per-tenant Standing Assignment work on AWS: (A) EventBridge Scheduler + SQS + ECS/Fargate workers + RDS, (B) a long-running ECS control-plane service with a Postgres-backed scheduler, or (C) EventBridge Scheduler launching ECS tasks directly with no queue. This is a from-scratch infrastructure-topology decision, not a repair of existing infrastructure.

## Problem

Construct's target architecture (`docs/notes/research/2026-07-continuous-work-audit/target-architecture.md`) converges embed capabilities, PR #408's directives, and PR #410's watch-triggers into one **Standing Assignment** concept: a durable, per-tenant recurring job that ticks on a trigger policy, checks an evidence cursor, and — only on meaningful change — runs bounded specialist work and drains approved Action Intents through the governed-write action plane. That control flow needs to run identically locally and on AWS (`target-architecture.md` §"Local vs AWS": "only the backend for run-store, intake-queue, and action-plane storage changes"). Nothing in the repo today decides *which* AWS primitives back that execution for a multi-tenant, bursty, sparse-tick workload, and the two epics that would consume this decision (`construct-2ec1y`, `construct-dqgdc`) are explicitly held empty pending it. This ADR makes a recommendation and flags it for human ratification because the downstream cost (idle compute spend) and reversibility (IaC, once built, is expensive to unwind) are real commitments this audit should not make unilaterally.

Team mode already assumes a Postgres-backed queue (`lib/queue/pg-queue.mjs`, confirmed real with row-locking and lease columns, truth-matrix row 35) and a Docker-based worker pool. This ADR's job is to pick the concrete AWS primitives that satisfy those abstract kinds for the Standing Assignment execution path specifically — it does not need to (and should not) change `deployment-mode.mjs`'s resource-kind vocabulary.

**Dependency on ADR-D (undrafted).** `construct-4uxq0.4.4` (ADR-D: delivery semantics — at-least-once + leases + idempotency for external writes) is still open (`OPEN`, owner "Audit drafts, User ratifies"). Its own evidence cites `lib/writes/control-plane.mjs:122` (in-memory-only executed-set, no durable lease) and the worker's confirmed duplicate-execution window (truth-matrix row 33). Whichever AWS topology this ADR recommends will carry its own message-delivery and retry semantics; those semantics need to compose with whatever ADR-D eventually formalizes for the action plane generally, not invent a second, incompatible retry model. This dependency is real and is flagged here rather than resolved — ADR-D remains a separate, still-open decision.

## Decision

**Recommend Option A — EventBridge Scheduler + SQS + ECS/Fargate workers + RDS — as the AWS deployment topology for Standing Assignment execution, proposed pending user ratification.**

EventBridge Scheduler triggers each tenant's Standing Assignment on its trigger policy (interval/cron), publishing onto an SQS queue rather than invoking a worker directly. ECS/Fargate workers, scaled by queue depth, claim messages and run the Standing Assignment control flow (`target-architecture.md`'s 8-step flow: evidence cursor check → run → action intents → approval → action plane drain → Oracle assurance). RDS Postgres backs durable Run/Action-Intent/Outcome state, matching the `queue: postgres` / `workers: docker→ecs` shape `lib/deployment-mode.mjs` already names abstractly for team/enterprise mode.

This is a recommendation, not a final decision. Per the bead's own framing ("Owner: User" — a from-scratch infra spend/commitment decision) and because **reversibility is low once the IaC exists** (see Reversibility below), this ADR requires explicit human sign-off before any Dockerfile, terraform EventBridge/SQS resource, or worker image is built. Nothing in this ADR authorizes implementation.

## Rationale

Reasoning below is grounded in live search performed for this ADR (2026-07-16) unless marked otherwise; see References for sources.

**Workload shape.** Standing Assignments are bursty and mostly no-op: `target-architecture.md`'s control flow stops at step 2 ("Evidence Cursor probed; if no meaningful change... stop here — no reasoning tokens spent") for the common case. Across many tenants on similar cadences (e.g., many teams on hourly triggers aligned to the hour), tick volume can spike briefly and then go idle. This is exactly the shape AWS's current guidance (per live search) steers toward event-driven, pay-per-invocation compute rather than an always-on service: "start simple with EventBridge + Lambda, add Step Functions when you need multi-step orchestration, and reach for ECS when you hit Lambda's time limits" — Standing Assignment work (bounded specialist/flow execution) plausibly exceeds Lambda's duration ceiling, which is why ECS/Fargate workers rather than Lambda functions are the right compute layer here, but the *triggering* half of that guidance (event-driven over always-on) still applies.

**Why not Option B (long-running ECS control-plane + Postgres-backed scheduler).** An always-on ECS service pays for compute 24/7 regardless of how many ticks are actual no-ops — the opposite of the sparse-tick profile above. It also duplicates a managed primitive: EventBridge Scheduler already provides recurring schedules, flexible time windows, per-invocation idempotency via client tokens, and native retry-policy + dead-letter-queue support (confirmed via live search of AWS's own EventBridge Scheduler `create-schedule` reference and ECS scheduling docs). A hand-rolled Postgres-backed scheduler reimplements a weaker version of what AWS ships as a managed service, and — per the "start simple, escalate only when needed" guidance found in search — reaching for an always-on control-plane before hitting a concrete limitation of the managed scheduler is the wrong default. This is also the option `construct-2ec1y`'s current description already assumes; the audit's own note on that epic treats that as unexamined inertia, not a validated choice, and this ADR agrees.

**Why not Option C (EventBridge Scheduler directly launches ECS tasks, no queue).** Simplest option, zero idle cost, fewest moving parts — genuinely attractive for a single-tenant or low-concurrency workload. EventBridge Scheduler's templated ECS RunTask target does carry its own idempotency (client token) and retry/DLQ support (confirmed via live search of the AWS CLI `create-schedule` reference and the EventBridge→ECS Serverless Land pattern), which covers *invocation* failures. But it provides no buffering for concurrent burst: per live-search guidance on multi-tenant SaaS queue design, "background job patterns... move to namespaced storage" and "most modern SaaS applications use a bridge model" mixing shared and per-tenant queues specifically to smooth bursty, multi-tenant load and apply per-tenant fairness/rate-limiting. Direct-launch has no queue at which to apply that fairness or absorb a burst of simultaneous tenant schedules against ECS task-launch throughput — it optimizes for the common sparse case at the cost of the burst case this workload is explicitly expected to have (multi-tenant, "bursty" per this ADR's own charge).

**Why Option A.** SQS is the missing piece between Scheduler's per-invocation idempotency and a durable, fair, bursty-load-absorbing multi-tenant queue. It composes with the sparse-tick, bursty-fanout profile (buffers concurrent tenant triggers, decouples trigger cadence from worker throughput, standard per-tenant sharding/fairness surface per the SaaS queue-design guidance above) while keeping the pay-per-invocation cost profile of A/C rather than B's constant control-plane spend. It also happens to map cleanly onto ADR-D: SQS's visibility-timeout-based at-least-once delivery and message-level dedup are structurally the same shape as the "at-least-once + leases + idempotency keys" model ADR-D (`construct-4uxq0.4.4`, still undrafted) is expected to formalize for the action plane generally — this ADR does not resolve ADR-D, but flags that whoever drafts it should treat SQS's semantics as a candidate concrete backing for the lease model rather than inventing an incompatible one.

**Comparable systems (context, not determinative).** Two systems were checked as reference points for "durable trigger + polling/queue-backed worker pool" as a pattern generally, not as AWS-specific validation: Temporal Cloud's worker architecture long-polls a managed task queue and scales workers independently of trigger cadence (per live search of Temporal's own worker-performance docs); GitHub Actions' runner dispatch model has a Listener process that registers, polls for work, and hands jobs to a Worker (per live search of Depot's GitHub Actions runner architecture writeup). Both validate "durable queue + worker pool, decoupled from the trigger" as a sound general shape. Neither is a precise analogy — both operate their own control plane, whereas Option A consumes AWS's managed EventBridge Scheduler and SQS rather than building one — which if anything strengthens the case against Option B (don't hand-roll a control-plane AWS already offers as a managed primitive).

**Cost.** Option B pays for ECS control-plane compute continuously, plus RDS, regardless of tick volume. Options A and C pay per Scheduler invocation (near-zero), per SQS message for A (near-zero), and per Fargate task-second only while a Standing Assignment is actually executing. No dollar-figure cost model was built for this ADR — the relative ordering (B > A > C in idle-cost terms) is qualitative reasoning from the pricing shape of each service, not a scored estimate. **`[unverified]`** — no concrete cost projection exists; a real comparison would need expected tenant count, tick frequency, and average run duration, none of which this ADR had available.

**Operational complexity and latency.** Component count: C < A < B. Option A's extra SQS hop is a standard, well-documented managed pattern (Serverless Land ships a reference "EventBridge Schedule → SQS → ECS" pattern per live search), not custom infrastructure. Cold-start latency (Fargate task launch, on the order of seconds) is common to A, B, and C's worker-launch path and is not latency-sensitive for background Standing Assignment execution (unlike a user-facing request path) — this factor does not meaningfully discriminate between the three options for this workload.

## Rejected alternatives

- **Option B — long-running ECS control-plane + Postgres-backed scheduler.** Rejected as the recommendation (not ruled out permanently): pays for idle compute against a workload that is mostly no-op ticks; duplicates EventBridge Scheduler's managed recurrence/idempotency/retry primitives in application code; is the option `construct-2ec1y`'s current description already assumes by inertia rather than by evaluation, which this ADR treats as a flag against it, not a point in its favor.
- **Option C — EventBridge Scheduler directly launches ECS tasks, no queue.** Rejected as the recommendation: simplest and cheapest, but provides no buffering or per-tenant fairness surface for a workload explicitly expected to be bursty and multi-tenant; a burst of simultaneously-due tenant schedules has no queue to absorb it before hitting ECS task-launch throughput.

## Consequences

- **Positive:** Once ratified, unblocks `construct-4uxq0.14.3` (which depends on this ADR alongside ADR-J and ADR-K) and "all Phase 12 AWS beads (P2 priority)" per the bead's own downstream-blocked list. Resolves whether `construct-2ec1y` can be populated with children — its current description, which hardcodes Option B's `desired_count=1` always-on-service language, needs to be **superseded/rewritten, not merely appended to**, if this ADR's Option A recommendation is ratified (per the epic's own audit note). Also unblocks `construct-dqgdc`, which is deferred behind both this ADR and `construct-2ec1y`'s post-ratification rescoping.
- **Negative / cost:** Adds three AWS primitives to build and operate for Standing Assignment execution (EventBridge Scheduler, SQS, plus the ECS/Fargate workers and RDS both B and C would also need) versus Option C's two. None of the required IaC exists today for *any* of the three options — no EventBridge/Scheduler/SQS resource exists anywhere in `deploy/terraform/` currently, confirmed by direct grep. This is unavoidable regardless of which option is chosen; it is not unique cost attributable to Option A. The existing `deploy/terraform/modules/ecs/` skeleton (ALB + single-service health check) is scoped to `construct serve` (WS-C's dashboard/API surface) and is a materially different shape from event-driven Fargate workers — ratifying this ADR does not decide whether `construct serve` itself should also become always-on; that remains `construct-2ec1y`'s own scope once unblocked.
- **Follow-up:** This ADR does not authorize implementation. The IaC (EventBridge Scheduler resource, SQS queue + DLQ/redrive policy, worker task definition, RDS wiring) is genuinely from-scratch work gated on ratification. ADR-D (`construct-4uxq0.4.4`, still undrafted) should account for Option A's SQS-based delivery semantics when it formalizes the action plane's at-least-once + lease + idempotency-key model, rather than defining an incompatible one independently.

## Reversibility

**Low, once the IaC is built** — this is exactly why status here is `proposed` and the decision owner is the user, not the audit. Terraform state, deployed EventBridge schedules, SQS queues with in-flight or dead-lettered messages, and RDS data all become real, stateful commitments the moment `apply` runs; unwinding a wrong topology choice after tenants are relying on it is materially more expensive than the decision itself. No implementation should start against this ADR until a human explicitly ratifies the recommendation in this document (or overrides it with Option B or C).
