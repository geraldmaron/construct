# ADR-0088: Actuation default posture — conservative double opt-in for reasoning, approval as the default action policy

- **Date**: 2026-07-16
- **Status**: accepted
- **Deciders**: Gerald Dagher
- **Supersedes**: none
- **Resolves**: `construct-4uxq0.4.13` (ADR-M: actuation default posture) — ratifies or revises the current default posture where the embed reasoning executor is off by default and `approval` (not `autonomous`) is the default action policy for anything beyond read/summarize/draft

## Problem

Construct's embed capabilities can, in principle, reason autonomously about evidence and propose external writes on a schedule with no human in the loop. Today that capability is gated behind two independent defaults that have never been formally ratified: the reasoning executor itself is off unless explicitly opted in, and even when reasoning runs, most action types default to requiring human approval rather than executing autonomously. `construct-4uxq0.4.13` asks whether to keep that conservative posture or revise it now that this session has landed two of the P0 write-plane fixes the original audit used to justify staying conservative.

## Context

**The double opt-in, verified against `lib/embed/reasoning-executor.mjs`.** `createReasoningExecutor` (line 186) returns `null` — meaning `lib/embed/capability-jobs.mjs`'s `runCapabilityTick` keeps recording the honest `skipped-with-reason(reasoning-executor-not-available)` tick — unless `reasoningExecutorEnabled()` (line 64) returns true. That function is a single enablement gate with two possible sources, not an AND of two flags: the env var `CONSTRUCT_EMBED_REASONING_EXECUTOR` (`1`/`true` enables, `0`/`false` disables) wins if set; otherwise it falls back to `daemon.embedReasoning.enabled: true` in `construct.config.json`. Either source alone flips the gate. But enablement is not sufficient to actually reason: even after `reasoningExecutorEnabled()` is true, the returned function (line 189) still requires a resolved provider API key (`opts.apiKey`, defaulting to `env.ANTHROPIC_API_KEY`) — no key means an honest `SKIP_REASON_NO_PROVIDER_KEY` skip, never a silent no-op-as-success. A third gate, `checkUnattendedSpend` (line 192), caps real spend per tick even once both the enablement flag and the key are present. So "double opt-in" in the truth matrix and the bead is best read as: (1) an explicit enablement flag (env var or config field, either satisfies it) plus (2) a real provider key — with a budget ceiling as a standing third check on every call, not a one-time gate.

**The approval-default policy, verified against `lib/embed/authority-guard.mjs` and `lib/embed/config.mjs`.** `DEFAULT_OPERATING_PROFILE.authority` (`config.mjs:118-127`) sets `read`, `summarize`, and `draftArtifacts` to `autonomous`, but `createIssues`, `updateIssues`, `publishDocs`, `externalPost`, and `repoWrites` — everything with an external or repo-visible effect — to `approval-queued`. `AuthorityGuard.check()` (`authority-guard.mjs:152`) enforces this with two independent fail-safes, not just the profile default: an authority key absent from the profile falls back to `'approval-queued'` ("fail-safe default", line 152), and if no `ApprovalQueue` is configured at all, the guard denies outright rather than defaulting open ("No approval queue present — default to deny for safety", lines 186-191). This confirms the bead's claim: `approval`, not `autonomous`, is the current real default for consequential actions, encoded in two places (the profile's own field defaults and the guard's fail-safe), not merely asserted in a document.

**What this session actually fixed, and what it didn't.** The truth matrix and FINAL-REPORT's P0 gap register (§5) named six P0 defects; three sit under E1 (write-plane integrity, `construct-4uxq0.9`): sent-log silent-swallow + non-atomic rewrite (`.9.1`), approval-queue non-atomic persistence + cross-process dedup gap (`.9.2`), and execution leases — none exist anywhere in the repo (`.9.3`). A read-only `bd show construct-4uxq0.9` at the time of drafting this ADR shows E1 at 4/8 children complete: `.9.1` and `.9.2` are closed (✓), along with two P1 silent-catch fixes from the same sweep (`.9.7` envelope.mjs policy-exception swallow, `.9.8` broker.mjs audit-record swallow). `.9.3` — execution leases — is still open (○), still blocked on ADR-D per the epic description, and still literally zero matches on `grep acquireLease\|withLease\|executionLease` across the repo as of the original audit; nothing in this session touched that grep result. `bd show construct-4uxq0.11` (E3: run lifecycle + evidence cursors) shows 0/5 children complete — all five (evidence-cursor advance-after-processing, worker lease/heartbeat wiring, intake-queue backend parity, meaningful-change gate generalization, at-least-once tick semantics) remain open. None of E3's children carry P0 severity in the audit's own gap register (worker lease/heartbeat wiring, the closest candidate, is tagged P2 as `.11.2`); the register's P0 list is concentrated entirely in E1.

## Decision

**Ratify the current conservative posture as-is: reasoning stays off unless explicitly double-opted-in, and `approval` (not `autonomous`) stays the default action policy for every action beyond read/summarize/draftArtifacts.** No code change follows from this ADR — it formalizes the default that is already shipping today as the intended one, and sets the specific unblocking condition for revisiting it (below), rather than leaving the trigger as a vague "once E1/E3 land."

## Rationale

The two P0 fixes that landed this session (`.9.1` sent-log atomicity, `.9.2` approval-queue atomicity) close exactly one class of risk: bookkeeping about writes and approvals can no longer silently corrupt itself through a non-atomic full-file rewrite or a swallowed persistence error. That is real progress and it was the audit's most acute finding. But it does not touch the P0 that most directly bears on expanding autonomy: `.9.3`, execution leases. Atomic bookkeeping tells you truthfully what happened; a lease is what stops two processes from *doing the same thing at the same time* in the first place. With reasoning off by default today, that gap is latent — low tick volume, mostly single-process. Flipping the default to autonomous-by-default (or reasoning-on-by-default) is precisely the change that would turn tick volume up and make concurrent/restarted daemon runs race to execute the same approved write a live, common scenario rather than an edge case. Recommending a default-posture change that increases exposure to a P0 the audit itself is still tracking as open — and that this session did not touch — would be reasoning about the fix that landed while ignoring the fix that didn't. E3's 0/5 completion (evidence-cursor semantics, worker lease/heartbeat wiring) reinforces this: nothing in the run-lifecycle layer that autonomous, higher-frequency ticks would stress has moved since the audit.

So the calculus has partially but not fully changed. The atomicity fixes reduce the *bookkeeping* risk the audit flagged; they do not reduce the *concurrent-execution* risk, which is the risk category most directly amplified by widening the default action policy. Given that, conservative defaults remain the right call — not because nothing changed this session, but because the specific gap that gates this decision is still open.

## Rejected alternatives

- **Option 2 (bead's alternative): enable reasoning by default once E1/E3 P0s are fixed.** Rejected for now, not permanently. As of this check, E1 is 4/8 complete with its remaining P0 (`.9.3`, execution leases) still open and blocked on ADR-D; E3 is 0/5 complete. Neither epic is "fixed" in the sense the bead's Option 2 requires. This ADR does not rule out Option 2 later — it names the specific unblocking condition (below) so a future re-evaluation has a concrete trigger instead of re-litigating the whole audit.
- **Partial relaxation: keep reasoning opt-in but move some action types (e.g. `createIssues`) to autonomous now.** Rejected: the execution-lease gap applies to any write path the approval queue or write-intent drain touches, not only to reasoning-originated proposals; loosening the action-policy default independently of the reasoning gate does not avoid the concurrency risk this ADR is conservative about.
- **Revert the two atomicity fixes' influence on this decision entirely and treat this as unchanged from the audit's original snapshot.** Rejected: the bead explicitly asks whether this session's fixes change the calculus, and ignoring them would itself be a form of not tracing the claim to current evidence. The honest answer is "partially, but not enough to flip the recommendation" — recorded above rather than asserted without the `.9.1`/`.9.2`/`.9.3` breakdown.

## Consequences

- Positive: zero behavior change — this ADR ratifies what is already shipping, so there is no migration or rollout risk from this decision alone. It gives `construct-4uxq0.10.8` (fate of the unwired deterministic presets) a concrete answer to build on: deterministic reasoning is not part of an expanded default posture right now, so that bead's "is deterministic reasoning part of the default posture" question resolves to no, pending re-evaluation.
- Positive: names an explicit, checkable unblocking condition — `.9.3` (execution leases) landing — rather than the audit's original vague "E1/E3 P0s" framing, which this session's partial progress on E1 has already made ambiguous (4/8 done, but the one P0 that matters for this decision is not among them).
- Negative / cost: E1 (`construct-4uxq0.9`) work — specifically `.9.3` — becomes explicitly gating for any future autonomy expansion, not just generally important; this raises its effective priority relative to other E1 children (`.9.4`–`.9.6`) that do not block this decision. E2 (`construct-4uxq0.10`, canonical-model epic) inherits the same sequencing pressure the bead already flagged: this ADR's "still conservative" answer means E2's rollout planning should not assume wider autonomy is imminent.
- Named downstream: `construct-4uxq0.10.8` (unwired preset fate) was blocked on this ADR and can now proceed using the "not part of the default posture yet" answer above. E1 and E2 sequencing: this ADR does not accelerate E1 as a whole, but it does mean `.9.3` specifically should be treated as the re-evaluation trigger for ADR-M, and E2's canonical-model rollout planning should treat wider default autonomy as not-yet-available rather than pending on an aggregate epic-completion percentage.

## Reversibility

The bead characterizes this as "high (a config default, not a structural decision)." That is correct for the mechanical act of changing the default — flipping `reasoningExecutorEnabled()`'s fallback or `DEFAULT_OPERATING_PROFILE.authority`'s values is a small, code-reviewable diff, exactly like ADR-0080's zero-behavior-change reversibility framing. It is not the whole picture, though. If a future ADR revises this posture to autonomous-by-default and users run under that default for any period, the *config toggle* is trivially revertible but the *actions already taken under it* — issues created, docs published, external posts sent while autonomous — are not undone by reverting the default, the same asymmetry the truth matrix's own approval-queue and sent-log findings are about (durable side effects vs. the flag that permitted them). So: **high reversibility for the code-level decision, not high reversibility for any autonomous actuation that already occurred under a more permissive default** — worth stating explicitly rather than inheriting the "config default = fully reversible" framing unqualified, since this default gates real-world side effects in a way a typical config toggle (e.g. a log-level default) does not.
