# ADR-0089: At-least-once delivery with durable execution leases + idempotency keys for external writes and worker jobs

- **Date**: 2026-07-16
- **Status**: accepted
- **Deciders**: Gerald Dagher
- **Supersedes**: none
- **Resolves (decision only)**: `construct-4uxq0.4.4` (ADR-D) — the delivery-semantics question the continuous-work audit's WP4 flagged as "audit-decidable now and unblocks all P0 beads." This ADR decides the *model* (at-least-once + durable lease + idempotency key); it does not implement the lease primitive itself. Per the bead: Audit drafts, User ratifies.

## Problem

Construct has two independent execution loops that mutate external systems or long-running local state, and neither has a durable concurrency guard:

1. **Governed write drain** (`lib/writes/control-plane.mjs:122 drainApprovedWriteIntents`) — walks an `ApprovalQueue`'s `'approved'` records and calls `writeWithEnvelope()` once per record, deduplicating via an `opts.executedApprovalIds ?? new Set()` created at `lib/writes/control-plane.mjs:123`. That `Set` lives only in the calling process's memory for the lifetime of one `drainApprovedWriteIntents()` call — it is never persisted, so nothing prevents two concurrent drain calls (two CLI invocations, a CLI call racing a future daemon-triggered drain) from both observing the same `'approved'` record and both calling `writeWithEnvelope()` for it.
2. **Team-mode worker loop** (`lib/worker/entrypoint.mjs:166 runWorkerLoop`) — claims a job from `PostgresIntakeQueue` (`lib/queue/pg-queue.mjs`) via `queue.claim({ claimedBy: workerName })` at `lib/worker/entrypoint.mjs:190`, with no `leaseSeconds` override, so the claim uses the queue's default lease (`PG_QUEUE_DEFAULT_LEASE_SECONDS = 120`, `lib/queue/pg-queue.mjs:13`, wired through the constructor default at `lib/queue/pg-queue.mjs:51`). `PostgresIntakeQueue` implements `heartbeat()` (`lib/queue/pg-queue.mjs:192`) to renew that lease and `fail()` (`lib/queue/pg-queue.mjs:218`) to release it on error — but `runWorkerLoop` and `processClaim` (`lib/worker/entrypoint.mjs:94-160`) never call either. The only production callers of `heartbeat`/`fail` are test files (`tests/worker-runtime.test.mjs`, `tests/pg-queue-reliability.test.mjs`, `tests/intake-queue-factory.test.mjs`, `tests/functional/pg-queue.functional.test.mjs`) — none of them is `lib/worker/entrypoint.mjs` itself. Meanwhile the default per-job execution budget (`jobFromPacket`'s `timeoutSeconds: packet?.timeoutSeconds || DEFAULT_TIMEOUT_SECONDS`, `lib/worker/entrypoint.mjs:82`, and independently `DEFAULT_TIMEOUT_SECONDS = 300` enforced inside `runJob` at `lib/worker/run.mjs:33`) defaults to 300 seconds — 2.5x the 120-second lease. A job that runs close to its own timeout has its lease expire mid-execution while the worker is still holding and working the job; `PostgresIntakeQueue.claim()`'s reclaim predicate (`OR (status = 'claimed' AND lease_expires_at <= now() AND attempt < max_attempts)`, `lib/queue/pg-queue.mjs:143`) then lets a second worker legitimately re-claim and re-execute the same job.
3. Additionally, `FilesystemIntakeQueue` (`lib/intake/filesystem-queue.mjs:54`) — the solo-mode intake backend — exposes only `enqueue`, `listPending`, `count`, `read`, `markProcessed`, `markSkipped`, `reopen`; it has no `claim`, `heartbeat`, or `fail` method at all. Nothing in this ADR changes that backend's shape; it is out of scope because solo mode has no concurrent workers to guard against.

No lease primitive exists anywhere in the write path today: `grep -rn "acquireLease\|withLease\|executionLease" lib/writes/ bin/` (run as part of this ADR's research) returns zero matches outside this file's own doc comments. The truth matrix's own summary is blunt about it: row 22, "Execution leases for external writes" — `grep acquireLease/withLease/executionLease → zero matches anywhere`, status `dead`. Row 33, the worker loop, is stronger: status `contradicted`, "**Confirmed real duplicate-execution window**: a job running close to its own timeout can have its lease expire and be re-claimed by a second worker while still executing." Row 35 shows the Postgres queue's lease/heartbeat/dead-letter machinery is itself correctly implemented in isolation but "unreachable from the actual worker loop" — status `implemented-but-disconnected`. The gap is not "no idea how to build this" — the primitive already exists in one subsystem and is simply not called by the other two.

Without a decision here, `construct-4uxq0.9.3` (P0: execution leases for external writes) has no target model to implement against, `construct-4uxq0.4.14` (ADR-N: approval/drain lifecycle) is explicitly hard-gated on this ADR landing first ("wiring the drain without leases would manufacture the exact duplicate-external-mutation P0 this audit flags"), and `construct-4uxq0.9.5` (408b: write-intent-drain wiring, post-lease) cannot start.

## Context

This is a design-time gap, not a runtime failure Oracle could have caught: `oracle-miss-report.md`'s per-row analysis of row 22 classifies it as "no evidence producer (feature absent, not failing)" — "Absence of a feature isn't something a runtime-evidence collector detects — nothing to observe." The report's remedy is exactly this ADR plus a follow-on invariant once leases exist (`external-write-has-idempotency-and-reconciliation`, seed #9 in its recommended invariant registry). Row 33's remedy is a contract test ("worker loop exercises every queue method its contract requires") layered on top of whatever model this ADR picks; that test is out of scope for this ADR and belongs to the implementing bead.

Two facts push the design toward at-least-once rather than trying to suppress duplicates before they happen:

- The **downstream systems Construct writes to are already at-least-once**: Jira, Confluence, GitHub, and Slack APIs offer no exactly-once write guarantee, and the queue backing team-mode work (`lib/queue/pg-queue.mjs`) is a `SELECT ... FOR UPDATE SKIP LOCKED` claim queue — the same primitive class used by widely deployed job queues (Postgres-backed queue implementations built on `FOR UPDATE SKIP LOCKED` document exactly this "lease_expire column ... if a job remains in 'processing' after the lease period has expired, it can then be picked up by another process" pattern — [Building real-time, thread-safe, resilient Queue with Postgres](https://naveennegi.medium.com/postgres-as-queue-deep-dive-into-fairly-advanced-implementation-68f28041853e)). A claim-with-expiry queue is structurally at-least-once by construction: the whole point of expiry-driven reclaim is that a second worker *may* legitimately pick up a job the first worker hasn't released. Fighting that with an at-most-once design means either removing reclaim (accepting permanent job loss on worker crash) or adding distributed coordination Construct has no infrastructure for.
- **This repo already has the durable idempotency half of the pattern**, just not connected to a durable lease. `writeWithEnvelope()` (referenced from `lib/writes/control-plane.mjs:90-98`) takes an `idempotencyKey: record.toolCall?.argsHash` and dedups through `WriteSentLog` (`lib/writes/sent-log.mjs`). The missing piece is specifically the *execution* guard — preventing two processes from both being mid-flight on the same record — not the idempotency key itself.

## Decision

1. **Adopt at-least-once delivery as the concurrency model for both execution loops** (governed-write drain and team-mode worker). A record or job may be executed more than once under crash, restart, or lease-expiry-during-execution; correctness is restored by idempotency, not by preventing re-delivery.
2. **Require a durable execution lease, not an in-memory one, guarding every execution attempt.** For `drainApprovedWriteIntents`, this means replacing (or wrapping) the in-memory `executedApprovalIds` Set (`lib/writes/control-plane.mjs:123`) with a lease recorded in durable storage — reusing the `ApprovalQueue`'s own persisted state (it already models `'awaiting_approval'` / `'approved'` / `'denied'` / `'expired'`, per the module header at `lib/writes/control-plane.mjs:14-26`) is the natural extension, adding an `'executing'`-with-lease-expiry state rather than inventing a second store. For the team-mode worker, this means wiring the *already-implemented* `heartbeat()` (`lib/queue/pg-queue.mjs:192`) into the job-execution path in `lib/worker/entrypoint.mjs` (called periodically while `runJob` is in flight, extending `lease_expires_at`) and `fail()` (`lib/queue/pg-queue.mjs:218`) on any terminal error, so a job's lease only expires when the worker legitimately can no longer renew it (crashed, killed, network-partitioned from Postgres) — not simply because it ran longer than a static default.
3. **Keep idempotency keys as the second, independent line of defense**, exactly as `writeWithEnvelope()` + `WriteSentLog` already do for governed writes. A lease prevents *concurrent* double-execution; an idempotency key protects against *sequential* re-delivery after a lease legitimately expires and a second attempt runs. Both are required; neither substitutes for the other — this mirrors the SQS guidance that heartbeat-extended visibility timeouts and idempotent consumer logic are complementary, not either/or ("Extend the visibility timeout programmatically for tasks that fail to complete... Make processing idempotent: Assume messages will be delivered more than once" — [Amazon SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), [How to Handle SQS Message Visibility Timeout](https://oneuptime.com/blog/post/2026-01-27-sqs-message-visibility-timeout/view)).
4. **Fix the lease/timeout ordering defect as part of implementation, not as a separate decision.** The 120s-lease / 300s-timeout inversion in `lib/worker/entrypoint.mjs` (confirmed above) is a direct consequence of the missing heartbeat call, not an independent bug — once `heartbeat()` is wired to renew the lease periodically during `runJob`, the static default ordering stops mattering for jobs that are actively heartbeating. The implementing bead (`construct-4uxq0.9.3`) should still audit whether the *initial* lease window (before the first heartbeat fires) is long enough to survive normal scheduling jitter, but that is a tuning detail within this model, not a reason to pick a different model.
5. **Scope**: this decision governs the two Postgres/queue-backed execution loops named above (governed-write drain, team-mode worker). It does not extend to `FilesystemIntakeQueue` (solo mode, single-process, no concurrent claimants to guard against) and does not mandate a specific lease-column schema for the `ApprovalQueue` extension — that schema is implementation work for `construct-4uxq0.9.3`.

## Rationale

**Comparable systems converge on the same shape** for exactly this problem — a consumer doing bounded-but-variable-length work against an at-least-once source:

- **AWS SQS** solves it with a visibility timeout plus a heartbeat that extends it: "create a heartbeat for your consumer process: specify the initial visibility timeout... and then—as long as your consumer still works on the message—keep extending the visibility timeout" ([Processing messages in a timely manner in Amazon SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/best-practices-processing-messages-timely-manner.html)). This is structurally identical to lease + `heartbeat()` in `pg-queue.mjs` — Construct already has the primitive, it is simply unwired.
- **Temporal** separates a *lease-like* schedule-to-start timeout (how long a task may sit unclaimed) from a *heartbeat timeout* on the activity itself, and is explicit that the heartbeat timeout is inert unless the activity actually heartbeats: "if setting heartbeat timeout, it is critical to also heartbeat from the activity, otherwise timeout is ignored" ([The four types of Activity timeouts](https://temporal.io/blog/activity-timeouts)). That is precisely today's defect in miniature: `pg-queue.mjs` has the lease/heartbeat machinery, but `entrypoint.mjs` never calls it, so the safeguard is present but inert.
- **Sidekiq** (via `sidekiq-unique-jobs`) and Postgres-native job queues both converge on lock-plus-expiry: unique-job locks with configurable TTL ([sidekiq-unique-jobs](https://github.com/mhenrixon/sidekiq-unique-jobs)), and hand-rolled Postgres queues using a `heartbeat_at` column plus a reaper that requeues jobs whose heartbeat has gone stale ("Workers update `heartbeat_at` every 5 seconds while processing, and a background 'reaper' checks for stale jobs... updating the status back to 'pending'" — [Durable Queue Workers With Just Postgres](https://mfyz.com/durable-queue-workers-with-just-postgres)). This is the general pattern this ADR asks the implementing bead to apply to `ApprovalQueue` for the write-intent drain, not just to `pg-queue.mjs` for the worker loop.

**This repo's own Postgres queue already implements the target pattern for one of the two loops** — `PostgresIntakeQueue` (`lib/queue/pg-queue.mjs:45-215`) is a `SELECT ... FOR UPDATE SKIP LOCKED` claim queue with `lease_expires_at`, `heartbeat()`, and `fail()` already built and covered by tests (truth-matrix row 35: "Correctly implemented row-locking, lease renewal, `attempt>=max_attempts → dead_letter`"). Extending the same claim-with-expiry shape to `ApprovalQueue` for the write-intent drain (rather than inventing a different concurrency primitive for that loop) keeps one mental model across both execution loops and reuses proven code.

**Rejecting exactly-once is not a reflexive "too fancy" call — it is grounded in what the external systems actually offer.** A distributed transaction across Construct's queue and a Jira/GitHub/Confluence/Slack write is not achievable regardless of effort: none of those providers exposes a two-phase-commit-compatible write API, so "exactly-once" here could only ever mean "best-effort at-most-once with a transactional *intent* record" — which collapses back into at-least-once-plus-idempotency the moment any external call has an ambiguous outcome (timeout after the write actually succeeded, network partition after send). The framing in the bead ("over-engineered for this system's scale") holds up under verification: it is not just a scale argument, it is that the destination systems make true exactly-once structurally unavailable, at any scale.

## Rejected alternatives

- **At-most-once, no retry.** Rejected: a job or write-intent that fails once (crash, worker OOM, network blip) is silently lost — the exact failure mode `oracle-miss-report.md`'s M1 vocabulary gap already flags as invisible to Oracle ("analysis didn't run" has no verdict). Given the write path already tolerates and dedups retries via `WriteSentLog`, discarding retry entirely would throw away a working mechanism to avoid a duplicate-execution risk that a lease already solves more directly.
- **Exactly-once via distributed transaction.** Rejected, per the bead's framing, verified above: none of the governed-write providers (Jira, Confluence, GitHub, Slack) exposes a transactional write API, so a distributed-transaction boundary could only wrap Construct's own queue state, not the external side effect — it would not actually deliver exactly-once semantics end-to-end, only push the ambiguity to "did the transaction commit before or after the external call landed," which is the same problem at-least-once + idempotency already solves without new infrastructure (no distributed transaction coordinator exists anywhere in this codebase today).
- **Keep the in-memory `executedApprovalIds` Set and just document the risk.** Considered because it is zero-cost — but rejected: the module's own header (`lib/writes/control-plane.mjs:1-32`) already documents `drainApprovedWriteIntents` as the sole gate on turning an approved intent into a real external write; leaving its only concurrency guard as memory that resets every process restart directly contradicts that stated guarantee, and is the literal mechanism behind truth-matrix row 22 (`dead`) and the reason ADR-N (`construct-4uxq0.4.14`) is hard-gated on this decision.
- **Fix only the worker loop's 120s/300s ordering (raise the lease default) without adding heartbeat.** Rejected as a point fix: raising the static lease number narrows the window but does not close it — any job whose runtime is unpredictable (which `runJob`'s general-purpose command execution, `lib/worker/run.mjs:60`, structurally is) can still exceed whatever static number is chosen. Heartbeat-based renewal is the only fix that scales with actual job duration rather than a guessed constant, matching Temporal's explicit design lesson above.

## Consequences

- **Positive**: gives `construct-4uxq0.9.3` (P0: execution leases for external writes) a concrete target model to implement against instead of an open design question; unblocks `construct-4uxq0.4.14` (ADR-N, approval/drain lifecycle), which is explicitly hard-gated on this ADR landing; unblocks `construct-4uxq0.9.5` (408b: write-intent-drain wiring), which depends on leases existing before the drain can be safely automated. Reuses an already-built, already-tested primitive (`pg-queue.mjs`'s lease/heartbeat/fail) rather than introducing a new concurrency mechanism, and the framing (at-least-once, exactly-once rejected) is now independently verified against both the code and comparable-systems research, not just restated from the bead.
- **Negative / cost**: `ApprovalQueue` (`lib/embed/approval-queue.mjs`) needs a new durable `'executing'`/lease-expiry state added to its state machine — non-trivial schema and migration work, scoped to `construct-4uxq0.9.3`. `lib/worker/entrypoint.mjs` needs `heartbeat()` wired into whatever supervises `runJob` mid-flight (a periodic timer, since `runJob` itself is a single blocking call today per `lib/worker/run.mjs:60`) — this is a real control-flow change, not a config tweak. Idempotency-key coverage must be confirmed for every governed-write provider (Jira/Confluence/GitHub today; Slack per truth-matrix row 28 does not exist on main yet) before leases alone are trusted to prevent user-visible duplicates.
- **Follow-up**: this is a proposal (Audit drafts, User ratifies, per `construct-4uxq0.4.4`). Implementing work is `construct-4uxq0.9.3` (the lease primitive itself, usable by both the drain and the worker), then `construct-4uxq0.4.14` (ADR-N, deciding manual-vs-automated drain now that leases will exist) and `construct-4uxq0.9.5` (408b, wiring the drain). The `oracle-miss-report.md` invariant seed `external-write-has-idempotency-and-reconciliation` (seed #9) and the row-33 contract-test remedy ("worker loop exercises every queue method its contract requires") should land alongside `construct-4uxq0.9.3` so the fix is verifiable, not just asserted.

## Reversibility

Medium: adding a lease is additive — it does not require rewriting or migrating any existing durable record shape in `WriteSentLog` or the Postgres queue tables, and idempotency keys keep working unchanged underneath it. It is not "high" reversibility because once `ApprovalQueue` gains a durable `'executing'` state and callers (CLI, any future automated drain) depend on it, removing the lease state would require a schema/behavior rollback across every caller, not just a doc change (contrast ADR-0080, which was pure ratification of existing behavior). Un-adopting this model would mean re-litigating ADR-N's drain design as well, since ADR-N is explicitly gated on leases existing.
