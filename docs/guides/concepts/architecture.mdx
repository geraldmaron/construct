## How to read this page

Start with the diagrams. They're the fastest way to build a mental model of the wiring. The text after explains the same thing twice on purpose: once in plain language, once in codebase terms. Pick whichever flavor lands faster, then read the other to lock it in.

## The 30-second version

Construct is one orchestration surface in OpenCode, Claude Code, Codex, or a supported editor.
A Workspace Preset shapes workspace-wide intake and artifact behavior. Each request becomes a
Plan of bounded Assignments. Every Assignment selects a Worker Profile, which combines a
runtime, model tier, Skills, Procedure affinity, and a Policy fence. Capabilities state what the
system can do; verification gates decide whether the result is complete.

The intake loop turns signals into outcomes: anything dropped into `inbox/` is classified using
the active Workspace Preset, planned as an Assignment graph, routed to workers with the required
Skills and Capabilities, executed inside explicit ownership boundaries, evidenced, evaluated,
and persisted. The rest of this page is wiring.

table is its architecture-level summary:

| Worker Profile | Assignable runtime, model tier, Skill emphasis, Procedure affinity, and Policy fence | `worker-profile` | `registry/worker-profiles/`; runtime in `lib/worker-profiles/` |

| Procedure | Reusable deterministic sequence invoked by Plans | `procedure` | `registry/procedures/`; runtime in `lib/procedures/` |
| Assignment | Bounded unit from a Plan, owned by one worker under a contract | `assignment` | `lib/assignments/` |
| Capability | Typed system operation with inputs, outputs, preconditions, and postconditions | `capability` | `registry/capabilities.json`; runtime in `lib/capabilities/` |
| Policy | Authority, approval, and external-effect rule | `policy` | `registry/policies/`; runtime in `lib/policy/` |
| Artifact | Content-identified output from a Run or Assignment | `artifact` | `.construct/artifacts/`; runtime in `lib/artifacts/` |
| Evidence | Assertion that an Artifact satisfies a requirement; a relationship, not a standalone record | `evidence` | `evidenced-by` graph edge; runtime in `lib/evidence/` |
| Projection | Derived adapter view of Construct-owned state | `projection` | `lib/projections/` |
| Graph Node | Non-authoritative representation of a domain or implementation entity | `graph-node` | `.construct/graph/`; runtime in `lib/graph/` |
| Graph Edge | Typed, provenance-bearing relationship between Graph Nodes | `graph-edge` | `.construct/graph/`; runtime in `lib/graph/` |

Workspace Preset and Worker Profile are deliberately separate. The `rnd`, `operations`,
`creative`, and `research` records contain workspace-wide intake, document, tone, and Skill
defaults, so they are Workspace Presets. Assignable engineering, review, research, or operations
records contain model/runtime selection, Skills, and fences, so they become Worker Profiles. A
preset can influence Profile selection; it is not itself a worker.

The retired domain uses map as follows: persona, fixed role, and specialist become Worker
Profile; scope as a selectable operating configuration becomes Workspace Preset; workflow as a
reusable Construct object becomes Procedure; team/group execution structures become Assignment
graphs expressed by a Plan. `contract` remains a subordinate input/output boundary, not a peer
domain object. `org` and `cx-` are removed from product namespaces. Retired Construct surfaces
are removed rather than held in a deprecated state or compatibility layer.

This is a semantic classification, not a word ban. Authorization scope, access-control role,
the `team` deployment mode, a GitHub Actions workflow, and an ordinary grouping operation remain
valid language. ADRs and research notes may retain an observed historical identifier as evidence,
but must not state it as current guidance or feed it into generated examples. Product-generation
qualifiers are not valid names; the product is Construct.

The cutover is one-way and ordered: registry/schema → catalogs/loaders → CLI, MCP, and execution
boundaries → docs, examples, and templates → tests and generated adapters. Producers and
consumers change together at each boundary; there is no alias or dual-read phase. The complete
consumer inventory, config fields, CLI/MCP nouns, graph-node names, and current-to-owner mapping
live in `config/canonical-terminology.json`.

## Interaction surfaces

The CLI registry is the substrate (~118 commands). OpenCode is the first-class conversational surface; other supported hosts reach the same engine through MCP, ACP, or generated adapter files ([ADR-0039](/decisions/adr/0039-interaction-surface-model)):

| Surface | Entry | Responsibility |
|---|---|---|
| OpenCode | `construct` agent in OpenCode | Primary conversational authoring surface |
| Agent / MCP | `@construct` or MCP tools in Claude, Codex, Cursor, Copilot, VS Code | Orchestration Policy, Skills, Procedures |
| Thin CLI | `construct status`, `construct doctor`, `construct intake`, … | Operator diagnostics, setup, queue inspection, CI/headless contracts |

Oracle (`construct oracle status`) sits alongside as an L0.5 bounded-auto health layer — not a user-facing conversation surface.

## Document I/O

Ingestion and export are optional halves bound to external tooling ([ADR-0024](/decisions/adr/0024-document-io-optional-capability), [ADR-0036](/decisions/adr/0036-document-ingestion-docling-mcp-evaluation.md)):

| Half | Entry | Engine |
|------|-------|--------|
| Ingest | `construct ingest` | Quality-aware extraction ladder: unpdf/mammoth (lightweight), Docling sidecar (local OCR/layout), Docling Serve (remote when privacy allows), whisper (AV) |
| Export | `construct export` / `construct publish` | Pandoc + Typst (PDF), branded HTML/deck, pptxgenjs (PPTX), LibreOffice (legacy `.doc`) |

**In** accepts PDF, Office, email, AV, and plain text → normalized markdown written from a RichDocument instance (ingest builds the IR once, renders markdown from it, and derives the `.assets.json` sidecar from the same object). Extraction tier selection (`lib/document-extract/extraction-ladder.mjs`) evaluates format, text yield, fidelity request, and privacy posture rather than extension alone: native structured parsers → lightweight parsers (unpdf/mammoth) → local Docling → remote Docling Serve → explicit unsupported/manual-recovery. Routing signals surface through `resolveExtractionRoutingSignals` in `lib/ingest/strategy.mjs`. **Authoring** stays typed markdown artifacts. **Out** spans PDF, DOCX, DOC, HTML, deck, PPTX, RTF, ODT, EPUB, and more. The production ingest → RichDocument → export path is certified end-to-end by `lib/certification/richdocument-production.mjs` (corpus fidelity, provenance survival, truthful `droppedInfo`).

Canonical format matrix: [Document I/O reference](/guides/reference/document-io). Brand tokens live in `lib/brand-tokens.mjs` and flow to PDF/HTML/deck/PPTX via `lib/publish-template.mjs`.

## Product intelligence: customer profiles and multi-PM workspaces

Two durable, cross-session stores back product-facing signal routing, both under `lib/embed/` and both surfaced by CLI (`construct customer`, `construct workspace`):

- **Customer profiles** (`lib/embed/customer-profiles.mjs`) are global account memory at `~/.construct/knowledge/internal/customer-profiles/<id>.md`, additive by design — history is preserved unless explicitly deleted. `detectCustomerMentions()` scans intake signal text for name/domain/alias matches; `lib/intake/prepare.mjs` calls it during intake preparation and, on a match, `linkSignalToCustomer()` appends a change-log entry to the matched profile via `updateCustomerProfile()`.
- **Workspaces** (`lib/embed/workspaces.mjs`) isolate workstreams and their customer ids and product areas at `~/.construct/knowledge/internal/workspaces/<id>.json`. `routeSignalToWorkspace()` resolves an incoming signal by customer-id membership first, then product-area keyword match; a signal matching more than one workspace is explicitly flagged as cross-workspace.

Both stores are CLI-only today (`construct customer list|show|add|search`, `construct workspace list|create|show|assign`) — no MCP tool or orchestration-policy integration exposes them to a worker beyond the intake-time auto-linking above.

**Runtime directory semantics.** Construct distinguishes `packageRoot` (the npm install directory — source of bundled Worker Profiles, Workspace Presets, Skills, schemas, hooks, and templates) from `projectRoot` (the user's repo, discovered by walking upward from cwd). Services that read or write durable state (`.construct/`, oracle, telemetry, beads) must use `projectRoot`; asset loaders must use `packageRoot`. `process.cwd()` is the raw fallback before `projectRoot` is resolved. See [Root semantics](/guides/concepts/root-semantics) for the full subsystem table and a worked example.

## In human terms

You ask Construct to fix a redirect or ship a portal. Construct frames the outcome, decomposes it
into bounded Assignments, selects the Worker Profiles and Skills each Assignment needs, and
checks every result against its Capability contract and Policy. Review, QA, and security are
Assignment responsibilities, not permanent characters in an organization chart. Nothing ships
until the gates pass. Beads projects the work; documentation records durable decisions; memory
preserves verified context.

## In technical terms

Construct classifies the request, resolves an execution track and required gates, then dispatches the assignment through the MCP server. Verification runs the release gates and contract postconditions before a commit; failures receive a chain-hashed record in `~/.construct/contract-violations.jsonl`. Providers are stateless adapters; durable state lives under the Construct state roots.

## Why it's built this way

- **One public surface.** The user talks to Construct. Worker Profiles are internal execution configuration and do not fragment that contract.
- **Stateless providers.** Providers never own durable state. Swapping GitHub for a custom Git provider, or adding Salesforce, doesn't migrate any data. Construct's stores stay put.
- **Mode-driven topology.** Deployment mode (`solo` | `team` | `enterprise`) selects the backends for the intake queue, run store, memory, telemetry, and workers. Queue and run-store selection resolve through extension manifests (`kind:"queue"` / `kind:"storage"`) with builtin defaults; an explicit backend that is not registered degrades visibly instead of silently falling through. Solo runs everything locally and degrades gracefully when an optional resource is missing. Team and enterprise now default to the Postgres intake queue, which supplies row-locked claims, expiring leases, and heartbeat renewal; if no SQL client is configured, the mode fails closed unless `CONSTRUCT_DEGRADED_OK=postgres-queue` explicitly permits a visible git-queue fallback. Shared run storage uses Postgres when configured. Brokered MCP dispatch is staged/experimental and not yet active in built-in deployments (tracked: construct-9oi4.10). See [deployment model](/guides/concepts/deployment-model).
- **Hard gates over soft hooks.** Comment policy, doc verification, template policy, and contract postconditions fail the build. They are not advisory. The default is "stop and fix"; CI is a backstop, not the primary check.
- **No fabrication, enforced.** Every load-bearing claim in every artifact traces to a source. Lint blocks unsupported assertions in real time. Intake traceability stamps every artifact's origin packet into its frontmatter. Contract postconditions verify structural requirements before a handoff crosses a phase boundary. See [Integrity and trust](/guides/concepts/integrity-and-trust).
- **Independent verification.** Review, QA, challenge, and security Assignments have explicit acceptance gates. Agreement without evidence does not satisfy them.

### Core

The foundation. Handles orchestration, Assignment dispatch, memory, sessions, and the MCP server. Zero external npm dependencies.

- **CLI surface**. `bin/construct` and `lib/cli-commands.mjs`
- **MCP server**. `lib/mcp/server.mjs`, tools split across `lib/mcp/tools/`
- **Orchestration policy**. `lib/orchestration-policy.mjs` (intent classification, execution track selection, gate evaluation, contract-chain resolution)
- **Agent contracts**. `registry/capabilities.json` postconditions and `lib/contracts/validate.mjs` (producer→consumer Assignment contracts with preconditions, postconditions, input/output schemas). Every postcondition is classified `executable` or `advisory` (`lib/contracts/coverage.mjs`, `construct-rf26.12`) rather than left as undifferentiated prose.
- **Observation store**. `.construct/observations/` (role-scoped, capped insights for continuous learning) backed by a retrieval adapter (`lib/storage/retrieval-adapter.mjs`, ADR-0081): a machine-scoped LanceDB vector index at `<stateRoot>/lancedb` (ADR-0066) when LanceDB is reachable, or a dependency-free keyword/BM25 index at `<stateRoot>/keyword-index` otherwise — selectable via `CONSTRUCT_RETRIEVAL_ADAPTER` (default `auto`). Both the vector index and the ONNX embedding model provision lazily — first `construct ingest`/observation store or search, not `construct init` (opt in early with `--seed-index`/`construct install --with-embeddings`). TTL/size eviction on the indexed rows (`resources.disk.observationsMaxDays`/`observationsMaxRows` in `construct.config.json`, default 90d/5000 rows) runs on every `construct ingest` and is surfaced in `construct doctor`/`construct prune` (`lib/storage/admin.mjs`'s `purgeExpiredData`, construct-rf26.17).
- **Session persistence**. `lib/session-store.mjs`, `.construct/sessions/` (distilled session records for resumption)
- **Hybrid search**. `lib/storage/` (file-state source, SQL store, vector index, hybrid query facade). One consolidated path: `lib/storage/hybrid-query.mjs` runs file BM25 + native pgvector HNSW ANN (`<=>`, with `hnsw.iterative_scan` on pgvector ≥ 0.8) + keyword, and fuses them by Reciprocal Rank Fusion (`lib/storage/rrf.mjs`) so incompatible score scales merge by rank. `lib/knowledge/search.mjs` accepts `tags` + `tagMatch` for tag-filtered BM25 over file content.
- **Plugin engine**. `lib/engine/` with six contracts (Embedder, Chunker, Indexer, Fuser, Reranker, Compressor). Each layer resolves to a built-in default unless overridden by `~/.config/construct/plugins.json`, `<project>/.construct/plugins.json`, or `CONSTRUCT_PLUGIN_<LAYER>` env. Failed overrides fall back to the default and surface in `construct doctor`. External git projects plug in by exporting a factory that satisfies the contract. `assertContract(layer, plugin)` runs at load time so the failure is loud, not silent.
- **Tag system**. `config/tag-vocabulary.json` is the repo-wide controlled vocabulary (five orthogonal facets: intake-type, lifecycle, priority, signal-strength, reversibility). Project-local overrides at `.construct/tags/vocabulary-overrides.json`. `lib/tags/vocabulary.mjs` merges both tiers; `lib/tags/lifecycle.mjs` manages the active/deprecated/archived lifecycle with Postgres-backed migration audit at `db/schema/007_tags.sql`. Auto-attribution: `suggestTags(triage, related, vocab)` in `lib/intake/classify.mjs` stamps `intake/<type>` tags from classification confidence; related-doc inheritance at 0.70. Four cross-cutting tags promote to graph entities: `signal/high-customer-interest`, `priority/p0`, `priority/p1`, `reversibility/irreversible`.
- **OTel telemetry**. `lib/telemetry/otel-tracer.mjs` provides a graceful-degrade facade over `@opentelemetry/api` (optional dep). When `OTEL_EXPORTER_OTLP_ENDPOINT` is set, real GenAI client spans emit `gen_ai.*` attributes per the OpenTelemetry GenAI semconv. W3C traceparent propagates across MCP boundaries via `params._meta` (SEP-414). When the SDK is absent or no endpoint is configured, a no-op path runs with zero overhead. `lib/telemetry/skill-calls.mjs` captures per-skill load events with latency, agent identity, session id, and token size; `construct skills usage|orphans|hot|correlate-quality` surfaces the rollup.
- **Workflow templates**. `templates/workflows/` YAML templates (new-feature, engineering-onboarding, cross-team-handoff) define inputs, artifact chains, and linked beads items with dependency order. `lib/workflows/instantiate.mjs` renders and creates the chain. `schemas/workflow.schema.json` validates all templates.
- **Hooks / enforcement**. `lib/hooks/` (session-start, bash-output-logger, repeated-read-guard, context-watch, audit-trail)
- **Audit trail**. `lib/audit-trail.mjs`, `~/.construct/audit-trail.jsonl` with tamper-evidence chain
- **Doc stamps**. UUIDv7 front-matter on all generated `.md` files for identity, provenance, and tamper detection

### Providers

Transport-agnostic interface to external systems. Each provider implements a capability matrix and chooses its own transport (MCP, REST, GraphQL, SDK, CLI, webhooks). Core dispatches through the interface. it never knows the transport.

**Capability matrix:**

| Capability | Description |
|---|---|
| `read` | Fetch items, pages, messages, files from the external system |
| `write` | Create or update items (work items, messages, pages, PRs) |
| `search` | Query the external system's index |
| `watch` | Poll or subscribe for changes |
| `webhook` | Receive inbound events from the external system |

**Provider contract:**
- Providers are stateless adapters. Durable state lives in core stores.
- Auth is per-provider, configured in `.construct/providers.yaml` or environment.
- A provider may support any subset of capabilities; unsupported capabilities return a typed error.
- Provider implementations live in `lib/providers/` (data-source adapters) and `lib/providers/contract/adapters/` (contract harness). See [ADR-0044](/decisions/adr/0044-tool-repo-root-layout).

**Provider scope framing.** Every provider config carries an allowlist (`repoAllowlist`/`repoAllowGlob` for GitHub, `projectAllowlist` for Jira, `spaceAllowlist` for Confluence, `channelAllowlist` for Slack). Requests targeting out-of-scope resources return a typed `OUT_OF_SCOPE` error. `construct creds set|rotate|list|revoke|test <provider>` manages credentials in `~/.config/construct/config.env` (0600 enforced), and `construct creds login copilot` runs the GitHub Copilot OAuth device flow (ADR-0042). Values may be plain keys or 1Password `op://` references, resolved at call time by `lib/providers/secret-resolver.mjs`. For hosted LLM providers (`openrouter`, `anthropic`, `openai`), `construct creds test` performs a lightweight authenticated probe through `lib/providers/connection-probe.mjs` and reports provider health without exposing credential values. `construct providers discover <name>` runs provider-specific discovery with TTL-cached results.

**Shipped providers:**

| Provider | Transport | Capabilities |
|---|---|---|
| Git repo | git CLI | read, write, watch |
| Project tracker (Jira) | REST API v3 | read, write, search, webhook |
| Messaging (Slack) | Slack Web API | read, write, watch, webhook |
| Code host (GitHub) | gh CLI | read, write, search, webhook |
| Knowledge base (Confluence) | REST API v2 | read, write, search |

### Model invocation

Two layers, kept deliberately separate (workspace-control-plane split verdict, `construct-b0nny.19`): Construct decides *which model tier* a call needs; it does not own *how* the call is transported.

- **Tier/policy metadata (retained).** `lib/model-router.mjs` (plus `lib/model-tiers.mjs`, `lib/model-policy.mjs`, `lib/model-pricing.mjs`, `lib/model-free-selector.mjs`, `lib/model-cheapest-provider.mjs`) resolves which model id serves a `reasoning`/`standard`/`fast` tier across the shipped provider families (Anthropic, OpenRouter sub-families, GitHub Copilot, OpenAI, Ollama, local), tracks provider credentials/cooldowns, and classifies failures for fallback selection. Read by `bin/construct` (`models`, `doctor`), the embedded-contract layer, MCP tools, `lib/opencode-runtime-plugin.mjs`, and setup/postinstall — every one of these consumes it as metadata only; none of them dispatch a model call themselves. `lib/model-registry.mjs` (a 17-line compatibility re-export stub) was retired in `construct-b0nny.19`; its two importers (`lib/embedded-contract/{capability,model-resolve}.mjs`) now import `lib/model-router.mjs` directly.
- **Invocation, migrated where a real dispatch loop existed.** The actual "send a request, get a response" transport is the E4 runtime-adapter contract (`lib/runtime/contract/`, `construct-b0nny.24`): `interface.mjs`/`conformance.mjs`/`registry.mjs` plus adapters for a `claude` CLI subprocess, the Claude Messages API, an ACP stdio agent, and an in-process handler. `construct-b0nny.19` found that `model-router.mjs` itself contains no invocation code — the genuine ad hoc invocation loops lived in individual call sites that resolved a model id from the router and then hand-rolled their own `fetch` to `api.anthropic.com/v1/messages`. Two such sites (`lib/intent-classifier.mjs`'s background routing verifier, `lib/schema-infer.mjs`'s document-schema inference) now route their Anthropic-direct calls through `adapters/coding/claude-api.mjs`, with per-call-site equivalence tests (`tests/intent-classifier-claude-api-migration.test.mjs`, `tests/schema-infer-claude-api-migration.test.mjs`); their OpenRouter-direct branches are unchanged, since no OpenRouter adapter exists in the E4 contract. Most of Construct's model invocation happens outside this process entirely — OpenCode (the primary conversational surface) and IDE-embedded hosts invoke models themselves; Construct resolves which model id/tier they should use and reacts to the failures they report (`lib/hooks/model-fallback.mjs`, the OpenCode plugin's fallback handler), rather than sitting in the request path.

### Runtime

Docker service management, embed daemon, and scheduler.

- **Service manager**. `lib/service-manager.mjs` (memory server lifecycle; local Postgres process management is out of scope — solo mode uses embedded LanceDB, and the optional SQL client opens only when `DATABASE_URL`/`CONSTRUCT_DATABASE_URL` is configured)
- **Embed daemon**. scheduled or long-running process that monitors sources through providers, produces snapshots, manages approval queue. `construct embed supervise` installs a platform-native supervisor (launchd/systemd/Task Scheduler) for auto-restart on crash.
- **Standing Assignments**. `lib/embed/standing-assignments.mjs` (ADR-0085) — the canonical durable record for recurring/triggered work: trigger spec, action spec, lifecycle (`active`/`paused`/`retired`), and attempt state, one atomic JSON record each (ADR-0081 temp+rename) under `.construct/runtime/standing-assignments/`. Each enabled embed capability is materialized as a `capability:<id>` assignment at daemon registration, and its scheduled tick runs through `runAssignmentAttempt` — the only path that advances `lastAttemptAt`, stamped strictly after execution, never on due-detection. Inspect with `construct embed assignments [list|status <id>]`.
- **Scheduler abstraction**. `lib/scheduler/index.mjs` — `registerJob`, `runJobOnce`, `listJobs`. Three modes: solo (native triggers via launchctl/systemd/Task Scheduler), team/enterprise (Postgres advisory-lock leader election), one-shot CI. Three built-in jobs: `tag-candidate-mining`, `skill-usage-rollup`, `doc-hygiene-scan`. CLI: `construct scheduler run|list|runner`.
- **Doc hygiene scanner**. `lib/hygiene/scan.mjs` selects stale lifecycle-tagged documents for review: `lifecycle/approved` older than 30 days, `lifecycle/draft` older than 7 days, any doc missing `last_verified_at`. `stampVerified` writes the field to frontmatter. Integrated into the `doc-hygiene-scan` scheduler job.
- **Resource bootstrap**. `lib/bootstrap/resources.mjs` probes optional resources (Postgres, ONNX model, Docker, git); `construct init` runs the full wizard.

Optional embed-daemon job `auto-backup` runs every `CONSTRUCT_AUTO_BACKUP_DAYS` days (off by default).

## Operating model: gates + capabilities + assignments

Every request flows through three structural layers:

1. **Gates**: preconditions that must hold before work begins, including framing, research, document ownership, authority, and approval.
2. **Capability contracts**: typed inputs, preconditions, output shapes, and postconditions that an Assignment must satisfy. Mechanically checkable postconditions execute in `lib/contracts/validate.mjs`; irreducible judgment remains explicitly advisory.
3. **Assignment sequence**: dispatch plan with ordering and parallel markers. Required review,
   research, and document-ownership Assignments are inserted by Policy.

Beyond the fixed gate set, **participation rules** (ADR-0070) recruit additional review or
advisory Assignments when a signal expression matches. Reasons remain visible on invocation
results, and every recruited Assignment is subject to the same Capability and Policy gates.

## Flow engine

Sequencing that used to live as prose injected into an agent's context (`lib/orchestration-policy.mjs`'s contract-chain resolution) is a deterministic engine ([ADR-0067](/decisions/adr/0067-deterministic-flow-engine)). `lib/flows/` is a zero-dependency typed-state engine: `defineFlow`/`loadFlow` validate a flow's state schema, step graph, and fan-out rules at load time, so a flow that loads at all is structurally valid — failures surface at authoring time, not mid-run. `runStep`/`advanceRun`/`runFlow` execute steps and route between them via pure, synchronous routers (`router(state)` must be deterministic; no LLM calls belong there), with `andJoin`/`anyJoin` combinators for reconvergence. Fan-out is restricted, not just discouraged: a step can only declare `fanOut: true` if it is also `readOnly: true` and names a `synthesis` step every branch joins into, encoding the same read-only/breadth-first restriction [ADR-0065](/decisions/adr/0065-orchestrator-worker-consolidation)'s evidence argues for. A step's per-run usage against a declared `budget` produces a typed `budget-exhausted` result instead of a silent truncation. See [Flow authoring](/guides/concepts/flow-authoring) for the full authoring guide, including the step contract (`workerBackend`/`run`/`router`/`budget`) and the idempotent-re-entry convention.

**Checkpoint and resume.** `lib/flows/checkpoint.mjs` persists a run after every completed step to the project's machine-scoped state root (`runtime/flows/runs/<runId>.json`, [ADR-0066](/decisions/adr/0066-config-layer-project-footprint)), atomic write via temp-file-then-rename — the same pattern `lib/orchestration/run-store.mjs` uses for orchestration runs. `resumeRun`/`startRun`/`runCheckpointed` reconstruct a run's state on resume and throw `FlowCheckpointError` rather than silently reinterpreting history if the checkpoint's flow id doesn't match the flow definition it's resumed against. `construct flow resume <run-id> --flow=<path> [--state=<json>]` drives a run (new or resumed) to completion; `construct flow status <run-id>` reads a checkpoint without driving it — this CLI is the engine's only live caller today.

**Delegation port removed (`construct-b0nny.13`, workspace-control-plane M0).** `lib/orchestration/delegation-flow.mjs` — the `construct-rf26.9` additive port of contract-chain dispatch onto the flow engine above — was deleted as dead code: it never gained a live caller beyond its own test suite once the MCP tool that would have exposed it (`orchestration_delegation_next`) was removed under the tool-surface budget, confirmed via the disposition matrix (`docs/notes/research/workspace-control-plane/synthesis/disposition-matrix.md`, Cluster C5). Contract-chain dispatch (see above) resolves directly from `routeRequest`'s `specialists`/`dispatchReasons` output, consumed by the orchestrator persona and `lib/orchestration/runtime.mjs`'s `buildTasks()` — there is no flow-step abstraction in that path.

## Construct on Construct

Construct applies the same control plane to its own maintenance. Deterministic watchers handle
repeatable checks; Worker Profiles are selected only for Assignments that require judgment. The
user stays in the loop for novel decisions and explicit approval, not routine operations.

Four operational tiers:

1. **Deterministic checks.** The doctor watcher library monitors process pressure, service health, disk, cost, and MCP protocol health. Recoverable actions are audit-logged to `~/.construct/doctor-log.jsonl`; no background doctor daemon auto-starts.
2. **L0.5. Oracle meta-review (deterministic synthesis + bounded auto, one-shot only).** `construct oracle review` (`lib/oracle/`) joins session observations, outcomes, contract violations, doctor log entries, alignment census, org graph (policy inventory, workflow gates, intake sign-offs), beads hygiene, and adapter parity into per-tick verdicts at `.construct/oracle/verdicts/<date>.json`. Auto actions (census, registry validate when needed, adapter sync in the tool repo) run without approval; high-severity **actionable** gaps auto-raise idempotent beads (persistent `gapId` dedup, open-bead check) when `CONSTRUCT_ORACLE_AUTO_RAISE` is not off — hygiene/meta gaps (`beads-hygiene`, `workflow-misaligned`, …) are verdict-only via `construct oracle gaps` and never file duplicate tracker beads; `detectBeadsDrift` excludes `[oracle/*]` meta beads from stuck/stale counts. Orchestration queues to `.construct/oracle/pending.jsonl` for explicit approval with sign-off metadata (`construct oracle approve <id>` executes by default). Routing artifacts land in `.construct/oracle/routing/`; duplicate hygiene beads: `construct oracle reconcile`. The Oracle background daemon and state migration utilities are removed; the surviving surface is the deterministic one-shot review API (`construct oracle review`/`status`/`pending`/`approve`/`gaps`/`reconcile`/`triage`). See [ADR 0043](/decisions/adr/0043-oracle-meta-controller) for the original design.
3. **Assignments.** Events and requests resolve to a worker profile and bounded capability set. The gateway applies thresholds, cooldowns, and rate ceilings, records the assignment in `~/.construct/role-pending.jsonl`, and surfaces it to Construct for execution within the declared policy fence.
4. **L2. User.** Commits, pushes, novel decisions, budget overrides, kill switches. Approval-required actions per `rules/common/commit-approval.md` are always L2. The goal is to make L2 rare. not zero.

Kill switches throughout: `CONSTRUCT_ROLES=off` (global L1), `CONSTRUCT_ROLE_<NAME>=off` (per-persona L1).

## Footprint contract

Construct's install and init paths are governed by a per-scope opt-in contract codified in [ADR 0029](/decisions/adr/0029-install-scopes-and-hook-budgets). Two scopes; `construct install` requires the caller to name one explicitly (construct-vzg2i.3) — a bare invocation hard-errors rather than silently defaulting.

### Project scope — `construct init` (per repository)

Project scope writes are confined to the project root and the project's `.git/` config. Nothing in this list ever lands on a machine without an explicit `construct init` invocation inside the project directory.

| Path | Purpose | Owner |
|---|---|---|
| `.construct/` | Project-local Construct runtime state | construct init |
| `.construct/` | Observations, sessions, traces, intake, task graphs (gitignored) | construct init |
| `.claude/agents/` · `.claude/commands/` · `.claude/settings.json` · `.mcp.json` | Claude Code adapter tree (agents + hooks/permissions + slash commands + MCP servers) | construct sync |
| `.codex/`, `.vscode/`, `.opencode/`, `.cursor/` | Per-host adapters when the host is detected (gitignored — run `npm run adapters` or `construct sync`) | construct sync |
| `construct.config.json` | Project config + active profile | construct init |
| `plan.md` | Local-only current plan (gitignored) | construct init |
| `CLAUDE.md` · `AGENTS.md` | Marker-block injection — Construct's section only, preserving surrounding content | construct sync |
| `.gitignore` | Appends Construct's runtime paths (idempotent) | construct init |
| `.beads/` | bd issue tracker init | construct init |
| `.git/config` `core.hooksPath` | Project-scoped git hooks path | construct init |

### Machine scope — `construct install --footprint=user` (per machine)

Machine scope writes are opt-in. A bare `construct install` (no `--footprint`) hard-errors naming the flag; `--footprint=project` prints footprint guidance and exits without touching the machine. `--footprint=user` writes the paths below; the marker-block writes to `~/.claude/*` require an itemized interactive consent prompt (or `--yes` for non-interactive contexts).

| Path | Purpose | Consent |
|---|---|---|
| `~/.config/construct/config.env` | Machine credentials (mode 0600) | `--footprint=user` |
| `~/.config/construct/lib` (symlink) | Hook lib symlink to the active Construct checkout's `lib/` | `--footprint=user` |
| `~/.config/opencode/opencode.json` | MCP entries — Construct's section merged | `--footprint=user` |
| `~/.codex/config.toml` | MCP entries — Construct's section merged | `--footprint=user` |
| `~/.claude/CLAUDE.md` | Marker block — Construct's section only | `--footprint=user` + interactive consent |
| `~/.claude/settings.json` | Global safety-hook injection — Construct's section only | `--footprint=user` + interactive consent |
| `~/.claude.json` | `context7` MCP in the top-level `mcpServers` (Claude Code's user scope; settings.json does not carry MCP server definitions) — Construct's entries only | `--footprint=user` + interactive consent |

### Never touched

- `~/.bashrc`, `~/.zshrc`, or any other shell rc — Construct never writes to shell init files.
- `npm` global config or registries.
- `git config --global core.hooksPath` — explicitly prohibited by [ADR 0027](/decisions/adr/0027-host-project-footprint-and-non-destructive-scaffolding) §3.
- Any path outside the table above without first appearing in `construct doctor` drift output and prompting for consent.

### Hook performance budgets

Every `lib/hooks/*.mjs` file declares a `@p95ms <N>` budget in its header. The benchmark harness `scripts/bench-hooks.mjs` measures p95 over N=20 runs against a synthetic event payload; a nightly CI gate fails when measured p95 exceeds the declared budget by more than 2×. Defaults: `UserPromptSubmit` 200 ms, `PreToolUse` / `PostToolUse` 500 ms, sync `Stop` arm 500 ms, `SessionStart` 1000 ms. Gate hooks (user-invoked, deliberate quality gates) declare an explicit budget — e.g. `pre-push-gate.mjs` is `@p95ms 180000`.

### Embedded operating profile

Embed mode is governed by a config-backed operating profile, not just a list of watched sources. The profile is the daemon's bearing: mission, strategy, focal resources, authority boundaries, artifact responsibilities, and risk model.

Precedence is explicit: approval rules and tracker/doc ownership override profile preferences. The default profile is assistive and read-first:

- autonomous: read sources, summarize, identify gaps, generate snapshots, draft roadmaps/status/summaries/artifacts
- approval-queued: create or update issues, publish durable docs, post externally, write broadly to the repo
- focal resources: `plan.md`, `docs/architecture.md`, `.construct/knowledge/`, `.construct/roadmap.md`
- artifact obligations: roadmaps, PRDs, RFCs, ADRs, memos, status updates, summaries, wireframes, and risks

Every snapshot discloses the active operating profile and any operating gaps, such as missing focal resources, missing sources, source read failures, or missing outputs. Roadmaps include the same profile obligations so operators can tell whether Construct is only observing or also missing responsibilities.

## Embedded contract layer (app-facing)

Two different `embed` names exist in this repo and must not be conflated:

- **`lib/embed/`** — the autonomous embed-mode daemon (`construct embed start`): scheduler, snapshot engine, approval queue, provider registry, and self-healing jobs. This is a running process, not a versioned SDK import surface.
- **`lib/embedded-contract/`** — the **Embedded Contract Layer (ECL)**, the versioned in-process SDK published to package consumers via `package.json` `exports` (`.` and `./embedded-contract` both resolve here). Deep imports through a wildcard `./lib/*` export are intentionally closed so consumers negotiate compatibility through `CONTRACT_VERSION` instead of internal module paths.

Distinct from Embed *mode* (the daemon above), the **Embedded Contract Layer (ECL)** is the stable, versioned surface another application uses to embed Construct as an orchestration layer. It lives in `lib/embedded-contract/` and exposes five read/execute contracts over one shared core, surfaced identically on three transports — CLI-JSON, MCP tools, and an SDK (`package.json` `exports` → `lib/embedded-contract/index.mjs`).

| Contract | Question it answers | Core | Surfaces |
|---|---|---|---|
| Capability discovery | What can this Construct do? | `capability.mjs` | `construct capability describe --json` · `capability_describe` · `describeCapabilities` |
| Triage / planning | What kind of work is this, who should own it? | `triage.mjs` | `construct intake classify --json` / `graph recommend --json` · `triage_recommend` · `recommendPlan` |
| Model resolution | Which model should an embedded workflow use? | `model-resolve.mjs` | `construct models resolve --json` · `model_resolve` · `resolveEmbeddedModel` |
| Execution capability | Will this run orchestrate or degrade to prompt-only, and why? | `execution.mjs` | `construct execution resolve --json` · `construct_execution_resolve` · `resolveExecution` |
| Workflow invocation | Run a role/skill workflow non-interactively | `workflow-invoke.mjs` + `workflow-defs.mjs` | `construct workflow invoke --json` · `workflow_invoke` · `invokeWorkflow` |

Invariants that make it safe to embed, especially for teams where auditability is non-negotiable:

- **One core, three surfaces.** CLI, MCP, and SDK are thin adapters; every response is built by the same core function and wrapped by `envelope.mjs`, so the surfaces return structurally identical envelopes (proven by `tests/embedded-contract-parity.test.mjs`).
- **Versioned.** Every envelope carries `contractVersion` (`contract-version.mjs`, semver, independent of the package version) plus `constructVersion` and `deploymentMode`, so an embedder can negotiate compatibility.
- **No secrets, structurally.** Every response passes `redaction.assertNoSecrets` before serialization; credential state is reported as a boolean (`requiresCredential`), never a value.
- **No drift.** Capability discovery reads the live registries (roles, skills, workflow defs, policies, providers), so the published contract cannot diverge from what the install actually supports.
- **Approval-gated writes.** Only workflow invocation can write, and only under `allow-durable-write`; `proposal-only` and `requires-human-approval` perform no durable writes. Team/enterprise durable writes are flagged as audited. Specialist reasoning is delegated to the host agent runtime — Construct returns the orchestration plan and provenance, never fabricated specialist output.

See [Embedded contract layer](/guides/concepts/embedded-contract) for the contract model and [Embedded contract API](/guides/reference/embed-api) for request/response schemas.

## Certification

`construct certify` (`lib/certification/`) is scenario-based evidence: a catalog of certification scenarios (`scenarios.mjs`) exercised through `runner.mjs`, each producing a durable run record (`schemas/certification-run.schema.json`, validated by `run.mjs`) stored at `.construct/certification/runs/<run-id>/run.json` (`store.mjs`). A run's verdict is one of `pass` / `fail` / `inconclusive` (`VERDICT_STATUSES`) from one of four sources — `deterministic`, `qualitative`, `skipped-provider`, `error` (`VERDICT_SOURCES`) — and a skipped provider call can never be promoted to a pass: hermetic scenarios run deterministic gates only, live scenarios require `CONSTRUCT_CERTIFY_LIVE=1`, and paid reference models additionally require `CONSTRUCT_CERTIFY_ALLOW_PAID=1` with an operator-acknowledged budget cap (`model-routing.mjs`, `CONSTRUCT_CERTIFY_BUDGET_USD`). Model routing defaults to OpenRouter's free tier.

`runner.mjs` composes certification from existing validators rather than duplicating them — capability ledger freshness, test-corpus inventory, artifact release gates, role-card validation, specialist-contract audits, golden artifact gates, and skill-scenario fixtures all feed one run. `status.mjs` rolls up latest verdicts, stale-impact markers, and catalog coverage across capabilities, specialists, skills, artifact types, document categories, and demos (`construct certify status`). `rc-gate.mjs` is the release-candidate gate: it blocks a release when release-critical capabilities are stale, hermetic scenarios regress, or only skipped live runs exist, running hermetic scenarios inline so CI does not depend on local run history (`construct certify gate`, wired into `release:check`).

## Living dependency matrix (change-impact spine)

Where the capability registry declares *what* connects to what, the dependency matrix (`lib/graph/`) makes the connections **traceable in both directions and keeps them current from code structure**, so a file change can be mapped to the workflows and tests it affects. It is a typed, directed graph hosted in the knowledge-graph layer at `.construct/graph/{nodes,edges}.jsonl` (gitignored, regenerated; the store is `lib/graph/store.mjs`). Node types: `file`, `module`, `test`, `capability`, `workflow`, `contract`, `surface`, `skill`, `rule`. Edge relations: `imports`, `realizes` (file→capability), `validates` (test→capability), `embeds` (capability→workflow), `uses`, `governed_by`, `exposes`, `contains`, `co_changes`.

Population is hybrid (`construct graph build`): (1) **registry ingest** (`build-from-registry.mjs`) seeds capability/workflow/test/contract/skill/surface nodes and their edges from `registry/capabilities.json`, `workflow-defs.mjs`, and `registry/`; (2) **static import derivation** (`build-import-graph.mjs`) walks `lib/`, `bin/`, `scripts/`, `tests/` for relative imports, adds `file`/`module` nodes with `imports` edges, and derives the otherwise-missing `realizes` (file→capability) edges from each capability's declared-test import closure; (3) **git co-change** (`build-co-change.mjs`) adds `module` nodes with `contains` and `co_changes` edges (reusing `captureDependencyPatterns`, which also feeds the entity store).

`construct graph build-targets` derives a static import graph for each registered source target. Each target graph persists independently at `.construct/graph/targets/<targetId>/{nodes,edges}.jsonl` and is queryable with `construct graph query`.

`construct impact [files] [--stdin] [--run] [--json]` (`lib/graph/impact.mjs`) is Test Impact Analysis: a changed file selects the tests that transitively import it plus the tests validating any capability it realizes, rolls up impacted capabilities and workflows, and flags changed files that realize no capability. **Oracle is the overseer** — `collectDependencyGraph` (`lib/oracle/read-model.mjs`) feeds `synthesizeVerdict` three gaps with deterministic routes (`lib/oracle/routing.mjs`): `matrix-coverage-gap` (no impl/test edge → `cx-architect`/`cx-qa`), `impact-untested` (realizing files changed after `lastValidated` → `cx-qa`/`cx-engineer`), and `dependency-graph-stale` (seeds changed since last build → `cx-engineer`). Document-type capabilities rely on `tests/certification/artifact-gates.test.mjs` plus workflow-level functional tests for validation stamps. Advisory-first: gaps and the `impact` command surface signals; nothing blocks.

## Work spec and graph-informed planning

`lib/planning/` (construct-b0nny.23, the workspace-control-plane program's E3 outcome — target-
model.md concepts 6/7/9, "Work Specification"/"Plan"/"Assignment") is a Work spec schema plus a
graph-informed decomposition check, not a tracker: `bd`/beads remains the tracker (E8's job,
`construct-b0nny.27`). A Work spec (`lib/planning/work-spec.mjs`) is one flat, `bd create`-shaped
object combining the *what/why* (objective, desiredOutcome, requirements, acceptance criteria,
...) and the *how* (`decomposition`: an array of Assignments, each with `touches` — the graph node
ids it reads or mutates — `dependsOn`, and `ownership`), mirroring this program's own bead
quality-field discipline since a Work spec IS a bead at execution time. `validateWorkSpec`/
`validateAssignment` never throw, returning error-string arrays, matching
`lib/directives/directive-config.mjs`'s `validateDirective` convention.

`lib/planning/decomposition-check.mjs` generalizes spike C's proven independence pattern
(`docs/notes/research/workspace-control-plane/synthesis/spike-c-parallel-software-change.md`)
into a reusable library, reusing — not re-deriving — the relational graph store's existing
`queryDown`/`queryPath` (`lib/graph/relational/queries.mjs`, construct-b0nny.12/.21): (1)
`detectDependencyCycles` — pure DFS cycle detection over a decomposition's own declared
`dependsOn` edges; (2) `checkDependencyResolution` — for every declared dependency, confirms a
real graph path connects the dependent assignment's touched nodes to the depended-on assignment's
touched nodes, flagging a dependency the graph cannot verify rather than trusting narrative intent
(directive §16); (3) `checkIndependenceClaims` — for every pair of assignments with no declared
dependency, checks spike C's exact signature (zero dependents-set overlap, `queryDown` default rel
`imports`) plus a direct `queryPath` check in both directions, since a graph path between two
assignments' touched nodes is itself the "hard dependency edge" an independence claim must not
share. `checkDecomposition` composes all three into one report.

`lib/planning/build-work-spec.mjs`'s `buildWorkSpec(rootDir, input)` produces a Work spec scoped
to `rootDir`'s Workspace (`ensureWorkspace`, above) and stamped with advisory Sources/Directives
context — read from the pre-E5-consolidation surfaces `lib/config/source-targets.mjs` and
`lib/directives/directive-config.mjs` already expose (Source/Directive's own target-model.md
domain stores are E5's job, not built yet) — before attaching `checkDecomposition`'s report as
`graphValidation`. `construct work-spec build|check|validate --from=<path|-> [--json] [--strict]`
(`lib/planning/cli.mjs`) is the CLI surface: `build` runs the full Workspace-scoped pipeline,
`check` runs the graph-informed report alone against a caller-supplied spec, `validate` runs the
schema check alone; `--strict` exits 1 when the report is not ok, mirroring `construct graph
validate --strict`.

### Beads projection and field authority (E8)

`lib/tracker-projection/` (construct-b0nny.27, the program's E8 outcome — target-model.md concept
16 "Projection", the *replace* verdict; ADR-0094) reframes `bd`/beads from tracker-of-record to a
*projection* of the graph-informed Work model, without replacing bd or touching `.beads/`: bd
stays the mandatory tracker CLI, the projection layer sits behind it and issues no bd write in
normal operation. `field-authority.mjs` is the reviewed per-field `{domain | tracker}` map — bd
owns its live operational fields (`status`, `assignee`, `owner`, `priority`, `labels`, and the
audit timestamps) while the domain (E1 graph + E3 Work-spec) owns the *derived* edges
(`dependencies`, `parent` — directive §16 "dependencies must derive from the graph, not narrative
intuition") plus the Work-spec what/why (`title`, `description`, `issue_type`). The rule (concept
16 Enforcement): a domain-owned field is never overwritten by the tracker and vice-versa.
`projection.mjs`'s `buildProjection` records that authority per field and preserves the *entire*
original bd issue verbatim in `raw_record` — every field, including model-unused ones
(`dependency_count`, `comment_count`, `created_by`, …). `import-beads.mjs` is read-only relative
to bd (it never calls `bd create`, so it structurally cannot repeat the program's known `bd create
--graph` lossiness), and `verifyRawRecords` proves zero data loss against the source snapshot.
`reconcile.mjs` is ongoing detect-and-report sync, not a one-time import: it diffs live bd against
the durable projections, *absorbing* a tracker-owned change as a legitimate bd update and
*reporting* a domain-owned change as a conflict (`drifted`) rather than clobbering it (concept 16
`projected → reconciling → in_sync → drifted`); `planDependencyProjection` emits the safe per-edge
`bd dep add` write-back plan, never the lossy `--graph` path. `store.mjs` persists projections as
diff-clean JSONL under `.construct/tracker-projections/` (atomic write reused from
`lib/graph/store.mjs`), readable with bd absent (tracker independence, directive §19). `construct
tracker-projection import|reconcile|status [--json] [--strict]` (`lib/tracker-projection/cli.mjs`)
is the CLI surface.

### Cutover verification (E9)

`scripts/verify-cutover.mjs` (construct-b0nny.28, the workspace-control-plane program's terminal
E9 outcome) is the mechanical acceptance gate for the whole program: it re-derives every prior
bead's deletion and completion criteria from the tree on disk and reports pass/fail *per bead*,
rather than trusting the sign-off recorded on each closed bead. Directive §15 singles this bead
out as the only one required to have mechanically verifiable acceptance, so the script — not a
review document — is the deliverable. It covers M0–M5b (flow-engine deletion, identity and
run-store convergence, the governed-write chokepoint, routing consolidation, Oracle-entity
deletion, the org-metaphor migration, the model loop, and the LanceDB de-core) and E1–E9, and
runs as `node scripts/verify-cutover.mjs [--json] [--bead=<id>] [--static-only]`.

Two properties keep it honest. First, criteria are real assertions — file absence, source scans
for live references, package metadata, and spawned CLI invocations — and the source scan is
string-aware, because a glob literal such as `'**/*.test.mjs'` contains `/*` and a naive comment
stripper would silently report zero hits for the rest of that file. Second, a criterion may be
marked *deferred*, which records a documented decision not to delete something and asserts that
its justification still holds: the teams/groups retirement deferral passes only while a live
consumer remains, and fails once the last one disappears, so a deferral cannot decay into rot.
`tests/functional/verify-cutover.functional.test.mjs` plants real violations in an isolated copy
of the tree and asserts the specific bead flips to FAIL while its siblings stay PASS — a verifier
that cannot fail would prove nothing.

The same bead completed the CLI role audit directive §19 calls for: the deprecated `matrix` alias
was removed (ADR-0053 gated removal on two release cycles; the alias shipped in v1.5.0 and six
releases followed), resolving the `graph`/`matrix` name overload the disposition matrix flagged
as A1. `construct graph` is the sole dependency-graph surface.

### Shared workspace server (team/enterprise deployment mode)

`lib/server/` (construct-b0nny.26, E7 — ADR-0093, design doc `shared-server-design.md`) is a
*strictly additive* deployment mode that serves the Workspace domain over a network boundary so
multiple users and worker processes can share one Workspace's state concurrently. It is reachable
only via an explicit `construct server start` with a reachable Postgres `DATABASE_URL`; no
solo-mode code path imports it, and a solo user who never runs it sees zero behavior change (the
SQLite `store.mjs` above is untouched). `lib/server/http.mjs` is a `node:http` façade (no
framework, ADR-0001; the same auth-pipeline shape `lib/mcp/transport/http.mjs` established)
delegating workspace-scoped routes to a Postgres-backed store (`lib/workspace/postgres-store.mjs`,
migration `lib/db/migrations/008_workspace_foundation.sql` — structurally identical tables and
CHECK vocabularies to the SQLite schema, `TEXT → TIMESTAMPTZ` per the domain design's pre-declared
substitution) and to the *unmodified* existing worker-claim primitives (`lib/queue/pg-queue.mjs`,
`lib/orchestration/worker-runtime.mjs`) — the server adds no new concurrency or recovery logic, it
exposes those over HTTP. Auth (`lib/server/auth.mjs`, migration `009_server_tokens.sql`) is
membership-resolved bearer tokens, not a parallel system: only a token's sha256 hash is stored
(raw value returned once at mint), each token resolves to exactly one `construct_workspace_members`
row and grants no authority beyond that row's `owner|member` role, and verification re-joins the
live membership table every request so `removeMember` takes effect on the very next call.
Bootstrap splits an operator secret (`CONSTRUCT_SERVER_ADMIN_TOKEN`, env-only, authorizes only
`POST /workspaces`; `501` when unset, never silently open) from per-member tokens; a token for one
workspace can never reach another's data. Deployment ships `Dockerfile.server` + `docker-compose.yml`
(Postgres + one-shot `migrate` service + server). The concurrent-user and recovery properties are
proven at the server boundary in `tests/functional/workspace-server.functional.test.mjs` (real
binary, real HTTP, real Postgres, a real `SIGKILL`), skipping with a named reason when no Postgres
is reachable.

## Cross-project synthesis

`construct synthesize --ask "<question>" [--projects=all|self|id,...]` (`lib/knowledge/synthesis.mjs`, construct-760c.4) is a map-reduce over the same multi-root corpus `knowledge_search --projects=` and `construct graph build-targets` read (`lib/sources/content-roots.mjs`'s `resolveContentRoots`/`expandProjectsFilter`). **Map**: for each selected project, `buildCorpus()` is filtered to that project's own chunks only and retrieved top-K (default 6) for the ask — retrieval-only, no model call, so this pass is deterministic and free. **Reduce**: the per-project sections (each citing `project:path`) plus a citation table are assembled into one prompt instructing the model to answer using only that context and to cite every cross-project claim by its `project:path` label — a structural no-fabrication constraint, not just an instruction. `--dry-run` stops after the map pass and returns the fully assembled context with zero model output, which is what makes the command deterministic and CI-testable; an unknown project id in `--projects=` is a hard error before any model call. The reduce call shells out to the `claude` CLI (`spawnSync('claude', ['--print', prompt])`); if the CLI is unavailable the command still returns the assembled context, flagged `cliMissing: true`, rather than failing silently.

## Packs

A pack (`lib/packs/`, ADR-0055) is the unit of persona-resolution the provider worker backend trusts: a manifest (`pack.manifest.json`) declaring `id`, `version`, `compatVersion`, and optional `prompts` (specialist id → persona prompt file), `teams`, `frameworks`, `handoffContracts`, `gates`, and `embedBindings` (LMCP-E4: per-specialist provider read/search grants plus a flat list of external-write proposal tokens, cross-checked against the builtin extension manifests so a binding can never grant a capability the referenced provider doesn't itself advertise). `lib/packs/loader.mjs`'s `loadAllPacks()` reads three tiers — builtin (`lib/packs/manifests/`), user (`~/.config/construct/packs/`), project (`.construct/packs/`) — and merges them by id, later tiers overriding earlier ones (project > user > builtin). A programmatically-injected core pack (`lib/packs/core-pack.mjs`) is always present at the builtin tier.

`lib/packs/prompts.mjs`'s `validatePackPrompts()` confirms every declared prompt file exists and carries parseable YAML frontmatter with a `role` field. `resolvePersonaPrompt()` is the *only* path `lib/orchestration/worker.mjs` uses to read a Worker Profile prompt body — it walks the tier-precedence-ordered pack list and returns the first pack declaring the role, with no fallback to reading `registry/worker-profiles/prompts/` directly when a pack declares the override. That is the pack boundary: a Worker Profile's prompt is whatever the pack registry resolves, never an ad hoc file read, so overriding a profile (or shipping a domain-specific one) is a pack-authoring operation, not a core-code change. How the provider worker backend consumes this at runtime — including the solo-mode degraded-fallback path when a pack miss occurs — is covered in the prompt-resolution paragraph under Local orchestration runtime, next.

## Local orchestration runtime (host-independent)

Hosts are front doors; Construct is the system. To stop the best orchestration experience from being coupled to whichever editor exposes native multi-agent execution, Construct owns a local orchestration runtime (`lib/orchestration/runtime.mjs` + `run-store.mjs`), surfaced as `construct orchestrate run|status [--json]`. A run intakes a request, plans a sequenced specialist chain (reusing `orchestration-policy.routeRequest`), resolves the execution-capability contract (`resolveExecution`), persists a durable, resumable run + task lifecycle, and emits lifecycle traces — returning the host-adapter metadata a thin host integration consumes (`executionMode`, `constructCapabilitiesActive`, `workerBackend`, `hostRole`, `degraded`, `selectedProvider`/`selectedModel`, `traceId`).

The runtime has two pluggable axes behind unchanged callers: a worker backend and a run store.

**Worker backends.** The `inline` backend (default) owns planning, sequencing, handoff state,
persistence, and observability and prepares each Assignment (`status='prepared'`,
`executor='inline:prepared'`); it does not itself perform model reasoning. The `provider` backend
(`lib/orchestration/worker.mjs`, selected through `orchestration.workerBackend` or
`executeRun({ workerBackend })`) executes each Assignment through the configured provider/model,
records real output as `task.output`, and records provider failures per Assignment without
crashing the Run. The prepare-only disclaimer applies only to inline Assignments (ADR-0020,
ADR-0021).

**Host execution seat (ADR-0063).** The `host` backend materializes each task's persona/user prompt (`materializeTaskPrompt`, shared with the `provider` backend so both resolve byte-identical prompts) and stops — no model call runs inside Construct. The run stands at a real, non-terminal `awaiting-host` status until the calling MCP host executes each prompt in its own session (its own subscription, not a separate API credential) and reports the result via the `orchestration_task_result` tool; `submitHostTaskResult` records it tagged `provenanceSource: 'host-reported'` (never conflated with a construct-verified `provider` execution) and finalizes the run through the same terminal-status computation the synchronous path uses. `orchestration_run`, reached only via MCP, defaults `worker_backend` to `host` when neither the call nor `construct.config.json` names one explicitly — the CLI's own default stays `inline` and fails loud on `--worker-backend=host` (no attached host session to execute against). A stale `awaiting-host` run (host disconnected mid-run) is a doctor advisory, not a silent failure. Phase 2 drives the identical loop server-side via MCP sampling when the connected client declares that capability.

**Handoff context (`buildUserPrompt`, `lib/orchestration/worker.mjs`).** A downstream task's user prompt folds in every prior task's real output (`status:'done'`, non-empty `task.output`) under a `## Prior specialist results` section, wrapped by `lib/security/trust.mjs`'s `wrapUntrusted` — a provider-verified upstream task at `team-authored` trust, a host-reported one (`provenanceSource: 'host-reported'`) at the lower `external-authenticated` level — so the receiving specialist evaluates it as data, not instructions. Budgeted at 1200 chars/task, 6000 total, nearest-preceding task prioritized. Because `materializeTaskPrompt` is shared, provider and host runs resolve byte-identical prompts for the same task; on the host backend, `submitHostTaskResult` re-materializes the next `awaiting-host` task's prompt immediately after recording a result, since `executeRun` originally materialized every task's prompt in one pass before any host result existed.

**Prompt resolution and the pack boundary (LMCP-E2).** The provider backend resolves each Worker Profile prompt ONLY through the pack registry (`lib/packs/loader.mjs` + `lib/packs/prompts.mjs`), falling back to `registry/worker-profiles/prompts/<id>.md` only when no pack declares an override. Pack load validates every declared prompt file and its YAML frontmatter (`validatePackPrompts`); in team/enterprise deployment mode a missing or malformed prompt is a hard load-time error naming the file, and a run can never execute a Worker Profile under a silently substituted prompt (`PERSONA_UNAVAILABLE` if a miss somehow still reaches the worker). Solo mode does not hard-fail at load time — a miss there degrades visibly: the task result and the `worker.completed` trace event carry `personaAvailable: false` and `degraded: 'persona-fallback'`, and the run's terminal status becomes `degraded` rather than a bare `completed`. `construct status` surfaces a `personaDegradedRuns` count from `.construct/runtime/orchestration/runs/`.

**Governed web capability (ADR-0050).** A specialist that declares `liveWebAccess: true` (the researcher) executes with a live web tool instead of a tool-less completion, closing the seam where the orchestrator promised "web access lives with the researcher" but nothing wired it. A typed `resolveWebCapability` grant runs in strict priority — `governed` (`WEB_SEARCH_URL` → a client tool-use loop over Construct's own `webSearch()`, F08 by construction), `provider-native` (Anthropic `web_search_20250305` / OpenRouter `openrouter:web_search`, every citation re-graded), `host-delegated` (opt-in), `unavailable` (typed `capability-unavailable` forcing an honest refusal that degrades the run). `governWebResults` (`lib/mcp/tools/web-search-governance.mjs`) is the single grader: every web result on every path — including the fail-closed re-grade on remote-service ingress — emerges `trust:'untrusted'` + Admiralty-graded, so a citation can never reach a specialist ungoverned. The tool is least-privilege (only the declared web role gets it) and bounded (`CONSTRUCT_WORKER_TOOL_ROUNDS`).

**Run stores.** `resolveRunStore` (`lib/orchestration/store.mjs`) returns one `{ saveRun, loadRun, listRuns }` interface over three backends: **Mode-A** filesystem (zero-dependency default, `.construct/runtime/orchestration/runs/`, no Docker), **Mode-B** SQLite (`run-store-sqlite.mjs`, lazy `node:sqlite` with `sqliteAvailable()` — falls back on Node older than 22.5), and **Mode-C** Postgres (`run-store-postgres.mjs`, shared team/enterprise store). Selection follows `orchestration.store` config / `CONSTRUCT_ORCHESTRATION_STORE` env override, else deployment mode (solo→filesystem, team/enterprise→postgres), resolving explicit storage backends through `kind:"storage"` manifests and degrading to filesystem with visible `requestedBackend`/`degradedReason` metadata when unavailable. Postgres uses the optional `postgres` SQL client only when `DATABASE_URL`/`CONSTRUCT_DATABASE_URL` is configured; `construct db status|migrate` probes and applies repo-owned migrations idempotently. Filesystem + inline is the byte-for-byte-unchanged default. Decisions recorded in ADR-0020 and ADR-0021 (extending ADR-0019).

**Unified build-audit record (construct-ifwhw.1).** The run store, lifecycle traces, and the contract-violation log were three parallel durable records with no object linking them by runId. `lib/orchestration/build-audit-record.mjs`'s `buildAuditRecord(cwd, runId)` joins a run's task chain (`run-store.mjs`), its lifecycle trace events (`lib/worker/trace.mjs`'s `readTraceEventsForRun`, matched on `metadata.runId`), and any contract violations its tasks triggered (`lib/contracts/violation-log.mjs`'s `recentViolations({ runId })`, now that `lib/orchestration/worker.mjs` threads `run.runId` into its `logViolation` calls) into one object. `materializeAuditRecord`/`loadAuditRecord` persist and read it back cross-process at `<stateRoot>/runtime/orchestration/audit-records/<runId>.json`, the same atomic write pattern as `run-store.mjs`. Per-task artifact/postcondition linkage rides along when a task's `outputPacket.artifactPath` names an authored doc; today no orchestration task populates that field, so the array is honestly empty rather than fabricated — it is the insertion point for a future artifact-authoring producer, not a claim that one exists yet.

**Artifact provenance.** `runConstructArtifactLoop` writes an observation independently of whether an artifact is materialized, so a `.construct/observations/<id>.json` record remains available either way.

**Postgres queue provider.** `PostgresIntakeQueue` (`lib/queue/pg-queue.mjs`) is the team/enterprise default `kind:"queue"` provider and can also be selected explicitly with `CONSTRUCT_INTAKE_QUEUE_BACKEND=postgres` or an equivalent manifest override. It stores queue items and claim history in migration-owned tables, claims with `SELECT ... FOR UPDATE SKIP LOCKED`, increments attempts on each claim, renews leases through `heartbeat()`, and reclaims expired claims without double-claiming live work. `fail()` applies retry/backoff policy and dead-letters maxed attempts, `requestCancellation()` makes cancellation visible at heartbeat boundaries, `markProcessed(...executionKey)` is idempotent for re-delivery, and `queueStats()` is the operator read model for pending/claimed/dead-letter depth. A missing SQL client in team/enterprise mode is a hard configuration error unless `CONSTRUCT_DEGRADED_OK=postgres-queue` is set; that override returns a visibly degraded git-backed queue.

**Worker heartbeat registry.** Team and enterprise workers register liveness in the migration-owned `construct_workers` table through `WorkerRegistry` (`lib/orchestration/worker-runtime.mjs`). `register()` creates or refreshes a worker identity with capabilities and TTL, `heartbeat()` renews liveness, `deregister()` marks a worker stopped, and `construct workers list [--json]` reports active, stale, and stopped workers when Postgres is configured.

**Team health surfaces.** `lib/team/health.mjs` joins `PostgresIntakeQueue.queueStats()` with `WorkerRegistry.list()` so `construct status` and `construct doctor` report queue depth, dead-letter depth, active workers, and stale workers from the same read model. In team/enterprise mode, a missing Postgres client is a doctor failure; DLQ entries and stale workers are visible degraded states. `dev/team-harness/verify.sh` is the local verification entry point for a configured team database.

**Engine-as-service.** The runtime is reachable so hosts can be thin clients — the pattern Claude Code, OpenCode, and Goose all use to deliver multi-agent inside editors that have no native subagent primitive (the editor's missing primitive is immaterial when the engine owns the loop). Orchestration runs **in-process** by default (`lib/orchestration/runtime.mjs`): the `orchestration_run`/`orchestration_status` MCP tools and `construct orchestrate run|status` drive it directly — no daemon, no port, no token for the solo default. A remote orchestration service stays opt-in via `CONSTRUCT_ORCHESTRATION_URL` (bearer token from `CONSTRUCT_ORCHESTRATION_TOKEN`); `construct orchestrate run|status --remote` is the reference thin client, and a VS Code/Copilot extension, OpenCode, or CI drives the same API. Responses use the versioned, secret-free embedded-contract envelope. Decision: ADR-0022.

## Approval model

Hybrid: autonomous for low-risk, human-gated for high-risk.

| Risk | Examples | Behavior |
|---|---|---|
| Low | Reading, analysis, draft generation, search | Autonomous |
| High | Work item creation, merge, doc publish, config changes | Queued for approval (messaging provider or `construct oracle`) |

### Governed-write chokepoint

`lib/writes/control-plane.mjs` is the sole path from a queued writeIntent to an executed
external write. A specialist only ever *recommends* a write (`lib/writes/write-intent.mjs`);
the durable `ApprovalQueue` (`lib/embed/approval-queue.mjs`) holds it in state
`awaiting_approval`; a human or policy actor decides out of band; and only
`control-plane.mjs`'s `executeApprovedWriteIntent`/`drainApprovedWriteIntents` resolve a
governed adapter and call `lib/writes/envelope.mjs`'s `writeWithEnvelope()` for a record
already `approved` — idempotency key, sent-log dedup, retry, and audit all live in that one
envelope call.

Every authority decision behind this chokepoint — a provider-write approval reaching
execution, an MCP destructive-tool approval-token issuance/consumption
(`lib/mcp/destructive-gate.mjs` + `destructive-approval.mjs`), or a role-fence action that
needed human visibility (`lib/hooks/edit-guard.mjs`, `guard-bash.mjs`,
`lib/embedded-contract/workflow-invoke.mjs`) — is appended to one shared JSONL ledger,
`lib/writes/authority-ledger.mjs`. This formalizes what was previously three separate
recorders (the ApprovalQueue itself, `mcp/destructive-approval.mjs`'s own token store, and
`lib/roles/approval-surface.mjs`'s pending-approval log) into a single auditable authority
store; `roles/approval-surface.mjs` is deleted, its three consumers now call
`recordApprovalNotice` from the ledger module directly.

### Sources / directives / workplace loop

`lib/workplace-loop/` (construct-b0nny.25, the workspace-control-plane program's E5 outcome —
`docs/notes/research/workspace-control-plane/synthesis/target-model.md` concept 4 and spike D,
`spike-d-daily-workplace-loop.md`) is the production generalization of spike D's proven
`detect → normalize → align → filter → gate → verify` pipeline from a fixture-driven proof into a
loop over a real connected source. `runDetect` (`detect.mjs`) fetches open issues from a real
GitHub source (`sources/github-source.mjs`, reusing `lib/providers/github/index.mjs`'s read-only
`search()` — the repo defaults to the checkout's own `git remote get-url origin`, never a
fabricated stand-in), fingerprints the normalized record set (`fingerprint.mjs`), and
short-circuits to `NOTHING_NEW` when the fingerprint is unchanged since the last run — the
no-fabrication guarantee spike D proved, now against live data: an unchanged source advances no
run counter and mints no proposal. On genuinely new content, rule-based detectors (`signals.mjs`:
stale issues by date math, unowned risk-labeled issues by label pattern, noise by absence of
substantive signal) run over *structural* properties of a real issue record rather than
ground-truth flags baked into a fixture — the part of the pipeline this bead exists to stress,
per spike D's own caveat that rule-based detection over a legible fixture does not prove judgment
over messy real data. Signals are aligned against the Workspace's real strategy pillars
(`align.mjs`, read from E2's `workplaceLoop.strategyPillars` setting key on `lib/workspace/store.mjs`;
absent pillars yield `no_strategy_configured`, never a fabricated conflict), and actionable
signals become a durable proposal (`propose.mjs`/`state-store.mjs`) whose external effects are
writeIntent-shaped.

Every external effect routes through the M2 chokepoint above, with no bypass: `gate.mjs`'s
`requestApproval` enqueues each proposed effect onto the same durable `ApprovalQueue`, `approveAll`
refuses without a named approver, and `applyProposal` refuses any partially- or un-approved
proposal before draining approved effects through `control-plane.mjs`'s `drainApprovedWriteIntents`
— the loop owns no second approval or execution mechanism. `construct workplace-loop
detect|request-approval|approve|apply|verify` (`cli.mjs`) is the CLI surface.

`lib/workplace-loop/directive-executor.mjs` is the E5 home for directive execution: it reproduces
`lib/oracle/directive-executor.mjs`'s behavior contract exactly — same budget-gating discipline
(`lib/policy/unattended-budget.mjs`), same `runTaskViaProvider` execution path, same
enqueue-only-never-execute boundary, same `CONSTRUCT_ORACLE_EXECUTE_DIRECTIVES` /
`oracle.executeDirectives` opt-in surface — differing only in the `surface` provenance tag on an
enqueued record (`workplace-loop-directive` vs `oracle-directive`). As of `construct-b0nny.17`,
`lib/oracle/execute.mjs`'s `directive-due` case calls this module, so directive execution runs
under E5, not the (now-deleted) Oracle daemon;
`tests/workplace-loop/directive-executor-equivalence.test.mjs` pins that the cutover changed no
observable behavior. The Oracle-local copy is intentionally kept as the behavioral rollback
reference the equivalence suite compares against, so re-selecting it is a one-line revert.

## Policy enforcement. three layers

Policy rules (comment convention, doc-update requirement, CI green before walk-away, branch hygiene) are enforced at three layers so violations cannot fall through the cracks. Quality gates fire unconditionally — no skip env vars on blocking checks. If a gate fires wrong, repair the policy at its source.

**Layer 1. Real-time (write/edit time).** Catches at the source.

- `comment-lint.mjs`. PostToolUse Write/Edit/MultiEdit, **blocking**. Banned patterns and missing required headers exit 2. No bypass — fix the comment or fix the policy in `lib/comment-lint.mjs`.
- `artifact-release-gate.mjs`. PostToolUse Write/Edit/MultiEdit, **advisory**. Surfaces manifest structure/visual gaps on typed docs under `docs/**` and `.construct/research/**`; full gate via `construct artifact validate`. Artifacts may declare `cx_release_gate: bypass` with `cx_release_gate_reason` — Oracle read model surfaces these for review.
- `doc-coupling-check.mjs`. PostToolUse, advisory. Counts code-file edits per session, prints stderr nudge at 3/5/10 when no doc files touched. Soft predecessor to the commit gate.
- `ci-status-check.mjs`. UserPromptSubmit. Queries `gh run list` (60s cache) and injects red-CI status into agent observation.

**Layer 2. Gate (commit/push time).** Catches at the boundary.

- `.beads/hooks/pre-commit` Construct policy section. calls `construct lint:comments` and `construct docs:verify` across the current worktree. Refuses commits with banned-pattern violations or code-without-docs.
- `pre-push-gate.mjs`. refuses `claude/*` branch pushes unconditionally; blocks re-pushing the exact SHA CI most recently rejected (SHA-aware: if HEAD has advanced past the failed commit, push goes through with a non-blocking notice); lints PR body on `gh pr create` / `gh pr edit` against template policy. Tests, build, audit, evals, and every `lint:*` live in `.github/workflows/ci.yml`, not in this hook.

**Layer 3. Safety net (CI + session end).** Catches escapees.

- `policy-engine.mjs` Stop handler (consolidated):
  - **red-CI block**. exits 2 when CI is red on the current branch and the agent edited code this session. Bypass: `CONSTRUCT_STOP_OK_RED_CI=1`.
  - **open-beads block**. exits 2 when `bd list --status in_progress` returns any issue. Bypass: `CONSTRUCT_STOP_OK_OPEN_BD=1`.
  - **drive criteria enforcement**. blocks Stop when drive mode is active and acceptance criteria lack evidence.
  - **drive-session advisory**. non-blocking surface of open `~/.construct/drive-session.json`.
- `construct doctor`. phantom-hook drift check; refuses to pass when `settings.template.json` registers a hook whose file is missing. Prevents the failure mode where defenses look wired up but silently no-op.

CI is the outermost safety net. Required status checks on `main` and `dev` (`retrieval evals`, `comment policy`, `docs drift check`, `dependency CVE audit`) prevent merges when any layer's escape made it to a PR.

## Context hygiene

Enforced via hooks, not advisory text:

- `bash-output-logger`. persists large outputs to disk, nudges grep over re-run
- `context-watch`. compaction guidance at 60%/80% of resolved context window
- Role skills loaded on demand via `get_skill`

## Session persistence

Distilled, not raw. Sessions store summary, decisions, files changed, open questions, and task snapshot. Full transcripts are ephemeral.

**Tiered injection at session start:**

| Tier | Behavior | Examples |
|---|---|---|
| 1 | Always injected | header, branch, status, approval reminder |
| 2 | When fresh and meaningful | context.md, skill-scope warnings, last-session resume |
| 3 | Hint pointing at MCP tool | prior observations → `memory_recent` |

## Learning loop

Observations (patterns, decisions, anti-patterns) are recorded per-role, vectorized for semantic search, and capped for bounded storage. Entities track recurring components, services, and dependencies. Session artifacts are captured automatically at session end.

## Key invariants

- Construct is the only public surface. Worker Profiles are internal execution configuration.
- Provider implementations never leak transport details into core.
- External tracker state is canonical for durable work when present.
- Single-writer rule governs parallel editing.
- Mutations are traceable via audit trail with tamper-evidence chain.
- Domain overlays must not auto-promote into permanent capabilities.
- Deployment mode selects backends; the agent loop is identical across solo / team / enterprise.
- Classification runs deterministically in the daemon; the agent does the LLM analysis.
- Task graph nodes cannot transition to `done` without an evidence record.
- Every MCP tool call emits a `tool.called` trace event; denials are typed errors. (Brokered MCP dispatch — for team/enterprise `mcp-broker` routing — is staged/experimental (tracked: construct-9oi4.10); the trace contract will apply when that path is active.)

## Worker Profiles

Worker Profiles are assignable configurations. Each declares a runtime/model tier, Skill
emphasis, Procedure affinity, and Policy fence. Construct selects them from an Assignment's
requirements; they do not appear as separate public assistants.

The canonical owner is `registry/worker-profiles/<id>.json` with prompt bodies under
`registry/worker-profiles/prompts/`. Loaders live in `lib/worker-profiles/` and
`lib/registry/loader.mjs`. The exact current-to-canonical mapping is in
`config/canonical-terminology.json`.

### User-defined Worker Profiles

User-defined Profiles follow the same schema and validation as built-ins. Project packs
(`.construct/packs/`) have higher precedence than user packs (`~/.config/construct/packs/`),
which have higher precedence than built-ins; resolution must report the winning source. A
Profile may reference existing Skills, Procedures, Capabilities, and Policies, but must not
duplicate their content or bypass their gates. Use `construct pack list|enable|info` to inspect
and enable project-tier packs.

### Headhunt: domain-overlay activation and promotion

`construct headhunt <domain>` (`lib/headhunt.mjs`) attaches a temporary domain-expertise overlay to the workers named by the request or selected by deterministic keyword buckets. It does not invent permanent Worker Profiles or derive a fixed roster from the active Workspace Preset. An overlay defaults to `permanence: 'temporary'` with a 7-day `expiresAt`; `--save` makes it durable and `construct headhunt cleanup` removes expired records. Overlay and promotion records live at `.construct/domain-overlays/` and `.construct/promotion-requests/`.

Promotion (`construct headhunt promote <overlay-id>`) does not write directly into `registry/**` — it creates a `promotion-request` record carrying the overlay's domain/objective/scope and a fixed checklist (`buildPromotionGates()`: explicit user request, demonstrated reuse beyond one-off use, clear scope and owner, fits existing routing, security review if the domain touches infra/auth/data, docs and validation plan before any persistent registry change). Promotion is deliberately a paper trail requiring human review, not an automatic escalation — a domain overlay earns a permanent Skill or Worker Profile only after a maintainer acts on the request through the normal pack and registry authoring paths.

Full roster with tier and purpose per profile: [Worker Profiles reference](/guides/reference/worker-profiles).
