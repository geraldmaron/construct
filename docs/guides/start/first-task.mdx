## Pick a project

```bash
cd ~/code/your-project
```

It needs to be a git repo (Construct uses `.git/` to wire pre-commit hooks). If it is not one yet, `construct init --yes` runs `git init` for you; use `construct init --interactive` to confirm first.

## Initialize Construct in the project

```bash
construct init --yes
```

One command does all of it:

- Scaffolds the project — `.construct/context.md` and `.construct/context.json` (durable per-project state Construct reads at session start), `.construct/handoffs/` (gitignored, session handoffs land here), a minimal `docs/` folder (index only — no guessed doc types). Init may also create a local Beads issue-tracker directory for later multi-session work — you do **not** need to file beads, triage intake, or declare graph change-intent before the first coding task (see [durable state →](/guides/concepts/beads-and-state) when you want that depth).
- Syncs a lean project adapter set — Claude Code under `.claude/` by default (plus any host already configured in the project). It does **not** scaffold every editor CLI on your PATH. Opt into more with `construct init --with-<host>` / `--all-hosts`, or later `construct sync --with-<host>`.
- Starts the local runtime by default — local dashboard at `http://localhost:<port>` (port auto-selected), memory MCP server at `127.0.0.1:8765`, local trace capture in `~/.construct/projects/<key>/traces/*.jsonl`. Pass `--no-start` to skip service startup, or `--interactive` for the guided flow.

Hard gates (secrets, tests, docs) still apply on commit. Progressive disclosure keeps Beads, intake, and graph as power surfaces — not day-1 ceremony ([NN/g](https://www.nngroup.com/articles/progressive-disclosure/)).

### Documentation packs (optional)

`init --yes` does **not** auto-pick ADRs, PRDs, RFCs, or other lanes. When you want starter templates:

```bash
construct init --yes --docs-preset=lean    # ADRs, memos, meetings, notes, PRDs
construct init --yes --with-adrs --with-rfcs
construct init --interactive               # Packs / Individual docs / Skip menu
```

Re-running `construct init` on an existing project is safe; it's idempotent. Re-run `construct sync` on its own any time you only need to refresh adapters (after a registry, prompt, or config change), and `construct dev` on its own any time you only need to (re)start services without touching adapters.

## Dispatch a task

Open your editor. Two modes depending on the request:

<Cards>
<Card title="Simple ask" href="/guides/reference/worker-profiles">
Address `@construct` directly. The public Worker Profile answers without a full Assignment chain.

```
@construct read the README and summarize what this project is.
```

Good for: questions, summaries, small lookups, one-file changes.
</Card>
<Card title="Involved work" href="/guides/concepts/architecture">
Construct routes through the Worker Profile chain: architect → researcher → reviewer → security.

```
@construct review the auth flow in src/auth/ and flag risks.
```

Good for: code review, architectural decisions, security-sensitive changes, PRDs.
</Card>
</Cards>

### Confirm Worker Profiles will actually run

Both dispatch paths above route through Worker Profiles — but a profile chain only runs a real LLM (**EXECUTE**) when a provider is attached; otherwise it only prepares prompts (**PLAN**) and returns no reasoned output. `construct init` printed a line telling you which one you're in:

```
Worker Profiles will EXECUTE (provider <family> + key found)
Worker Profiles will only PLAN (fix: set orchestration.workerBackend=provider + a key)
```

If you're in Claude Code or OpenCode, a host session is already attached, so profiles EXECUTE with no extra setup. On any other host (Codex, Copilot, VS Code, Cursor), or if you want Claude Code to use a specific provider model instead of the host's own, set `orchestration.workerBackend: "provider"` in `construct.config.json` and export a materialized provider key (`ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, or `OPENAI_API_KEY`). Rerun `construct doctor` and check the last line before trusting profile output. See [install → EXECUTE vs PLAN](/guides/start/install#execute-vs-plan-do-worker-profiles-actually-run-an-llm).

## When you need more (opt-in)

Everything above is enough to write code with `@construct`. Reach for these only when the work shape needs them:

| Need | Surface | Guide |
|---|---|---|
| Work arrives as a file (bug report, paste, dump) | `inbox/` + `construct intake` | [Intake and triage →](/guides/concepts/intake-and-triage) |
| Multi-session tracking, blockers, audit trail | Beads (`bd` / `construct beads`) | [Beads and state →](/guides/concepts/beads-and-state) |
| Per-signal execution plan from a triaged packet | `construct graph from-intake <id>` | [Intake and triage →](/guides/concepts/intake-and-triage) |
| Pre-change impact packet (large refactors / dogfood) | `construct graph intent declare` | [CLI / graph →](/guides/reference/cli) |

None of these are required to clear a pending intake queue or declare graph intent before a normal chat coding task.

## What just happened

Construct's public Worker Profile [held the conversation](/guides/reference/worker-profiles), but behind the scenes it [routed work through internal profiles](/guides/concepts/architecture) and [enforced policy gates](/guides/concepts/gates-and-enforcement) on any mutations. Session state was persisted to `.construct/context.md` so the next session resumes mid-flight.
