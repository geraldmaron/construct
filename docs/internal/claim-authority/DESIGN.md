# One claim authority for managed delivery

As of 2026-10-17. Design prerequisite for `work-0a36e600`; related tool-surface work: `work-4503dc02`. This is a design decision, not an implemented or experimentally validated change. The adversarial review below is self-review, with shared context and no independent native semantic verification. The managed authoring run reported that no supported native reviewer was bound.

## Decision and scope

Choose **A: collapse the two authorities into one stored claim record**. Retain the per-run delivery work item as durable purpose, history and an address hosts can inspect; remove its independent claim authority and the step's independently stored lease. Both become views of the same claim. Path rows describe the scope of that claim and carry no second credential or clock.

The claim has execution and custody phases. Completing a step ends its execution authority, but can retain custody of the artifact until the next step is claimed, the single term expires, or the run pauses or ends. This is necessary to preserve the existing inter-step reservation: a step's success does not mean the next writer may take the artifact.

Do not unify workflow execution with admission of ordinary ledger work. Both use the same claim machinery, but a ledger claim still grants no workflow step, capability or approval. Do not rename all tools or shorten their descriptions as part of the storage change. This note settles their roles and compatibility path; host behavior changes retain §41(4)'s separate live-evaluation gate, which was not run for this task.

## Current split: failures and existing defenses

The following distinguishes observed defects, code-derived failure sequences and limitations. The existing outer claim/submit transactions already prevent several partial-write failures; replacing them with eventual cleanup would regress safety.

1. **Cancelled delivery work remains executable-looking forever (observed, user report dated 2026-10-17).** Two runs cancelled on 2026-10-15 left their `work-<run>-delivery` items open indefinitely. CLI cancellation does not invoke the broker helper. Even when the helper is invoked, failure/cancellation uses `releaseWork`, which sets status back to `open`, rather than terminalizing the synthetic work. The observation does not establish an indefinitely live path lock: `liveRows` stops exclusion at `claim_until`. It establishes indefinitely open ledger debt and misleading readiness/history.
2. **Cancel waits on an expired lease (observed historical defect, already fixed).** Main's `c1ac4356cfb624ae817ee6cd33c9b1173d5d5020` reaps dead leases before checking after-step cancellation. This worktree includes the behavior in `9c44837c`; the service diff against `c1ac4356` is empty. Preserve `tests/kernel/workflow/service.test.ts`'s expired-holder cancellation intent. That fix does not settle the delivery work item.
3. **Settlement depends on who happens to call next (read).** `settleManagedDelivery` returns unless the item is still claimed by this session/agent owner. A cancel, fail, or no-packet claim by another session therefore cannot reconcile it. A terminal run can have a still-claimed or subsequently open synthetic item. A generic later claim can reacquire that item without acquiring any step.
4. **Two clocks can separate execution from exclusion (read/inferred).** An explicit heartbeat renews only the step. MCP courtesy renewal often renews both but does so by different identities and calls; direct broker/service callers lack that wrapper. Work renewal uses MAX to preserve a longer term. A step can outlive the path claim, allowing another claim on its file, or an idle/finished step can leave a longer path hold. Courtesy renewal can keep an orphaned delivery claim alive while its session performs unrelated work.
5. **Two transfer policies can separate holders (read/inferred).** Ordinary work takeover permits quiet-session recovery, parent-agent reclamation and reservation transfer; managed recovery requires observed ended/dead evidence before early step expiry. A work handoff moves no step lease or approval. Generic takeover/accept/release can therefore move or free the artifact while an old executable step still exists, or leave an acceptor unable to resume until a different authority expires. The hidden delivery secret makes the host dependent on broker-specific recovery.
6. **Paused, failed and terminal states differ by entry point (read).** In this baseline the helper handles succeeded, failed, cancelled, blocked **and waiting_for_decision**, not only failed/cancelled. Success is separately guarded by current execution evidence. A no-packet interactive claim sometimes settles; a headless claim does not; direct service failure/cancellation/resume/expiry and executor cleanup do not settle delivery. Expiry accounting and run advancement can be correct while the ledger still disagrees.
7. **A repair can create a more serious regression (inferred).** Sweeping all apparently stale delivery items by age can erase an explicit handoff or enable replay of a prior writing/action attempt. Existing recovery deliberately requires exact artifact, checkout, newer manual request, matching frozen workflow, kernel admission, no action/write history, no existing/unreadable artifact, no children and no handoff. Preserve those predicates, not only the happy-path reclaim.
8. **Worktree, alias and conservative scope mismatches (read/inferred).** Ledger transfers can move custody to a different checkout or drop conflicting inherited paths while execution still resolves through its former checkout. Files with spaces may reserve a directory or `/`; equating that scope with exact artifact identity can supersede a different artifact. Root scopes collide across lanes; narrower overlaps are merge risks. A pure lexical replacement can miss symlink/hardlink/case/Unicode aliases. Existing validators prevent many of these acquisitions today.
9. **Two tokens are conceptually different but look like one operation (read).** A step nonce authenticates execution; a work token authenticates custody; path tokens are another stored random value unused for authorization by the overlap reader. Guessing an attempt number, reading metadata, copying a handoff packet or presenting the wrong token must never settle either generation. Three claim verbs and divergent interactive/headless error packets make recovery harder for hosts.
10. **Independent metadata repair or migration can silently widen authority (inferred).** Choosing the longest of two disagreeing expiries, the latest of two owners, or an item with the right ID but wrong admission can make an old writer current. Multiple ready DAG steps can be leased by repeated claims; the per-run delivery record cannot express distinct concurrent step holders safely. Restoring a snapshot must not restore credentials. A partial upgrade or an old live writer can reintroduce the split.

No claim here establishes that a compliant claim can fence arbitrary filesystem writes by an old process. Both options fence kernel submissions and coordinate compliant hosts; neither is an operating-system file lock.

## Options under the required cases

### A. One stored authority, with execution and custody phases

Steelman: put owner, credential, expiry, generation, active-step binding and edit lane in one canonical record. Workflow and ledger operations call the same transaction boundary; a finished or cancelled run cannot leave another independently renewable delivery claim. Preserve the work item and events as durable history, and the existing path engine as the only overlap algorithm.

| Case | Failure if A is implemented carelessly | Required behavior/control |
| --- | --- | --- |
| Path-overlap refusal | Acquiring a step before committing its path rows exposes execution without exclusion; excluding all claims by the same owner hides a second writer | Gate, acquire, reserve, attempt/event writes in one `BEGIN IMMEDIATE` transaction. On any conflict roll back everything, including attempt count and supersession. Exclude only the exact authority being renewed; reuse the existing overlap/alias engine |
| Dead-session recovery | Treating a quiet editor as dead invalidates its running step; unbounded retries spend nothing and loop | Managed early recovery still needs observed end/death, unknown waits for expiry, and expiry allowance remains separate from failed-validation budget. Ordinary ledger-only quiet/parent-agent takeover remains supported. Recovery rotates the single credential and keeps finished steps/output |
| Handoff/takeover | Transferring a live executable step carries approvals; accepting custody with dropped paths accidentally grants writing | For managed work, offering ends the executable attempt as paused, preserves checkpoint/history and changes the same authority to offered custody. Acceptance rotates its credential, transfers only actual reservations, and grants no executable step. A subsequent claim re-gates under the recipient executor. If required paths were dropped, return them and refuse execution until reacquired |
| Worktree lanes | Moving authority without moving evidence resolution writes one checkout and verifies another | Store lane/branch with the authority, validate known lanes and inherited paths, keep normal cross-lane merge-risk/refuse behavior and root exception. Explicit renewal into a conflicting lane rolls back; handoff/takeover drops collisions as today. Reclaiming execution must resolve/checkpoint the artifact in the new lane |
| Three claim verbs | Collapsing storage becomes a tokenless bypass through `work claim`, or headless callers get interactive powers | Workflow acquisition is one gated operation; interactive and headless entry points share it under their existing capability bindings. Ordinary `work action=claim` remains ledger-only. Managed item mutation dispatches to the run-aware authority path; it cannot manufacture a step |
| In-flight state migration | An old nonce or maximum expiry resurrects authority; parallel step leases cannot fit one active binding | Explicit format upgrade, stopped holders, backup and fenced reissue policy below. Abort ambiguous migration rather than pick a writer |
| Host surface | Host sees two secrets or treats custody as permission to write | One execution token in a successful workflow packet, one term, explicit delivery phase/path/lane. Public work/status/coordination views hide secret; custody packets explicitly require a fresh workflow claim |
| Gap between steps | Ending the claim on every successful step lets another writer acquire between write and verification | Keep the same stored authority and expiry in custody with no active executable step. Next claim rotates its credential and binds the next attempt after gates. Pauses that currently release custody continue to release it |

The tradeoff is an explicit migration and shared storage change. A managed run with one artifact must serialize its executable steps at this authority; same-owner calls are not an exemption. Non-artifact workflows may retain parallel independent steps. Do not silently choose one active step when upgrading an already parallel artifact run.

### B. Ledger reservation as a pure projection of the step lease

Steelman: leave execution's nonce/expiry where it is and derive a virtual delivery work row and virtual path reservation from the run destination and current leased step. With no second credential or independently mutable claim, cancellation and expiry automatically remove the projection; ordinary work can retain its present ledger machinery. There is less new lease mutation code to get wrong.

| Case | Failure mode of the strongest pure projection |
| --- | --- |
| Path-overlap refusal | Every ordinary work acquisition, managed claim, check, hook and awareness query must consume the union of stored ordinary reservations and projected step reservations under the same write lock. Updating only broker claim packets makes ordinary `work claim` blind to managed writers. Deriving scope/aliases after commit is too late |
| Dead-session recovery | Early expiry must update the step authority; an omitted session binding can make a live headless executor look orphaned. The existing observed-death/unknown distinction and bounded expiry accounting still apply. Projection removes duplicate cleanup, not recovery policy |
| Handoff/takeover | Ordinary handoff currently extends a custody hold and transfers no step lease. A live-step projection has nowhere to hold an offer after execution stops. Moving the step transfers execution implicitly; keeping a separate offer expiry restores a second authority. Storing custody state on a step can work, but that is a unified stored authority with new lifecycle semantics, effectively A |
| Worktree lanes | The step currently lacks the reservation's lane/branch/agent and exact-versus-conservative path metadata. Deriving from the session's current lane changes old claims when a session moves; retaining it only in events makes all reads depend on correct event-generation reconstruction. Persisting it on the step is a format change, contrary to §41(2)'s tentative no-format-change advantage |
| Three claim verbs | Both workflow verbs can share acquisition, but virtual delivery IDs must reject or route work mutations. Supporting generic handoff/release/takeover as independent writes would break purity. Hosts need typed recovery rather than apparent success on a virtual item |
| In-flight migration | Keeping old stored delivery work while adding projections double-counts reservations or leaves old claims renewable. At minimum retire/fence the old authority and define how references, offers, paths and pending acceptance receipts survive. A no-DDL rollout still changes persistent meaning; use an explicit format fence to stop old writers |
| Host surface | Virtual work show/list/ready, coordination, hooks, export/restore and history must agree on stable identity and expired/terminal status. Reconstructing only `delivery` in a claim packet yields invisible holds to other hosts |
| Gap between steps | After submission clears the step owner/term, no leased step exists to project. Exclusion vanishes between drafting, writing and verification. Projecting the latest attempt's historical expiry invents live authority from completed history; handoff holds can outlast it. Reserving through the next unclaimed step invents a holder and credential |

**Reject B for this requirement set.** It is viable only if the product deliberately gives up custody between steps and independent handoff holds, or adds a stored custody phase to its step authority. The former loses present behavior; the latter concedes A's central data model and migration cost. A projection is appropriate for public reads of the chosen authority, not as a substitute for modelling its whole lifetime.

## Proposed single-record contract

All names in this section are proposed. Introduce `work_claims` as the single reusable claim store, distinct from the existing graph `claims` table. Move authority code from the existing work/step implementations into `src/kernel/work/authority.ts`; extend those implementations as adapters rather than retaining a second lease engine. No dependency is needed.

One row has:

- `id`; `kind` = `work`, `managed_delivery` or `step`; nullable `work_id`, `run_id`, `subject_step_id`; uniqueness by the relevant subject. A managed delivery row has its stable delivery work ID and run ID. A non-delivery workflow uses one row per executable step, preserving DAG concurrency. An ordinary ledger claim has its work ID. A managed delivery is never also given a step-kind row.
- `phase` = `executing`, `custody`, `offered` or `released`; `generation`; private `nonce`; `owner`, `executor_id`, `session_id`, `agent`; `lane_root`, `branch`; `until`, `touched_at`; nullable `active_step_id`, `active_attempt`; creation/update and release reason/time. Work custody has no active step; executable claims bind one exact step and attempt. Released claims have no capability, live owner or deadline. Ownership/executor fields are kernel-bound, not caller-selected identity strings.
- Keep the bounded handoff packet and immutable offer identity on durable work metadata, and the existing hashed acceptance receipt in history. They describe an offer but grant no separate lease. Its hold ends at this row's `until`. Only `phase='offered'` with the matching row generation makes the offer live.

Enforce subject/kind checks, foreign keys, a unique authority per managed run/work/standalone step, and a unique active-step binding. The canonical claim plus `step_runs.state`, `attempts` and the run's state must match to execute; nonce alone is never a capability for any step. `step_attempts` remains history and retry accounting. Generation and attempt are public fences, not secrets.

Rebuild `path_leases` to reference `claim_id`, carrying only reservation ID, optional durable work reference for history, normalized path/mode and creation/release facts. Remove its token, `until`, holder and lane copies; obtain those through the claim join. Rebuild `work_items` without authoritative claim columns; derive its public claim fields/status from the claim. Retain domain status, purpose, scope, handoff and history. `claimed` becomes a public projection of an unreleased claim (time separately determines liveness); an expired claim must not erase the generation needed to reject stale settlement. Rebuild `step_runs` without owner/until/nonce columns; retain `leaseOwner`/`leaseUntil` in its public API as joined projections for compatibility.

Keep the stable synthetic work ID for lineage and host inspection. Its terminal delivery status follows the run: verified success is completed, cancellation is cancelled, failure is closed as cancelled with the run failure reason (not successful delivery). Blocked/waiting runs release authority and remain blocked, excluded from generic ready/claim lists; `claim_work` resumes them after gates. No cancelled/failed delivery item is reopened as executable ordinary work. Business work associated with the run is a separate purpose and is not automatically completed or cancelled by this synthetic delivery transition.

### Transitions and fences

1. **Acquire:** gate a ready step, validate artifact/lane/aliases, check overlap, allocate or transition its authority, rotate nonce, bind step+attempt, write path scope, attempt and events atomically. A delivery authority already executing refuses another executable step, even for the same owner. Do not consume retries on refused paths. Preserve the prior-preparation recovery predicates and rollback boundary.
2. **Renew:** heartbeat and courtesy renewal update only `work_claims.until`, never a step/path/work copy; use canonical times and MAX semantics. Renewal cannot resurrect an expired or released generation. Dedupe courtesy renewal when a session owns both the workflow and work projection. An acceptance retry retains the existing non-renewal exclusion.
3. **Submit/fail/retry:** authenticate owner/executor, nonce, generation, active step, attempt and time. Close the attempt using the existing failed-versus-expired budget rules. For a continuing managed run, clear active binding and enter custody, keeping this same deadline; the old step is no longer submit-able. The next acquisition rotates nonce and increments only the newly attempted step. For non-delivery step claims, release authority on settlement.
4. **Pause or finish:** kernel workflow transitions reconcile delivery state and claim in the same transaction, regardless of broker or CLI caller. Blocked/decision waits release custody as today; terminal transitions release it and terminalize delivery metadata. Preserve current artifact receipts/execution checks before marking successful delivery. After-step cancel retains executing authority until submission/expiry; immediate cancel fences it at once. Always reap expired leases before deciding whether cancellation must wait.
5. **Expire/recover:** live queries exclude `until <= now` without requiring a sweeper. The next write records expiry and closes a bound attempt at most once, then releases authority; recovery can reacquire the same run with a new generation. Observed early session termination may fence managed execution, but an explicit offered handoff retains its directed hold through the single term even after its offerer ends. No new request may automatically replace prior writing/actions, extant artifacts or ambiguous custody.
6. **Handoff:** authenticate current nonce; for managed execution close the bound attempt as paused, return its step to ready, clear execution and enter offered custody atomically. The offerer keeps custody and the same credential until acceptance, release or expiry; it cannot submit the paused attempt. Preserve the current longer handoff hold. Acceptance rotates nonce and generation, moves actual scope or reports dropped collisions, marks receipt, and enters custody. It transfers no approval and must never replay a writing action. Recipient next calls workflow acquisition, which revalidates gates, evidence and required paths. Preserve lost-response recovery only for the exact accepted generation, recipient and lane, without renewal. Cancellation through the run can still terminate an offer.
7. **Takeover/release:** ordinary ledger rules keep their quiet-cap and parent-agent semantics. Managed execution requires expiry or observed termination, plus recipient-aware offers; custody takeover never grants execution. Exact-generation expired cleanup is allowed, but stale completion/cancel/renew is refused. Managed `work release` with an active step must fail with recovery to checkpoint/handoff or run cancellation, rather than silently freeing its path; completing/reopening a synthetic item independently also refuses. Lane transfer/drop behavior remains visible to the caller.

Kernel serialization can wait for a lock; it must produce either the complete transition or no transition. Missing session/process evidence means unknown and waiting for term expiry, not a guessed death. Missing/corrupt claim subject or path identity refuses acquisition. A failed evidence reader blocks success, never releases a second independent authority accidentally. Throughput, latency and production recovery rates for this proposal are **unmeasured**.

### Format-6 upgrade of in-flight runs

Use the existing `construct migrate` path: stop all Construct holders, inspect them, take the private SQLite backup under the upgrade lock, recheck the stored format, migrate transactionally, validate foreign keys/shape/invariants and stamp 6 last. Migration policy is deliberately fencing, not transparent continuation of old capabilities:

| Existing state | Conversion |
| --- | --- |
| Ordinary live ledger claim | Preserve owner/session/agent/lane, exact term, scope and offered handoff semantics in one work-kind row; reissue its nonce. Old token cannot renew, release or settle. Holder recovers through explicit new-build recovery using observed stopped-session evidence/expiry; do not publish reissued secrets in migration output |
| Managed delivery with one matching live step and matching holder provenance | Build one managed row with that active binding, run/work identities, lane and scope. Use the **earlier** step/work expiry so migration does not silently grant extra time. Reissue nonce. Resumption uses the normal observed-ended/expired reclaim path and next attempt, retaining succeeded steps and evidence. Migration does not spend a validation failure or automatically rerun an action |
| Managed delivery live in a between-step gap | Convert the existing delivery claim to custody, with its existing term/scope and no executable binding; reissue nonce. Keep explicit offers, directed recipient and original hold. No fake ready-step holder |
| Run with no stored delivery but an active local-artifact step | Derive the intended path from frozen intake, validate admission/run identity and lane provenance, and collision-check under the upgrade lock before creating the missing metadata/authority. If scope/lane/holder is not provable, abort the upgrade with item-specific recovery; never infer it from a current shell checkout |
| Non-artifact step lease | Convert to a step-kind authority with exact owner/term/attempt binding and a reissued nonce. Preserve independent DAG step claims. No delivery item is invented for an absent local destination |
| Cancelled or failed run with open/claimed delivery item | Preserve work ID/history and terminalize the synthetic item as cancelled with an explanatory run outcome. Release scope and carry no live authority. Never delete artifacts, children, links or execution evidence. Business child work survives for explicit disposition |
| Succeeded run with delivery residue | Reconcile artifact verification before calling delivery completed. If unavailable or inconsistent, retain a non-ready historical/blocked reconciliation record with no execution capability; do not infer success from the terminal run flag alone |
| Expired step/work claim | Import durable scope/history, carry no live capability. Close any still-open expired attempt once through existing expiry accounting, retaining its failed-versus-expired distinction; ready the step or fail it only under its original budget rules |
| Missing/contradictory owners, malformed offers, extra unmanaged paths, multiple simultaneously leased artifact steps, unsafe aliases or collisions | Abort the entire upgrade with a bounded report of IDs and reasons, no secrets. Reconcile in the old build and retry. Do not select the newest owner, longest expiry or union of paths as authority |

An active step plus an explicit delivery handoff, or an active step whose work term already expired, is a contradiction needing explicit pre-upgrade reconciliation, not a reason to transfer execution. Lane data comes from the stored reservation/claim and matching generation-bound session evidence; no path or branch is invented. Require all rows for a managed scope to agree before rebuilding it.

Preserve append-only activity unchanged; add migration events containing IDs, prior outcomes and fencing reasons, never tokens. Invalidate pending acceptance-recovery capabilities for pre-upgrade generations while retaining the public offer/packet and recipient hold; recipients prepare a fresh capability. Export/restore remains durable-data-only and never imports new claim authority. Existing references to delivery work IDs continue to resolve.

After a successful upgrade, old credentials are intentionally unusable. Recovery instructions must say to inspect run/work status and use permitted recovery; never replay completed steps or recover merely by knowing a session name. A stopped holder whose process/session state is unknown waits for the preserved deadline. The original backup is the rollback point before any new-format work is performed; after new writes, downgrading requires stopping holders and an explicit reconciliation of those writes, not blindly restoring a stale backup.

## Adversarial review of the completed proposal

This is self-review. The best case for A is that all callers, including CLI cancellation and executor cleanup, must pass through one renewable row; there is nothing else to forget to release. The best case for B is its much smaller mutation surface: a projection from a proven step lease is easier to trust than a new state machine. The deciding constraint is that present custody and directed handoff outlive an executable step; removing them would change safety behavior.

### Six challenges and results

1. **Strongest failure mode:** A recipient accepts custody in a checkout where an inherited path is dropped, then the unified token is accepted as authority to submit or write the next step. Result: two writers despite apparently successful transfer. Serious finding 1 below; acceptance must yield custody only and execution must reacquire its full scope under gates.
2. **Best alternative:** B eliminates the cancellation cleanup bug without centralizing unrelated ordinary work or migrating all claims. Result: strongest version still lacks custody during step gaps and explicit offer holds. Adding phase/lane/expiry state to preserve them is A with step-shaped storage. Rejection stands for the stated requirements; B would win if those requirements were deliberately removed.
3. **Load-bearing claims:** checked the actual `liveRows` join, cleared step fields on settlement, owner-gated broker helper, direct CLI/service cancellation, separate renewal paths, transfer/drop contract, immutable handoff receipt logic, current format and migration guards, and the cancellation fix in git. The orphan observation is attributed to the user, not claimed as independently reproduced. Proposed correctness and migration performance are unmeasured. Result: source supports the diagnosis; implementation acceptance remains open.
4. **Assumption inversion:** suppose a run leases two ready steps for the same artifact, the holder is remote/unknown, the destination has spaces/aliases, or old binaries continue writing. Result: serialize only managed artifact execution; refuse ambiguous in-flight upgrade; unknown does not mean dead; retain conservative scope/alias checks; enforce format fencing and stopped-holder migration. Serious findings 2 and 3 below.
5. **Who bears the cost:** a mistaken decision corrupts the absent concurrent agent's edits and the user's artifacts; migration downtime and token recovery fall on the operator, not just the implementer. Result: retain directed holds, exact-generation recovery and backup, expose dropped scope and rehearse on a live copy before rollout. No claim of human acceptance is made.
6. **Five-minute hostile expert:** “You have collapsed rows but kept two clocks, moved approvals with a handoff, or removed the path lock between successful steps.” Result: schema removes duplicate authority fields; offered/custody states carry one deadline and no execution; failure injection and inter-step races are mandatory. Also ask “what about non-artifact DAGs?” They retain per-step authority rather than suffering an unannounced global serialization change.

### Findings and controls

1. **Custody mistaken for executable permission** [severity: serious]
   Failure: accept/takeover succeeds with dropped scope and a recipient submits under a transferred approval.
   Evidence: existing `transferPaths` intentionally drops collisions; `acceptWork` explicitly transfers no step lease/approval.
   Smallest fix: require `phase='executing'`, full required scope, exact active binding and fresh recipient gate; acceptance alone yields custody. Covered by transition rules and required tests.
2. **Parallel in-flight artifact steps cannot be collapsed arbitrarily** [severity: serious]
   Failure: migration chooses one nonce and silently leaves another old writer able to act, or loses its output/action history.
   Evidence: `claimInRun` considers ready DAG steps without a global no-other-leased-step condition, while delivery identity is per run.
   Smallest fix: refuse ambiguous upgrades; reconcile old holders first; enforce one executing step per artifact authority after upgrade. Preserve non-artifact concurrency. Covered by migration refusal and race tests.
3. **Mixed-format writers or credentials recreate split authority** [severity: serious]
   Failure: an old MCP process renews removed columns or a pre-upgrade credential operates against a new owner.
   Evidence: state migration explicitly requires stopped holders; existing open-store/restamp tests guard this boundary, and prior upgrades reissued work secrets.
   Smallest fix: explicit format bump, stopped-holder backup, remove old fields, reissue/fence both token families, invalidate old acceptance recovery and test already-open writer refusal. Covered by migration plan.

The strongest objection to A is that this is a larger shared-state migration than deleting a broker helper. That objection is correct about cost, but a cleanup-only patch cannot represent custody, execution and transfer under one credential; it leaves the original divergence available through generic work mutations and direct service calls. The accepted controls constrain the larger change to one authority engine, reuse the existing overlap/handoff algorithms, keep stable work/history addresses, and forbid rollout until old safety tests and live-copy migration checks establish the intended behavior.
