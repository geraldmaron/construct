# Construct fresh-user intake — 2026-10-09


Subsequent authorized local implementation and fresh-consumer evidence are tracked in [the implementation assessment](../implementation-2026-10-09/RESULTS.md). This document retains the original audited baseline.

## Executive verdict

**The requested experience is not yet established by alpha.26.** Construct has a substantial working kernel: project discovery, typed intake, versioned catalogs, native work, leases, workflow gates, source manifests, evidence resolution, drift rules, and durable resumption. A cooperating caller can use those pieces to complete an outcome. That is materially different from demonstrating that a fresh user can ask naturally, have the right methods and connected sources selected, and receive reliable results after the session exits.

The decisive gaps are **truthful capability/readiness reporting, execution-backed verification, trustworthy source invalidation, and an actual scheduled executor**. A fresh native Codex task produced a correct grounded outcome and correctly revised it after controlled source corrections, but neither turn created a Construct session, run, deliverable, source observation or skill-resolution record. Natural activation across supported hosts remains unproven; the cause of absent tool use is unresolved. See [the independently scored native trial](NATIVE-TRIAL.md). More skill prose alone will not close these gaps. Preserve useful contracts; repair the boundary between declared intent, observed capability, executed work, and verified outcome.

**Recommendation:** accept the user's outcome as the product target; gate claims about autonomous or cross-harness reliability on the acceptance matrix below. Do not approve a broad rewrite from this intake. The local follow-up program is `work-18402da5`; its nine bounded items and links to existing work are in [BACKLOG.md](BACKLOG.md).

Assessment basis: commit `9a0c835bec7c27655ab65e5255f0655a9fa9c30d`, package `3.0.0-alpha.26`, inspected on 2026-10-09. A public-registry install of `@geraldmaron/construct@alpha` matched **456 built runtime/catalog files with no differences** ([comparison](evidence/package-comparison.json)). Subsequent concurrent repository edits are outside this baseline; none were reverted, staged, or committed by this assessment. Code links below are pinned to the assessed revision.

## Recommended architecture boundaries

**Kernel owns durable contracts:** project identity/constitution, source and capability records, dependency graph, statements and supersessions, work/run/step state, leases, permission decisions, provenance/evidence status, invalidation, receipts and audit events. It validates structural invariants without pretending to infer every domain's truth.

**Host adapter owns interaction:** activation instructions, typed intent from the model, visible tool inventory, sandbox and authentication probes, approvals/elicitation, model execution, and verified tool-call capture. It reports observed capability with time, scope and evidence. All adapters pass the same semantic contract suite; configuration format and hook mechanism remain host-specific.

**Source adapter owns access and observation:** API/OpenAPI operations, MCP tools/resources, files/Git and future transports map into a versioned observation envelope. Include source principal, method/query, access scope, schema fingerprint, stable identity, content hash, provider revision, observed/effective time, coverage/cursor, units, deletions, sensitivity, authority and report/witness status. Adapter-derived metadata is evidence, not an instruction. Discover only accessible sources; unknown sources stay explicit unknowns.

**Model and method layer owns interpretation:** select and compose specialist methods based on outcome, risk, domain, uncertainty and capability; produce an inspectable plan and evidence dependencies. Obtain current doctrine where needed. Detect possible semantic conflicts with uncertainty and citations; do not let model opinion bypass deterministic gates or impersonate user approval. Composition needs compatible input/output contracts and explicit stop conditions, not a growing list of named personas.

**Executor and clock are separate external contracts:** a clock emits a due event; a durable executor loads project state, acquires a run, invokes the supported host/model, observes budgets and approvals, renews leases, persists receipts, and delivers an authorized result. The kernel need not become a daemon. State restoration, authentication, cancellation, idempotency, retry policy and delivery receipt must be tested. Without a provisioned executor, say “defined, not active” or “blocked”; closing chat cannot leave an implied promise of continued work.

**Experience layer reports one honest status:** installed, connected, authorized, observed, eligible, queued, running, waiting on person, failed, verified, delivered. A user should get the next useful action without learning these internal APIs. Expose omissions and material blockers, not every implementation detail.

Primary-source research supports these separations, not a requirement to adopt a particular framework: [MCP discovery and schemas](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [OpenAPI interfaces](https://spec.openapis.org/oas/v3.2.1.html), [Agent Skills packaging](https://agentskills.io/specification), and [MCP Tasks opt-in](https://modelcontextprotocol.io/extensions/tasks/overview) describe distinct contracts. None supplies Construct's domain authority, model judgment, or executor automatically. See [SOURCES.md](SOURCES.md) for current versions and caveats.

## Adversarial assessment

**VERDICT: Needs validation** for the fresh-user product promise. The blanket claim that current alpha already satisfies it is rejected by the demonstrated executor and verification gaps. Keep the working foundation and apply bounded controls.

**Steelman.** Host models already interpret requests, have tools and can research; Construct should supply durable organization, reusable methods and gates rather than build another general agent. The current typed-intake architecture is consistent with that. Scripted outcomes and substantial deterministic tests show this is more than documentation.

1. **Concrete failure:** “Every Monday summarize the current service risk.” The clock records a runnable event with no executor. If manually resumed, an unchanged provider timestamp hides changed units; a citation resolves; `passed:true` validates the result. Each layer appears individually successful while the promised result is missing or wrong.
2. **Best alternative:** A thin skill pack using the host's native scheduler and source tools may outperform an expanding kernel for simple personal use. Test this baseline on identical prompts. Construct earns complexity through durable cross-session evidence, truthful permissions, dependency invalidation and outcome verification; retain only machinery that improves those measures.
3. **Claims under attack:** “Qualified,” “validated,” “available,” “healthy,” and “started” each need a documented evidentiary meaning. Current behavior supports weaker interpretations than an ordinary user may infer. Claims should weaken until evidence strengthens.
4. **Invert assumptions:** The host misses the skill; source text is malicious; credentials expire; the most relevant decision is older than the retrieval cap; schema adds a nullable field or changes units without version; clock fires twice or late; worker exits after a write; two teammates disagree about authority. These are acceptance cases, not exotic edge cases.
5. **Who pays:** A user pays in silent wrong decisions and missed work; a team pays in duplicate effort and stale context; operators pay in token cost, storage, connector maintenance and recovery. Budget, ownership, retention/deletion, secret redaction, evaluation drift and incident diagnosis belong in the contracts.
6. **Hostile expert objection:** “Your client hand-fed typed requests and source reports, so you have not tested the product.” Correct. Public CLI/MCP tests establish boundary behavior only. The native trial now supports correct host behavior without Construct orchestration; unavailable CLI/tool-exposure evidence is not counted as a pass. A held-out first-question evaluation with no skill hints and actual executor continuation is indispensable.

Refuters: a digest-bound independent live record proving successful unprompted activation would narrow the routing gap; a verified external executor/state recipe would narrow the scheduling gap; failing negative controls would confirm that proposed gates are too weak. Code showing a timestamp/mtime fast path is harmless is insufficient against reproduced wrong results; the byte-change controls must pass.

Premortem: six months of added skills and connectors produce a persuasive demo while first-run activation, source completeness and autonomous delivery remain unreliable. Prevent this by making consumer outcomes and adversarial controls release-blocking, including a simple host-native baseline and cost/latency measurements. Do not count number of skills, passing schema tests or backlog volume as adoption evidence.

Additional requirements absent or insufficiently explicit: multi-user authority and revocation; stable tenant/source identities; retention and deletion of observed text; versioned schema mapping; replay-safe external effects; secret handling in evidence/logs; bounded cost/time; human escalation and failed delivery; availability/backup of durable state; relevant-change precision/recall; knowledge expiry; interoperability version negotiation; traceable cancellation. These are distributed across the bounded items rather than a mandate for a new monolith.
