| `concurrency-busy-timeout-and-journal` | partially-confirmed | high | **State store has no busy_timeout and uses rollback journal: concurrent sessions fail with 'database is locked'.** openStateStore (src/kernel/state/open.ts:74) opens node:sqlite with the default busy timeout of 0 and leaves the database in rollback-journal (DELETE) mode; the real project DB is in DELETE mode. Two writers overlapping, or a read that lands inside another process's commit window, fail immediately with 'database is locked' (including inside openStateStore's format check, surfaced as 'cannot open the state database'). Reads during another process's open-but-uncommitted write transaction do succeed, so not every overlap fails. | `external-sqlite-concurrency-unsafe` | confirmed | critical | **State store has no busy timeout and uses rollback journal; concurrent sessions get 'database is locked'.** The claim holds, and the real defect is worse than stated. (1) The only DB open, src/kernel/state/open.ts:74, uses busy timeout 0 with the rollback (delete) journal. A 4-process race produced 9 orphaned entity rows from partly committed createWork calls plus spurious FOREIGN KEY failures. (3) New: if a serve process starts while another session holds a lock, openStateStore throws. serve then silently drops to the unbound MCP surface for the whole session and tells the user to 'Run construct init', which is misleading. Failure rates depend on workload (roughly 4% to 97% per worker in my runs), so the 'a third of calls' figure is illustrative only. On WAL: switching lets readers and the writer run together, but writer-vs-writer contention still needs a nonzero busy timeout, and the depth leak needs its own fix. Raising the engines floor to a Node that bundles SQLite >=3.51.3 (e.g. 22.23.1) or a backport is prudent before enabling WAL. It is not mandatory: the primary source calls the bug extremely unlikely. |
