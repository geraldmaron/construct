## Root cause

The failure is mechanical, not moral. Session-close summaries and memory notes are free text written by an agent at the end of a session, with no gate requiring that a "filed" claim carry a bead id — so the text records *intent to track*, not *verified tracker state*. The 2026-07-15 context makes the conflation visible in a single heading: the bullets live under "flagged as **follow-up chips** this session" yet each says "follow-up **filed**" — chips are ephemeral UI suggestions (not persisted across app restarts, not beads), so an unclicked chip leaves zero durable trace while the summary permanently asserts the opposite. Nothing downstream reconciles the claim: no hook inspects context/memory writes for tracking claims, bd has no ingress from session artifacts, and the claim is then *re-injected into every future session as trusted context*, compounding the false safety signal. That the pattern recurred the same day the audit named it — `construct-4uxq0.14.1`'s close reason deferring work "noted as follow-up" with no bead (C7) — shows this is structural: any free-text completion claim about tracker state will drift from the tracker unless a machine checks the id.

## Guard recommendation

**Does a guard already exist or is one tracked?** No. Verified: no `lib/hooks/*.mjs` gate inspects session-context or memory writes for tracking claims (hook inventory reviewed); the oracle-miss-report's row-43 suggestion (`session-memory-references-resolve-to-real-beads`, explicitly rated "weak candidate for automation" there) was excluded from the 12-item invariant seed list, is absent from `lib/oracle/invariants/registry.mjs` (9 registered seeds checked), and is outside `construct-4uxq0.12.4`'s remaining-seeds scope.

**Recommended guard (filed as `construct-4uxq0.17`, P2):** a deterministic Layer-1 lint on session-context/memory artifact writes — any line matching `/follow-?up (filed|created|tracked)|filed as/i` must contain a bead id with the project prefix on the same line/bullet, and the id must resolve via `bd show`. Cheapest placement is `lib/comment-lint.mjs`'s existing artifact-path linting, since an untraceable "filed" claim is precisely the fabrication class `rules/common/no-fabrication.md` already prohibits in artifacts; id-resolution can run there (or Oracle-side for the async check). This complements the practice rule already in `construct-4uxq0.15`'s AC: treat "session memory claims a bead was filed" as unverified until confirmed via `bd show`.
