# External agent-framework fit matrix (R1)

Ten external frameworks and interop protocols, researched against Construct's architecture (a JavaScript/Node.js meta-orchestration system with a fixed, curated 12-specialist roster, machine-checkable handoff **contracts** between specialists, a skills layer, and MCP host integration). Every load-bearing claim traces to a primary source fetched 2026-07-13 (the GitHub repo/README/LICENSE, PyPI/npm, the official docs, or the spec); versions were cross-checked against package registries. Interpretations are labelled `[INFERENCE]`; unconfirmed items `[unverified]`. Prior June-2026 coverage (aider/Cline/Goose/OpenHands/smolagents, AGENTS.md, ACP) was not re-done.

Verdict taxonomy: **adopt-pattern** (borrow the idea into Construct's own layer) · **adapt-behind-adapter** (integrate only behind a boundary) · **retain-as-benchmark** (a reference to measure against, not adopt) · **reject** (structural non-fit).

## What the research says about Construct

**1. Construct's central thesis is externally validated — by convergence, not by one source.** Three independent projects arrived at the same idea Construct already ships: a machine-checkable contract as the artifact handed between roles. CodeTeam's CTO agent normalizes a design into "a machine-checkable contract that specifies file ownership, public interfaces, and dependency constraints" for Developer agents — a near-verbatim description of Construct's handoff contracts + postconditions, reached independently in an academic prototype. PydanticAI enforces typed outputs and *returns validation failures to the model to retry until the schema is satisfied*. Google ADK's Task API bounds a delegation with `finish_task`/return-of-control and a single-turn-controlled-output vs multi-turn mode. The contract-mediated handoff is not a Construct idiosyncrasy; it is where the field is converging.

**2. Nothing here is a drop-in dependency.** Eight of the ten are Python (or Python + .NET); the two Node-native ones are either not an orchestration layer (NanoClaw is a single-agent assistant harness) or unlicensed prototypes (CodeTeam). Even the frameworks with official TypeScript ports (OpenAI Agents SDK, LangGraph) carry a full agent-loop/graph runtime whose abstractions collide with Construct's opinionated fixed-roster + contract model. **The transferable value is patterns, not runtimes** — which is also the cheapest and most license-safe path.

**3. The biggest capability gap the field exposes is durable state / resume.** Construct's handoffs execute but do not yet persist-and-resume mid-chain. Every mature framework has solved this and they converge on one shape: snapshot state at a step boundary, store it behind a pluggable backend, resume by an id. LangGraph's **checkpointer** is the reference implementation (per-superstep snapshot, in-memory/Postgres/SQLite savers, `thread_id` resume, and — notably — the *same* mechanism powers its HITL interrupts). CrewAI's `@persist` (resume vs fork), PydanticAI's durability-as-pluggable-concern (Temporal/DBOS), and ADK's SessionService are the same pattern. **Recommendation: a checkpointer-style abstraction for Construct's orchestration runtime** (snapshot the run's task chain + contract state at each handoff boundary; resume by `runId`) is the single highest-value pattern to adopt, and it unifies with the approval-gate work below.

**4. Human-in-the-loop has a standard shape too: serialize → approve → resume.** OpenAI's `RunState` serialize/deserialize, PydanticAI's `DeferredToolRequests`/`DeferredToolResults` (approve / deny / override-args), LangGraph's interrupt-on-checkpoint, and MCP sampling's "review/edit/deny" gate are the same protocol. Construct's out-of-band approval tokens already gate destructive actions; **modeling an approval as a serializable pause on the same state the checkpointer persists** would make Construct's HITL resumable across processes, not just in-session.

**5. The async task lifecycle has standardized under the Linux Foundation.** MCP **Tasks** (SEP-1686, Final) and **A2A** (v1.0.0) independently landed the *identical* lifecycle: `submitted → working → input_required → {completed, failed, cancelled}`, with client-generated idempotent IDs and a correlation key threading every related message. Both are now Linux-Foundation governed. **Recommendation: align Construct's terminal-status taxonomy (`construct-72gqn.9`/`.16`) and durable-handoff vocabulary to this shared lifecycle** — it is one standard that keeps Construct interoperable with both ecosystems at once, and it validates the honest-terminal-status work already done.

**6. MCP `sampling` is deprecated (spec 2026-07-28, SEP-2577) — and the deprecation validates Construct's design.** The spec now tells implementers to "migrate to integrating directly with LLM provider APIs" instead of the server→host sampling round-trip. Construct's host-backend already materializes a prompt envelope and lets the host execute with its own keys/model — precisely the direct-integration path the standard now recommends. **Recommendation: do not retrofit onto sampling; keep the sampling HITL controls (review/edit prompt, review/deny response) as the human-gate pattern, and note this reconciles the deferred MCP-spec bead (`construct-rf26.20`).**

**7. Eval-as-code is the norm, and Construct's H2 behavioral certification is aligned with it.** ADK's evalset + `adk eval` (tool-trajectory match + LLM-judge), PydanticAI's `pydantic-evals` (OTel-native), CrewAI's `crewai test`, and AutoGen Bench all treat evaluation as a re-runnable, scored, version-controlled artifact — exactly the direction of Construct's just-built `specialist-behavior-live` gate and team-vs-solo comparison (`construct-72gqn.14`/`.18`). The gap to close later is **OpenTelemetry-native tracing** (ADK, PydanticAI, AutoGen all standardize on it), which would make Construct's traces portable.

## Verdicts and the follow-on decisions they seed

- **adopt-pattern** (borrow into Construct's own layer): OpenAI Agents SDK (handoff primitive, RunState HITL), LangGraph (checkpointer, interrupt-HITL), Google ADK (Task API delegation contract, eval-as-code), CrewAI (delegation-as-tools, resume/fork), PydanticAI (typed-output-retry as contract enforcement, deferred-tool approval), MCP Tasks (lifecycle + correlation), CodeTeam (contract-as-handoff-artifact — idea only).
- **adapt-behind-adapter**: A2A — the right standard *if/when* Construct exposes specialists for external federation (auto-emit an Agent Card per specialist profile at `/.well-known/agent-card.json`); internal handoffs stay native. Degrades to retain-as-benchmark absent a federation requirement.
- **retain-as-benchmark**: AutoGen (maintenance mode + named successor make it a reference, not a bet — but its Swarm `HandoffMessage` idiom and layered Core/AgentChat split are worth studying); NanoClaw (best-evidenced MIT/Node Claude-SDK harness — borrow its OS-level container-per-agent isolation for a future sandboxing story, but it is not multi-specialist orchestration).
- **reject / do-not-build-on**: AgentForge (GPL-3.0 copyleft + Python + general-purpose scope); MCP **sampling** (deprecated).

**Material findings worth their own ADR/RFC** (not authored here — R1 is the brief): (a) a checkpointer-style durable-handoff-state design amending the ADR-0065/0067 lineage; (b) aligning Construct's handoff/terminal-state vocabulary to the MCP-Tasks/A2A shared lifecycle; (c) a decision to keep host-executes-the-prompt as canonical now that MCP sampling is deprecated, closing `construct-rf26.20`. Each of these is a bounded, evidence-backed next step, not a rewrite. No external framework should become a core dependency without its own benchmark + threat analysis + ADR, per the audit's own guardrail.
