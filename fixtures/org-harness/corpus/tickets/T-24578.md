# T-24578: Source Hydrator for ApplicationSets

> Origin: https://github.com/argoproj/argo-cd/issues/24578 (verbatim base; see PROVENANCE.md for edits)

# Summary

Add Source Hydrator support to `ApplicationSets`, similar to the existing `Application` Source Hydrator feature.

# Motivation
I want to control the destroy order of Application creation/deletion for a cluster in a multi-cluster environment when deprovisioning it.
`ApplicationSets` don't support DAG-based `Application` destroy ordering across multiple `ApplicationSets`. This means that if there are multiple `ApplicationSets` deploying to a cluster, the deletion ordering of the resulting `Applications` is "shadowed" by the `ApplicationSets`.
This leaves users with no alternative other than to implement an app-of-apps patterns per cluster to use sync waves for controlled destroy ordering.

## Workaround

<img width="5880" height="1674" alt="Image" src="https://github.com/user-attachments/assets/34550501-2851-4640-b502-2481ee7e2a5e" />

Shown in the diagram is a workaround I came up with by using an `Application` following the app-of-apps pattern per cluster.  The (conditional) templating functionalities of `ApplicationSets` (such as conditionally enabling an `Application` for a cluster, templating helm values, etc) is recreated with a custom helm chart. 
This creates an unnecessary layer of indirection that I'd much rather avoid in favor of using `ApplicationSets`. 
This allows the sync-wave feature to work as expected, as all `Applications` of a cluster are owned by a single app-of-apps `Application`.
Could be that I'm structuring my code unidiomatic and that this problem could be solved with ArgoCD natively. If that is the case, I'd be happy to hear about your feedback.

# Proposal

<img width="6306" height="2120" alt="Image" src="https://github.com/user-attachments/assets/84a5b435-dc31-4d09-8cff-885f88eb01df" />

The `ApplicationSets` could support the Source Hydrator feature that would allow for ArgoCD-native templating with `ApplicationSets`. The resulting `Applications` would then be synced to a Git repo. Ideally, there are capabilities to customize the location of the resources in the repo.
This would allow an `ApplicationSet` (named `appset-of-apps` in the diagram) to template an `app-of-apps` named `Application`  based on cluster generator. This `Application` would then pull all hydrated `Applications` per cluster and enforce the resource dependencies through sync-waves.

I'm leaving implementation-specifics out of this proposal for now, as I'm not really qualified to propose them without doing some extensive research:)
