# T-27833: Disallow Applications to sync namespace resources

> Origin: https://github.com/argoproj/argo-cd/issues/27833 (verbatim base; see PROVENANCE.md for edits)

# Summary

We would like to let Application to create namespaces dynamically but the Application should not have persmission to sync `kind: namespace` resources into the cluster.

# Motivation

We use ApplicationSet to create Application for each review environment. Each review environment starts with the prefix of gitlab group they are in + branch name, eg: `group1-project1-feature-branch`.

The ApplicationSet controls the labels on the created namespace with `managedNamespaceMetadata`.

We would like Argo CD to dynamically create (and delete) namespaces for each review environment with `CreateNamespace=true` flag on the Application spec. The namespace created by Application will carry labels defining the security boundry (eg: `pod-security.kubernetes.io/enforce: baseline`) and other configuration.

What we tried:

- We restrict the Application to be allowed to manage namespaces starting with `group1-project1-*` by setting the AppProject `clusterResourceWhitelist` with `kind: Namespace` and `name: group1-project1-*`. This scopes down which namespaces the Application can touch but does not remove permissions for namespace resource.

- We have added a policy to the AppProject forbidding a user to perform any action on namespace resource by defining policy `p, proj:<appproject-name>:<role>, applications, */*/Namespace/*/*, <appproject-name>/*, deny`. This RBAC policy controls actions taken through ArgoCD's API/UI, but it does not prevent ArgoCD's Application controller from applying resources committed to the repository.

The user is still able to commit a namespace resource into the repository Argo CD syncs from. If the name on the namespace matches the `clusterResourceWhitelist` pattern (and it is not very hard to guess the name since it follows the pattern mentioned above), the namespace will be deployed to the cluster potentially overwriting the labels set by the Application. The users can easily escape their permission boundry by not defining the `pod-security.kubernetes.io/enforce: baseline` label, allowing for privilaged workloads.

This issue is very similar to https://github.com/argoproj/argo-cd/issues/22869 which I believe was resolved only partly.

# Proposal

One option would be to use the service account impersonation feature but have option which rasources are handled by the Argo CD control plane and which resources are controlled by the impersonalted SA. For the impersonated SA we could then remove permissions for `kind: namespace`. The Application bootstrapping including the namespace creation would use the argo cd SA while the sync operation would use the impersonated SA.
