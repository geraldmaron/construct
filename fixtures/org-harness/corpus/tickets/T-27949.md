# T-27949: ApplicationSet ProgressiveSync leaves child applications out of sync on source change

> Origin: https://github.com/argoproj/argo-cd/issues/27949 (verbatim base; see PROVENANCE.md for edits)

**Describe the bug**

RollingSync can miss a spec-only generated Application change when the generated child `Application.spec` changes but the resolved source revision does not.

This looks related to the fix for https://github.com/argoproj/argo-cd/issues/26685, but there still appears to be a timing gap in v3.4.2.

In our case, an ApplicationSet generates child Applications whose Helm parameters include an image tag. On a PR update, only the generated child `Application.spec.source.helm.parameters` changes. The Git `targetRevision` remains the same.

We are also piloting the source hydrator on this repository: every hydration cycle lands a fresh commit on the hydrated branch that the child Applications deploy from, and each of those commits is picked up as a source change.

Observed sequence:

1. ApplicationSet detects the generated child Application spec differs from the current child Application spec.
2. The child Application is still `Synced` and `Healthy` for the previous spec at that moment.
3. Progressive sync status is reset to `Waiting`, but then immediately promoted back to `Healthy`.
4. The ApplicationSet controller updates the child Application spec to the new Helm parameter.
5. The child Application becomes `OutOfSync`, but ApplicationSet progressive status remains `Healthy`.
6. No sync operation is created because `syncDesiredApplications` only syncs Applications in `Pending`.

The rollout then reports complete even though the child Applications are `OutOfSync`.

Looking at the source for this, it seems that:
- `specChanged` is detected in `updateApplicationSetApplicationStatus`.
- Because the current child Application is still `Synced/Healthy`, the status is immediately promoted to `Healthy`.
- Later, once the child spec update makes the app `OutOfSync`, the desired spec and current spec are already equal, so `specChanged` no longer fires.

**To Reproduce**

Minimal shape:

1. Enable ApplicationSet progressive syncs.
2. Create a RollingSync ApplicationSet that generates at least one Helm child Application.
3. Let the child Application become `Synced` and `Healthy`.
4. Change only a generated Helm parameter in the ApplicationSet template/list data while keeping `targetRevision` unchanged.
5. Observe the child Application spec update and become `OutOfSync`.
6. Observe ApplicationSet `status.applicationStatus` remains `Healthy` and no new child Application sync operation is created.

Example ApplicationSet:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: rollingsync-spec-only-repro
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - list:
        elements:
          - name: rollingsync-repro-app
            phase: phase-1
            imageTag: v1
  strategy:
    type: RollingSync
    rollingSync:
      steps:
        - matchExpressions:
            - key: phase
              operator: In
              values:
                - phase-1
          maxUpdate: 1
  template:
    metadata:
      name: "{{ .name }}"
      labels:
        phase: "{{ .phase }}"
    spec:
      project: default
      destination:
        server: https://kubernetes.default.svc
        namespace: default
      source:
        repoURL: https://github.com/example/repro-chart.git
        targetRevision: main
        path: chart
        helm:
          parameters:
            - name: image.tag
               value: "{{ .imageTag }}"
               forceString: true
      syncPolicy:
        syncOptions:
          - CreateNamespace=true
```

After the app is healthy, patch only the generated parameter:

```
kubectl -n argocd patch applicationset rollingsync-spec-only-repro --type=json \
    -p='[
      {
        "op": "replace",
        "path": "/spec/generators/0/list/elements/0/imageTag",
        "value": "v2"
      }
    ]'
```

Expected state after patch:

- ApplicationSet progressive status should move the child to Waiting/Pending.
- ApplicationSet controller should create a sync operation for the child Application.
- Child Application should sync to image.tag=v2.

Actual state:

- Child Application spec changes to image.tag=v2.
- Child Application becomes OutOfSync.
- ApplicationSet status.applicationStatus remains Healthy.
- No sync operation is created.

Relevant status example from a live case:

```
status:
  applicationStatus:
    - application: pr-3606-frontend
       lastTransitionTime: "2026-05-20T20:46:03Z"
       message: Application resource has synced, updating status to Healthy
       status: Healthy
       step: "5"
       targetRevisions:
         - a8f5d3fe55cb36b2ee46653be32114f4966ac9b6
```

But the child Application is:

```
  spec.source.helm.parameters: image tag = new-sha
  status.sync.comparedTo.source.helm.parameters: image tag = new-sha
  status.sync.status: OutOfSync
  status.health.status: Healthy
  status.operationState.phase: Succeeded
  last successful sync operation applied: old-sha
```

Expected behavior:

When the generated Application spec changes, RollingSync should not mark the ApplicationSet child status Healthy based only on the pre-update child Application being Synced/Healthy.

It should keep the child in Waiting/Pending until the generated spec has been applied and a sync has occurred for the new desired spec, or otherwise store enough desired-spec identity in status.applicationStatus to avoid losing the trigger once the child Application spec is updated.

Relevant code path in v3.4.2:
- applicationset_controller.go: specChanged detects generated spec changes.
- Immediately after, a Waiting status can be promoted back to Healthy if the current child Application is still Synced/Healthy.
- syncDesiredApplications only creates a sync operation when the ApplicationSet child status is Pending.
